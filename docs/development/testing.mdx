# Testing

Use Corepack and the pinned pnpm toolchain:

```bash
corepack pnpm@10.12.4 run typecheck
corepack pnpm@10.12.4 run lint
corepack pnpm@10.12.4 run test:coverage
corepack pnpm@10.12.4 run eval:bugbot
corepack pnpm@10.12.4 run build
corepack pnpm@10.12.4 run validate:agent-docs
corepack pnpm@10.12.4 run validate:docs-page
corepack pnpm@10.12.4 run validate:documentation
corepack pnpm@10.12.4 run validate:workflows
corepack pnpm@10.12.4 run validate:specifications
git diff --check
```

`validate:documentation` also enforces heading fragments, the complete setup
workflow and single-action catalogs, parity between the six embedded issue
examples and their setup templates, and high-risk release contracts such as
the default-branch continuation prerequisite, npm direct-publish policy,
polling controls, and orchestration Variables. It also rejects removed public
inputs, actions, commands, and orchestration modes.

`validate:specifications` validates unique capability ownership, safe existing
repository-relative evidence paths, complete registration of top-level SDDs,
retrospective-baseline structure, and byte-for-byte freshness of the generated
`specs/CATALOG.md` view. It also enforces the communication-program test ledger:
at least 128 semantic-publication cases and 136 localization cases, allocated to
disjoint test files. Parameterized declarations count once, and removing tests,
inflating an allocation, or assigning one file to both budgets fails the gate.

The ledger lives at
`src/architecture/github_communication_test_budget.json`. Its qualifying counts
are a conservative audit of new Jest `it`/`test` declarations since the two SDDs
landed at baseline `0bb83b75^`; a table-driven declaration is not multiplied by
its data rows.

Merge-queue contract tests cover ruleset-only targets, classic/ruleset union,
GitHub Actions workflow parsing on target and candidate refs, external exact
attestations, setup/doctor drift, pre-PR and pre-enqueue ordering, queue
membership idempotency, and head-bound enqueue. These tests use provider fakes;
they never create a live queue entry or poll check runs.

These deterministic checks cannot inspect live GitHub/npm settings or judge
desktop/mobile, light/dark, and assistive-technology rendering; keep those as
explicit operator and human UX gates.

Tests MUST isolate environment variables such as `AGENT_PROVIDER`, `AGENT_MODEL_PROVIDER`, `AGENT_MODEL`, and `AGENT_EXECUTABLE`. Real provider smoke tests are separate from deterministic unit tests and MUST NOT run without authorization and cost controls. Coverage thresholds are enforced by Jest and must not be reduced to accommodate a new code path; add focused tests instead.

`eval:bugbot` runs the offline Bugbot quality harness. Corpus cases score precision, recall, F1, exact-location, severity, category, line distance, false positives/negatives, and confidence calibration independently, so prompt or model changes cannot hide false positives behind a single pass/fail number. `copilot bugbot-benchmark` can generate predictions with the real configured agent for a cost-controlled manual or scheduled gate; `copilot bugbot-eval` scores them. Ground truth is not passed to the agent. Extend the corpus when a production review exposes a new failure mode.

`copilot bugbot-analytics` aggregates content-free telemetry exported by the Action. Do not add prompt, diff, source, comment, response, credential, or rule content to the telemetry schema.

## Qualification source and runtime admission

New Bugbot qualification runs use an explicit committed implementation pin.
Before loading application modules, the corpus and review entrypoints compare
the physical `src/`, lockfile, compiler configuration and package manifest with
that commit's regular Git blobs. Ignored files, JavaScript shadows, symlinks,
staged differences and Git's assume-unchanged hints cannot conceal another
executed source. The reusable check strips inherited `GIT_*` variables, anchors
the Git directory and worktree explicitly, disables replacement objects and
fsmonitor, and excludes global/system configuration. It also supports linked
local worktrees.

```text
Committed plan -> physical source proof -> driver/runtime proof -> import -> dispatch
```

Text equivalent: prove the actual source, evaluation drivers, Node executable
and TypeScript compiler before importing the application; prove the prepared
model executable and any launcher again before dispatch. The start record
retains the implementation commit/tree, source inventory digest, lockfile and
compiler digests, driver hashes and runtime identities. A version string alone
does not establish executable identity.

Preregister a **new** plan after reviewing the corrections. Include the current
`qualificationDrivers` inventory exported by `ev07-shadow/implementation.cjs`,
including the shared `execution-provenance.cjs`. Record the `node`,
`nodeSha256`, `typescript`, `typescriptSha256`, `git`, `gitExecutable` and
`gitSha256` observations returned by
`runtimeIdentity(root)` alongside the existing exact CLI/launcher identities.
Git proof commands use the trusted operating-system executable, never `PATH`.
Linux uses `/usr/bin/git`; macOS resolves the actual developer-tools Git with
`/usr/bin/xcrun` in a clean environment. The supported qualification bootstrap
is Linux/macOS and does not claim Windows qualification or Setup acceptance.
Commit the completed plan before measurement. The normal-flow diagnostic's
selected subject manifest similarly requires `implementation`, `runtime` and
`drivers` from its exported `normalFlowDrivers` inventory; its direct runtime
uses an absolute `runtime.executable` and optional absolute `runtime.launcher`.
These are local evaluation artifacts, with no new public Action setting.

Run `pnpm run test:bugbot-shadow-verification` for the deterministic admission
controls. They use temporary Git repositories and blocked model/write paths.
An admission error means no application/model work was admitted. Inspect the
named source, staged inventory, driver or runtime mismatch, then restore the
selected bytes or prepare a separately reviewed and committed preregistration.
Do not regenerate expected hashes merely to suppress a failure.

Historical manifests, ledgers, scores and unsuccessful campaigns retain their
original bytes and reproduce through their frozen commits. Their old plans
cannot admit a run through the corrected drivers. Passing deterministic
admission neither passes the 174-case corpus nor admits the 42 paired reviews.
Keep `BUGBOT_VERIFICATION_MODE=disabled`, evaluated-PR write attempts at zero,
explicit cancellation, optional usage telemetry and the existing score floors.
Latency is measured after investigation; admission introduces no research
deadline, turn count or token budget.

Workflow queue tests inject a clock, random source, and scheduler/delay port. They
cover workflow-scoped active-status traversals and later-page matches, strict
lower-ID/workflow-file filtering, malformed responses, fail-closed provider errors, 429 and
rate-limited 403 headers, bounded fallback backoff/jitter, and the absolute deadline.
The workflow contract test keeps the nine queue-bearing workflow names synchronized with the
validator and verifies the `90m queue / 120m job` budget, required runners, action
inputs, missing/short timeouts, forbidden durable-mutation concurrency, and the
distinct branch concurrency and event-ownership contracts for Commit and Pull
Request jobs. The Bugbot ownership policy matrix and push-shaped integration
test additionally prove that exact-head provider discovery—not a nonexistent
`pull_request` field on the push payload—stops duplicate agent review before
the diff and conversation are loaded.

GitHub lifecycle tests cover admission before queue polling, PAT-owner normal-run
discard, valid single-action preservation, identity lookup failure, and the absence
of project composition, agent provisioning, setup, publication, and persistence on
discarded runs.

The lifecycle replay integration suite feeds normalized, serialized-shaped
`pull_request_review` payloads through the real lifecycle synchronization use
case. It verifies deterministic labels for approved reviews, requested changes,
and ambiguous multi-PR events without invoking an agent route. External check
workflows are intentionally outside the workflows shipped by Copilot.

Configuration tests cover current-schema round trips and fail-closed handling of
missing, malformed, or different-version durable values. Architecture tests also
guard the narrow context contracts used by extracted policies and lifecycle
reconciliation.

Branch synchronization tests cover durable configuration and linked-branch discovery,
pagination, parent/child comparisons, bot-owned sticky comments, explicit and natural-language
commands, authorization, dry runs, clean merges, conflict eligibility, agent postflight,
credential-free verification, unexpected workspace mutations, and remote-head races. The
all-branch observer workflow is also contract-checked to remain free of agent inputs.

Architecture tests additionally verify that production imports remain acyclic,
application code does not depend on concrete adapters, and pure model/policy
code remains free of runtime, provider, and logging dependencies. The
product-facing agent inventory test also requires exactly one guarded query for
Think, help, recommendations, progress, PR descriptions, and Bugbot, and prompt
tests require both `targetLocale` and `outputLocale`. Workflow tests prove that
a mismatched response cannot publish or mutate labels, descriptions,
recommendation state, or findings. Refresh the
local topology before an architecture review with Graphify, and use the
RepoWise index-only health/dead-code reports to distinguish current complexity
from history-based churn signals:

`RepoWise Code Health` is an optional manual workflow. PRs, pushes and merge
groups do not launch it, and it must not be a required branch check. To run an
analysis, open **Actions → RepoWise Code Health → Run workflow**, select a
reviewed repository branch, and launch it. The CLI equivalent for development is
`gh workflow run repowise.yml --ref develop`. The workflow already exists on the
default branch, as required for [manual dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

Open the run's Job Summary for the analyzed commit, phase status, elapsed time
and peak RSS. Download `repowise-code-health` (14 days) for health Markdown/JSON,
safe-only dead-code JSON, the security JSON aggregate, index/phase logs,
`revision.txt`, `scope.json`, `timings.json` and `history-resources.json`.

The pinned RepoWise 0.58.0 builds one fresh standard index and exports its stored
health/dead-code results. Index git analytics retain a 500-commit limit; security
separately covers **all reachable history**, including removed secrets and generated
bundles, using RepoWise's supported source extensions, secret patterns and
allowlists. Two spawned workers read one blob at a time each, with at most two
tasks/results in flight and results consumed in upstream order. Worker failures
propagate. The adapter avoids
computing code-smell findings discarded by history mode. This remains an advisory
signal scanner; an aggregate with no findings is not proof that no secrets exist.

Indexing has a 900-second/4 GiB virtual-memory cap. Each health export and dead-code
has a 60-second/2 GiB cap; security has a 1200-second/2 GiB coordinator cap and
a 1 GiB cap per worker, inside the
40-minute job. Limits apply per process; reported peak RSS is the largest process,
not aggregate simultaneous memory. These budgets accommodate the roughly 9 GB of
historical JavaScript without retaining all of it in memory. Two available CPU
cores are recommended for the bounded parallel history scan.

An interrupted scan, Git error, stale/failed index or invalid report marks analysis
incomplete and fails this optional run. Completed reports and diagnostics still
upload; invalid JSON is removed. Inspect the named phase log, fix the cause, then
rerun. A newer manual run for the same ref cancels the older one; cancellation or
runner loss can prevent publication. No manual run blocks automatic CI. Upgrading
the pin requires the Python compatibility fixtures, which run before every manual
analysis. They compare secret detection with upstream and verify deleted secrets,
other refs, bounded reads and failures.

Manual RepoWise runs and repository-owned CI use self-hosted Ubuntu
`codex` runners. `CI Check` skips fork PRs before runner allocation and
uses the `vypdev` group for internal reviews. It starts three independent jobs:

- **CI / Static checks:** diff, lint, types, documentation, workflow and
  specification contracts, dependency audit, and deterministic Bugbot checks.
- **CI / Build and package:** build, generated bundle and extension validation,
  and npm package validation and smoke test in the same checkout.
- **CI / Tests and coverage:** repository and extension tests, coverage budgets,
  and advisory Codecov export.

The required **CI Check** job reports all three results and succeeds only
when all three jobs succeed. Use the named job logs to locate a failure.
The jobs can overlap when matching runners are available; inspect the Actions
timeline for queue time as well as execution time. Run the three-platform
setup matrix by manual dispatch from protected `master`.

Several runner registrations may share one server. The model-free Bugbot
command fixes Node's concurrent test files at two, matching Jest's existing
two-worker allocation rather than deriving another allocation from all host
processors. It runs the same fourteen files and complete case inventory;
descendant processes are not a global host reservation. Keep native Git/Jest
deadlines and coverage gates intact. A controlled fanout result cannot explain
an earlier timeout without the corresponding host telemetry. See the
[shared-host worker control](https://github.com/vypdev/copilot/tree/develop/quality/bugbot/evidence/issue-974/controls/shared-host-worker-fanout)
for its before/after observation and limits.

```bash

repowise init . --no-workspace --no-prose --no-agents --no-editor-setup \
  --coverage-report coverage/lcov.info
repowise dead-code --safe-only --format json --no-workspace
```

## Permission journal integration budget

`setup_permission_operator_actions.test.ts` uses a real temporary directory and
journal, including file writes, `fsync`, atomic replacement, recovery and cleanup.
Its tests and hooks have a bounded 30-second Jest budget. A rejected dispatch
alone flushes six journal versions, so the generic five-second unit-test deadline
can expire during slow filesystem operations under hosted Windows coverage.

For issue #577, adding 900 ms to each real journal flush reproduced the original
five-second timeout. With the 30-second integration budget, all eight cases
completed, including the two-transaction recovery case. This demonstrates the
budget mismatch; historical CI logs do not identify the underlying host storage
or scheduling delay. Keep real persistence and every authority/cleanup assertion.
Fake timers cover Actions polling; recovery switches back to real timers before
starting its next journal transaction. Other suites retain their existing budgets.
Hosted Windows full coverage remains the platform verification gate.

## CI aggregate predicate

The source repository's `CI Check` gate requires success from all three independent
workers. `validate:workflows` binds its command to the executable contract in
`scripts/validate-workflow-contract.cjs`; it compares the complete command without

placement, fork exclusion, public check identity, parallel jobs and consumer

## Normal-flow shadow cancellation

The local normal-flow shadow runner forwards its explicit cancellation signal
into the ordinary review operation, detector and verifier. An interrupted run
records `workflow-result.status=interrupted`, retains its started/pending request
observations, and exits with status 130. It cannot report successful ordinary
completion or issue a completed verification receipt. A matched experimental
arm that is canceled does not start its inherited comparison arm.

Run `pnpm run test:bugbot-shadow-verification` for the model-free stage controls:
before detection, during detection, after preparation, during verification,
after a technical provider interruption, and uninterrupted completion. The
controlled programmatic ports exercise the actual runner and application with
pinned temporary Git sources and fail-on-write SCM ports. They are synthetic
controls, not model measurements or qualification evidence. The loader uses the
shipping compiler options so the real progress/cancellation path is exercised.

The post-provider control observes a settled `provider-turn-failed` result while
the signal is still active, then explicitly cancels the enclosing operation.
Its event-order assertions distinguish this boundary from cancellation inside
the verifier. The retained counterfactual rejects the former fixture's early
abort; the corrected control still requires interrupted status, blocked
publication, empty writes and exit 130. See the exact logs and readable ledgers
in `quality/bugbot/evidence/issue-972/post-provider-order-validation.json`.

Use a new output destination for every actual attempt and retain the interrupted
ledger. Old ledgers remain historical observations; replay needs the new driver
pin and its applicable source/runtime admission. This adds no Action setting,
elapsed-time cutoff, token budget or turn limit. Usage remains optional telemetry.

After the #970/#972 integration, the cancellation controls enter through the
external bootstrap too. Their disposable source snapshot and plan are committed
before execution; a pinned owned wrapper supplies controlled providers while
executing the actual runner. Its optional internal result observer exposes the
post-provider boundary to the control without adding a CLI setting. The relative-lab case uses the
same fixture. This does not add a production test mode or bypass source/runtime
admission. Seven actual-operation cases and one matched-arm case distinguish
interruption, completion and provider failure; the bootstrap exits 130, 0 and 1
respectively. No model campaign or evaluated-PR write is performed by these
controls.

Some bound-corpus evaluator fixtures authenticate the real repository HEAD.
After merging package or application changes locally, commit the candidate
through the required repository hook before expecting those root-bound controls
