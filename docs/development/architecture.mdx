# Architecture

Guarded PR approval uses a separate trusted observer entrypoint, a pure domain decision (`pull_request_approval`), a read-before-write application use case, and a GitHub adapter. The adapter owns exact producer/rule/review queries and the `commit_id`-pinned native review. Its PR assessment card and supplemental Check are derived UI; GitHub's native review is authoritative. The observer has no PR-head checkout or agent invocation. See the [runtime SDD](../../specs/guarded-pull-request-approval.md) and [setup/doctor SDD](../../specs/guarded-pull-request-approval-setup-and-doctor.md).

The repository separates semantic application ports from provider-specific adapters.

GitHub conversation output crosses a closed publication boundary. Capabilities
produce typed `none`, `reply`, `status`, `transition`, or `inline-finding`
intents; the publication layer maps only reviewed semantic payloads and can
never render `Result.steps`, reminders, errors, or debug logs. Status
and reply workflows validate exact bot ownership, stable correlation or topic
identity, and semantic digests before creating or updating a comment. The
checked-in publication mutation inventory fails CI if a new application use
case writes a comment or review without an explicit architectural decision.
The same bounded publication port exposes duplicate removal only to semantic
reconcilers. They select later comments only after paginated discovery verifies
the exact identity and bot owner. The GitHub repository treats an already absent
comment as idempotently removed, maps a deletion-forbidden response to a
localized compact-pointer fallback plus bounded Job Summary evidence, and
propagates every other provider failure.
Action notifications use a separate immutable transition marker and the same
publication boundary. A closed trusted action, semantic identity, and source
version derive the fingerprint; visible prose never participates. The shared
coordinator creates at most one notification for that fingerprint, re-lists to
heal concurrent creation, and reports `created` or `reused` with content-free
identity evidence in the repository-locale Job Summary.
Initial issue help and addressed Think requests follow that rule: each agent
step returns an immutable `direct-answer` projection and receives no GitHub
mutation port. The shared reply reconciler sanitizes and publishes the answer
once for the source-comment or event correlation. Optional translation evidence
stays typed until this publication boundary; the renderer uses the same resolved
catalog as the answer and creates the inert, collapsed original-request block.
Issue routing emits a welcome only when an eligible normal issue
produces neither a publishable plan nor a direct answer; release and hotfix
issues leave conversation ownership to their durable dashboard. Before the
optional fallback is emitted, a read-only comment port checks exact-target,
bot-owned plan, direct-answer, and current welcome reply markers. An unavailable history read fails
closed by omitting the welcome. An unchanged stored recommendation is projected
again so the status reconciler can preserve or recreate its current plan card.

Commit-derived progress crosses an additional source-freshness boundary. A
provider-neutral application port reads the authoritative branch `HEAD`; the
progress workflow snapshots it before agent analysis and checks it again
immediately before changing issue or PR labels. The status-card reconciler
rechecks that same expected object ID before every create or update. A push
event or CLI workspace whose source is already old is discarded before agent work. A branch that
advances during the run produces a successful, skipped `stale-source` outcome,
leaves native state and conversation state untouched, and is explained only in
the Job Summary. Git object-ID validation accepts canonical SHA-1 and SHA-256
forms; Octokit and credentials remain confined to the data/composition layers.

Repository-facing language follows the same boundary. Entrypoints build one
canonical, frozen locale profile: `repository-locale` defaults to `en-US`, and
empty issue or pull-request overrides inherit it. Presentation policies request
stable message IDs from a versioned catalog instead of branching on language.
Reviewed English and Spanish catalogs resolve by exact locale or compatible base
language; any other valid BCP-47 locale uses one schema-constrained, per-run
cached language-agent request. A missing or invalid dynamic slice falls back
atomically to English and records only locale, source, descriptor count, and a
stable reason in the Job Summary.

`copilot doctor` applies that boundary before constructing any visible check.
The doctor use case resolves one complete catalog from the repository locale,
passes the same immutable view into merge-queue readiness, returns it with the
semantic report, and the CLI presenter uses that exact view. Setup passes an
explicit English catalog to embedded readiness because setup is still creating
the profile. Stable check IDs, evidence keys, verdicts, refs, and credential
names remain machine facts; raw provider and credential-health prose is never
rendered. Pull-request-mode selection returns reason codes rather than localized
strings, so neither application use cases nor composition roots branch on `en`
or `es`.

Product-facing agent calls cross a second closed locale boundary. The fixed
inventory is Think, initial help, recommendations, progress, pull-request
descriptions, and Bugbot review. Each call uses the common structured-query
options builder, receives `targetLocale`, requires `outputLocale`, and validates
an exact canonical match before any product mutation. An architecture test
compares the call sites with that inventory, while strict-schema tests require
the locale field in every response contract.

Repository-aware local actions reuse that catalog boundary for terminal labels.
The Think CLI renders its semantic payload under a localized `Answer` label and
does not need a synthetic GitHub issue or a comment mutation; `--issue` adds
optional issue-description context only. Machine keys and command names remain
English.

Language adaptation is separate from catalog resolution. Comment admission,
command parsing, and authorization establish trusted command identity before at
most one prose adaptation. The language port has no comment-update capability:
human source comments remain unchanged, while a translated bot response may add
one collapsed, escaped context block. Commands, flags, refs, URLs, markers,
Check names, log codes, and machine-readable fields never localize. Architecture
tests reject feature-local `en`/`es` branches in common presentation and any
source-comment mutation dependency in the adaptation path.

Technical operands are enforced, not prompt-trusted. The adaptation policy
replaces code spans, slash and bare-file paths, recognizable refs/versions,
issue or PR references, URLs, quoted literals, option flags, and commit IDs with
deterministic placeholders; commands without adaptable prose protect every
argument. A response is rejected unless each placeholder is returned exactly
once and in order and no new technical operand appears; only then does the
application restore the original values. Explicit-request errors
are projected to one safe `application-error` reply by the shared publisher,
while background errors stay in operator evidence. Local human output follows
the same outcome/evidence split: it renders localized aggregate state and
semantic errors, never raw `Result.steps` or reminder prose.

- Application: use cases, pure policies (agent configuration, reviewer/assignee
  selection, and result publication), and semantic ports.
- Data/repository: external adapters for agent execution, authentication, provisioning, GitHub, and Git.
- Infrastructure: runtime wiring, GitHub/process implementations, and concrete logging.
- Domain model/policies: provider-neutral rules such as action types, label-to-branch resolution, and version arithmetic.
- Composition roots: bind capabilities without universal facades. Findings,
  language translation, and fixer execution use separate application ports;
  provider-specific CLI adapters remain behind those ports.

The application layer MUST NOT import GitHub SDKs, concrete CLIs, process libraries, or provider-specific protocols. Provider adapters MUST NOT define business policy. Configuration validation belongs at the boundary before execution. Prompt construction, untrusted-content handling, and GitHub publication sanitization are separate policies so no agent capability can bypass the security boundary.

The scheduled inactivity cleanup follows the same split: the pure
`issue_inactivity` policy decides eligibility, application ports expose issue
snapshots and closure commands, the repository maps GitHub's `updated_at` and
labels, and the composition root wires the adapters. The use case revalidates
each issue immediately before mutation so the periodic scan remains best-effort
and fail-closed for changed candidates.

Setup follows the same boundary. A pure immutable questionnaire policy owns
question order, conditional states, validation, and fresh configuration
snapshots. A controller drives that policy through a raw terminal driver whose
only responsibilities are interactivity, text input, masked secret input, and
idempotent close. Separate render, plan presentation, and confirmation ports own
user-facing output; `--non-interactive` never constructs the terminal.

Credential collection, workflow comparison, approval, and doctor decisions live
in application use cases and semantic ports. GitHub Secret encryption, workflow
dispatch, provider metadata requests, and setup-only temporary health-workflow
bootstrap are infrastructure adapters. Remote Variables and Secrets expose
separate query and command adapters instead of a broad resource facade. Doctor
receives query ports only, schedules independent probes with a fixed maximum of
four, and restores declared order in its stable `pass|warn|fail|skipped` report.
Secret values never enter questionnaire state, setup override files, Variables,
plans, logs, reports, or generated workflow templates.

The setup policy is intentionally split by responsibility:

- `setup_configuration_defaults.ts` owns defaults and override merging.
- `setup_configuration_validation.ts` owns structural and semantic validation.
- `setup_configuration_storage_policy.ts` owns repository/organization scope
  resolution and effective-resource preservation.
- `setup_configuration_clone_policy.ts` owns reference-isolated configuration copies.
- `setup_questionnaire_policy.ts` owns setup states, questions, transitions, and answers.
- `setup_configuration_plan.ts` owns the reviewable provisioning plan.
- `setup_doctor_report_policy.ts` owns stable check validation and aggregation.
- `setup_resource_provisioning.ts` owns grouping and port calls for Variables
  and Secrets.

There are no installed users or persisted setup state to migrate, so this is a
greenfield contract: no legacy prompt facade, compatibility overload, dual
reader/writer, deprecated result, or transitional state alias is retained.

The runtime `Execution` aggregate is projected at the setup route into a fresh
`InitialSetupContext`; the setup workflow consumes only label, issue-type,
selected setup configuration, provisioning credential, remote-configuration,
and workflow-update facts. Repository coordinates and the GitHub authentication
token are captured by setup composition ports and never enter that context.
Action input keys are defined in `src/application/contracts/input_keys.ts`,
provider-independent action types remain in `src/data/model/action_types.ts`,
and unrelated constants have explicit owners instead of a global constants
module.

Runtime aggregates are kept at the composition boundary. Extracted policies and
reconciliation use cases receive narrow context contracts containing only the
facts they need; they do not depend on the complete `Execution` aggregate.
This keeps pure decisions independently testable and makes new event sources
less likely to couple unrelated capabilities. Application failures use the
closed `ApplicationError` contract: one of 20 semantic codes, a derived
category and retry decision, impact, recommended action, retained-state
summary, and request correlation UUID. A raw cause is ECMAScript-private,
never serialized or logged, and cannot enter `Result.errors`. The generic Job
Summary, repository-aware CLI, deployment completion, and ordinary Action
completion project one shared code-specific error catalog. Stable codes and
references remain machine-readable; labels, impact, action, retained state, and
retry guidance follow `repository-locale`, and producer error prose is not
replayed. The pre-repository CLI boundary uses English; the early GitHub Action
boundary can use bundled English or Spanish from its validated input and falls
back atomically to English when dynamic localization is not yet available.
Partial operations select a closed recovery descriptor with only validated
branch-name or issue-number variables. This preserves exact rollback and
retained-state guidance in every locale without permitting feature code to
override presentation with arbitrary strings.

The main-run setup path follows that rule end to end. Its action boundary copies
and freezes a `SetupExecutionContext`, setup returns a discriminated result, and
only the boundary applies resolved identity, labels, versions, and configuration
fields. The composition root captures repository coordinates and credentials in
the concrete adapters, so setup contexts and their nested version-description
queries contain neither tokens nor provider clients. There is no aggregate
overload or compatibility adapter for the removed setup signatures.

An AST architecture ratchet resolves the real `Execution` class symbol through
renamed imports, re-exports, type aliases, and utility types. Its checked-in
allowlist may shrink but cannot grow or move to new files; every entry records a
closed boundary role and rationale, and a synthetic negative fixture proves
that indirect aliases remain detectable. The final inventory keeps the
aggregate only at construction, route-contract, coordinator, and entrypoint
boundaries; leaf use cases receive freshly copied, readonly capability contexts.

The P2-B Bugbot boundary first copies repository, target, trigger, ignore, and
organization-rule facts into a frozen `BugbotContextSelectionContext`. Only the
detection route extends it with locale, selected-agent, severity, limits, and
bounded review configuration as `BugbotReviewOperationContext`. Both contracts
exclude the SCM token, mutable `Ai` model, event objects, and provider clients;
selection-only workflows cannot request analysis configuration. P2-C binds SCM
and Git authority in infrastructure ports, so Bugbot leaves receive neither
credentials nor unbound provider calls.

The P2-D comment boundary applies the same rule to reusable issue and pull
request behavior. The two comment route coordinators project a frozen
`CommentAutomationContext`; permissions, translation, Think, title, result
publication, configuration persistence, and project linking then receive still
narrower readonly records. `shared_capability_port_binding.ts` captures
repository identity and credentials once and exposes operation-only ports for
membership, description, notification, comment update, title, and project
content. Publication and persistence snapshot mutable inputs before I/O, and
publication failures return a semantic result instead of mutating the context.
The exact `Execution` inventory is 75 after this cut, down from 104 after P2-C.

P2-E projects separate frozen issue and pull-request step requests at the two
route coordinators. `lifecycle_capability_port_binding.ts` captures repository
identity and credentials once, while leaf methods accept only operation facts.
Branch preparation returns an immutable configuration patch that the issue
route applies after the step completes; nested helpers cannot mutate route-owned
state during provider I/O. PR linkage reads and updates only the exact bound PR,
uses a temporary owned recovery marker, restores the authoritative original body
and base on success or failure, and names any retained partial state. Automatic
and authorized-command PR descriptions now share one discriminated request.
This clean cut removes all `Execution` imports from the issue/PR step directories
and lowers the exact repository inventory from 75 to 47.

P2-F extends the boundary across push and single-action capabilities. Routes
project separate frozen records for release/tag publication, setup, progress,
recommendations, inactivity, issue comments, branch observation and sync,
commit notification and sizing, activity markers, and deployment. The
`push_single_action_capability_port_binding.ts` composition boundary captures
repository coordinates and credentials once; application methods accept only
semantic operation facts and cannot retarget provider calls. Recommendation and
activity changes return explicit outcomes for the owning route. Deployment owns
an isolated invocation-state copy whose durable revisions cross only its fenced
state port. Obsolete setup and commit-prefix mutation paths were deleted, and
the exact production `Execution` consumer inventory fell from 47 to 13.

P2-G audits and locks that final 13-consumer boundary. Lifecycle synchronization,
the last aggregate-shaped alias below it, now receives a frozen discriminated
snapshot containing one issue/PR target, configured lifecycle labels, event
action, and bounded review/check evidence. Repository identity and credentials
are captured once by bound label and pull-request-head ports. The use case
re-reads authoritative labels, ignores stale head evidence, performs at most one
conditional write, and returns a readonly label patch. Only the entrypoint
applies that patch to its aggregate after provider success; a failure retains
both provider and local labels and exposes only a semantic error.

```text
Execution entrypoint -> frozen lifecycle snapshot -> pure state policies
                     -> bound label/head ports -> Result + label patch
                     -> entrypoint-owned aggregate update
```

The raw-error architecture guard also follows caught values through local
declarations and assignments. A derived provider message cannot reach logging;
`toApplicationError` is the explicit semantic boundary.

Configuration embedded in issue or pull-request content is versioned. Readers
accept only the current schema and fail closed on missing, malformed, or
different-version payloads. Writers emit only current, known fields, so stale
state cannot silently change runtime behavior.

## Workflow queue boundary

The workflow-local queue is an application use case backed by semantic ports. Each
workflow has its own queue; `workflow_queue_policy.ts` owns the 90-minute queue
budget, adaptive polling schedule, jitter bounds, and retry budgets. The use case
receives a clock and random-value port so deadline and delay behavior remain
deterministic in tests; concrete system clock/random and timer adapters are wired in
`workflow_queue_composition_root.ts`.

`ActivePreviousWorkflowRunsRepository` uses GitHub's workflow-scoped runs endpoint
for the current workflow file. Each poll queries the five active statuses directly,
paginates those live subsets, and filters lower run IDs locally; completed history is
never traversed.
Provider errors remain at the repository boundary: rate-limited 429/403 responses,
transient HTTP/network failures, server wait headers, and malformed pages are
classified there and never become a synthetic zero count. Retry logging exposes only
sanitized reason, attempt, delay, and reset metadata. Queue-bearing jobs use a
120-minute workflow timeout, leaving 30 minutes of headroom beyond the queue budget.

The workflow identifier comes from `GITHUB_WORKFLOW_REF`. A missing identifier or
unavailable workflow-scoped endpoint fails closed instead of falling back to a
repository-wide traversal. Exact counting still requires exhaustive pagination of
each active-status subset because an older run can appear on a later page.
`per_page: 100` keeps request count proportional to the live queue rather than the
workflow's completed history or the entire repository.

GitHub Action runs also perform an admission preflight before constructing the full
execution. The preflight uses the semantic authenticated-user port and a pure
application policy to identify normal runs triggered by the PAT owner. Those runs
complete without entering the queue; valid explicit single actions remain admitted.
This decision belongs to the GitHub lifecycle and is deliberately not added to the
shared `mainRun` path used by the local action.

## Bugbot reconciliation boundary

Bugbot final reconciliation is a single pipeline split into four narrow
responsibilities:

```text
reconcileBugbotReviewState
  -> loadBugbotReconciliationSnapshot
  -> projectBugbotProviderEvidence
  -> buildBugbotReconciliationPlan
  -> synchronizeBugbotReviewPresentation
```

The workflow projects `Execution` into the provider-neutral
`BugbotReconciliationTarget` and credential contracts before entering this
pipeline. The reconciler does not depend on the runtime aggregate and does not
perform provider reads or presentation writes directly. Canonical finding and
durable destination contracts live under `domain/bugbot`; application policies
never import types from a concrete use-case directory.

Snapshot acquisition verifies the pull-request head before reading any durable
surface, reads independent surfaces concurrently, and verifies the head again
afterward. A revision change discards the whole snapshot. Each surface records
`verified`, `failed`, or `not-applicable`, so an empty successful read cannot be
confused with a failed read. Provider projection keeps linked-issue and PR
evidence separate and folds them conservatively: a clean destination cannot
hide a non-clean or unverifiable destination.

The pure reconciliation plan owns missing-publication and missing-durable-
evidence decisions. The presentation use case owns only bounded review/status
writes: at most 20 review summaries are selected per run and writes use bounded
concurrency. Existing integration scenarios exercise the full pipeline, while
snapshot, projection, plan, ownership, and presentation boundaries have focused
unit tests.

## Branch synchronization boundary

Branch synchronization has two independent entry points behind the same semantic
ports. The all-branch push workflow invokes `check_branch_sync_action`, which can
reach only dependency discovery, branch comparison, and the generic semantic
issue-publication adapter.
It has no agent role or agent environment. The comment command resolves one target,
authorizes the actor, and delegates Git merge ownership to a specialized workspace
adapter. The fixer capability becomes reachable only after Git reports eligible
conflicts.

The application use case owns orchestration and publishable results; pure policies
own command parsing, dependency selection, stable publication identity, source-head
fingerprints, and localized safe rendering; repositories
translate GitHub GraphQL/REST responses; and the Git adapter owns transient merge
state. Verification runs without credentials. The adapter rejects changes to Git
heads, merge metadata, the non-conflicted index, or the prepared path set, then
re-fetches both remote heads immediately before the trusted commit/push boundary.

The observer creates only the initial stale status card, skips an identical
render, updates changed stale/aligned projections in place, and delegates only an
aligned-to-stale human-action transition to the shared immutable notification
coordinator. That coordinator reuses the generic issue-comment publication port
for exact bot ownership, concurrent-create reconciliation, duplicate removal or
compaction, and content-free Job Summary evidence. Branch-sync defines no parallel
comment authority.

## Deployment orchestration boundary

Release and hotfix deployment is a durable state machine rather than one
runner-owned script:

```text
preparing -> promotion_pr_pending -> promoted -> publishing
  -> published -> reconciliation_pending -> completed

any non-terminal phase -> blocked -> previous safe phase after correction
```

Every durable snapshot has one exact failure invariant: `lastFailure` is `null`
outside `blocked`, and a blocked snapshot contains a closed failure object with
the exact previous non-blocked phase. Unknown state fields and blocked snapshots
without that evidence fail before presentation or continuation.

`deployment_configuration.ts`, `deployment_operation.ts`, and the pure planning,
lifecycle, continuation-guard, and presentation policies own bounded values and
decisions. They have no GitHub client, workflow payload, process, timer, or
filesystem dependency. `DeploymentOrchestrationUseCase` receives the narrow
`DeploymentOrchestrationContext`; the `Execution` aggregate is structurally
projected by the single-action boundary.

Application ports keep managed-PR mutation, target-rule inspection, Git
refs/ancestry, workflow continuation, durable issue state, publication receipts,
and presentation as separate capabilities. `GithubManagedPullRequestRepository`
maps PR and merge-queue membership, `GithubTargetMergeCapabilitiesInspector`
combines classic protection with effective rulesets and bounded workflow YAML,
and `GithubDeploymentGitRepository` owns refs and ancestry. Pure readiness policy
owns `ready`, `unknown`, and `unsupported` decisions plus exact attestation
matching. Runtime, setup, and doctor share that policy; entrypoints never supply
an optimistic static capability boolean. `DeploymentStateRepository` owns the
strict schema-v3 hidden issue block. The composition root is the only place that
binds these repositories and the Octokit adapter.

Durable transitions compare the operation ID and expected stored phase before
each write. PR and publication side effects use deterministic markers, exact
branch/SHA facts, and postcondition verification. A continuation event or
workflow dispatch is only a wake-up signal: it must present the same operation
ID, then authoritative issue and GitHub state are reloaded. The privileged PR
completion workflow checks out the trusted base and never executes the PR head.

Presentation is a separate mutation-free boundary. A typed English/Spanish
catalog renders the durable issue dashboard, promotion and reconciliation PRs,
and deployment Job Summary. Provider mutations accept those rendered values but
cannot choose phase transitions. Architecture tests enforce the narrow context,
provider-neutral port vocabulary, mutation-free renderer, global dependency
direction, and acyclic production imports.

The generic GitHub Actions Job Summary follows the same boundary. One complete
typed catalog is resolved for `repository-locale`; bundled English and Spanish,
arbitrary dynamic locales, and atomic English fallback share the repository
localization resolver. The summary renders localization evidence once, keeps
machine event/state/error values stable, and projects routine results as compact
localized aggregate counts. Only failed results receive an expanded diagnostic
section. Internal result names, `Result.steps`, and arbitrary error messages remain
in logs or machine evidence; they are never replayed into the summary. Failures
show code-specific localized impact, action, and retained-state guidance beside
the stable code, retry decision, and correlation reference.
