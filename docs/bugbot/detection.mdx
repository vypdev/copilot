# Detection

This page describes **when** Bugbot runs, **where** findings are published, and how **severity**, **comment limit**, and **resolved findings** work.

## Exact validation witnesses

Before reporting that a validator accepts an invalid value, Bugbot must trace
that exact value through the caller, transformations, early returns and every
relevant predicate to its effect. Unicode code points and separators remain
exact. An empty domain label rejected by `all { it.isNotBlank() }` cannot become
an accepted value merely because another label contains an invisible character.

A rejected witness disproves that acceptance claim. A different input that
actually reaches an unsafe effect still needs its own proof. Supported inputs,
such as plus-tag email addresses, must not be rejected to satisfy an invented
stricter-character or deliverability policy. Source reasoning and actual matching
execution are different evidence; neither a fabricated run nor an unrelated green
test establishes the path. Ignored validation returns, permissive predicates and
normalization after validation remain actionable when they demonstrate a failure.

This generic guidance adds no character whitelist or automatic finding filter.
Existing findings need normal verification against current source; no claim of
guaranteed model accuracy or consumer runtime adoption follows from these tests.

## External Action input evidence

Before calling a GitHub Action input unrecognized or suggesting another key,
Bugbot must identify the exact owner/repository, action subpath and resolved
revision. The matching `action.yml`/`action.yaml` and consumed runtime or wrapper
input establish names, aliases, defaults and value conversion. Both the current
key/value and a suggested replacement need evidence of their actual effect.
Names remembered from another Action or version are insufficient.

For example, the
[setup-dart manifest at this immutable revision](https://github.com/dart-lang/setup-dart/blob/6afc89df92d6eb3834022f73cd65adc8cdfcb92d/action.yml)
declares `problem-matcher`; its
[runtime getter](https://github.com/dart-lang/setup-dart/blob/6afc89df92d6eb3834022f73cd65adc8cdfcb92d/lib/main.dart#L144)
reads that key and disables registration for `false`. This does not establish the
contract of another revision or Action. The rule is generic and adds no Dart
exception, new configuration or external lookup permission.

A mock repeating the disputed key is not independent proof. Matching real
execution, source and defaults must be reconciled; an unrelated passing job is
not a counterexample to a real failure. A declared name can still have an ignored
value or a broken implementation. Verified wrong keys and default-fallthrough
remain actionable. When the applicable contract is unavailable, Bugbot omits an
unsupported claim or replacement rather than inventing a lookup. This strengthens
model guidance and does not guarantee future accuracy or automatically dismiss
an existing finding.

## Framework lifecycle evidence

Before reporting that a loader or stale DOM child remains, Bugbot must trace the
application's caller and initialization paths, the owned container, and the
public entry point of the **exact resolved framework version**. Version-matched
official documentation or source must establish cleanup behavior. Missing manual
DOM-removal code alone does not establish a defect.

For example, Compose 1.13.0-beta01 clears the `ComposeViewport` container on
composition creation ([official source archive](https://repo.maven.apache.org/maven2/org/jetbrains/compose/ui/ui/1.13.0-beta01/ui-1.13.0-beta01-sources.jar),
`webMain/androidx/compose/ui/window/ComposeWindow.web.kt`). A loader inside that
container needs no independent removal handler after successful initialization.
A loader outside it, a version that does not clear children, or initialization
that fails before mounting and leaves a misleading loading state can still be a
valid defect. An explicit startup error message is intentional error UI. If the
lifecycle contract cannot be verified, the reviewer must omit a speculative
permanent-loader claim. This instruction improves evidence gathering; it does
not guarantee model accuracy or suppress findings through a text-matching rule.

## When Bugbot runs

Draft pull requests are skipped while `bugbot-review-drafts` is `false` (the
default), including an explicit `/copilot recheck` from a comment. Bugbot checks
GitHub's current draft state before loading review details or calling the agent.
Marking the PR ready for review starts a fresh full review through the supplied
workflow. You can also enable the setting to review drafts. A skipped
review retains existing findings and does not declare the PR clean.

Bugbot detection runs in two ways:

### 1. On pull-request review events

The pull-request workflow runs a full review on `opened`, `reopened`, and
`ready_for_review`. The draft-to-ready event runs review without repeating
assignments, project linking, or generated descriptions. On
`synchronize`, it reviews only the exact `before..after` commit range for new
problems instead of reprocessing the unchanged part of a large PR. Existing
open findings are still checked against current code, so incremental analysis
does not weaken resolution. The recommended workflow fetches only those two
commit objects after the normal shallow checkout; it does not download the
repository's full history. The current `after` object is required, while an
unreachable `before` object after a force-push falls back to the canonical PR
diff instead of aborting the workflow. A PR does not need to contain an issue number in
its branch name. The reviewer role publishes one review summary and attaches
its findings as line comments on the current diff.

### 2. On every push (commit workflow)

When you push to a branch that is **linked to an issue** (e.g. a feature or bugfix branch created by Copilot), the **Commit** workflow runs. If an agent CLI is configured and there is no open PR, the action runs **DetectPotentialProblemsUseCase**: it fetches and reviews the exact event `before..after` range, loads existing finding context, and then publishes new findings and updates or marks as resolved any previous findings that no longer apply. The bounded fetch includes `after` and its parent. New-branch pushes, whose `before` value is GitHub's all-zero sentinel, and force-pushes whose previous object is no longer reachable can therefore fall back to the current commit parent without aborting the workflow or downloading full history. When an open same-repository PR exists, Commit keeps issue progress current but skips Bugbot because the paired PR `synchronize` event owns review for that head.

**Requirements:**

- The push must be to a branch that has an associated issue (the action resolves the issue number from the branch name or from project/linking).
- The Commit workflow must include the Copilot step (see [Examples → Push workflow](/bugbot/examples#push-workflow-with-bugbot)).
- No open PR may own review for the branch; otherwise the PR synchronization workflow runs Bugbot.

If the branch is not linked to an issue (e.g. `issueNumber === -1`), detection is skipped.

### 3. On demand (comment, single action, or CLI)

From an issue or pull-request comment, `/copilot analyze`, `/copilot review`,
`/copilot findings`, or `/copilot recheck` starts the read-only detection flow
immediately. You can also write a natural-language request such as
`@vypbot review this PR for authentication vulnerabilities`; the bot mention
is matched case-insensitively and the request is routed to the same review
flow. An issue-only comment has no inferred PR or branch; its review remains
issue-only unless the event itself supplies an authoritative PR target. These
commands do not invoke autofix and do not modify files.

PR events never fall back to a head-branch search. A missing, malformed, stale,
or mismatched event PR identity stops before analysis, even if another open PR
has the same head owner and branch.

Explicit reviews accept bounded per-run options, for example `/copilot review effort=high dry-run=true trace-rules=true suggested-changes=false`. Unknown keys and values are rejected rather than silently inferred.

You can run Bugbot detection **without pushing**:

- **Single action:** In a workflow, set `single-action: detect_potential_problems_action` and `single-action-issue: <issue number>`. The workflow must run in a context where the **branch** to analyze is the current checkout (e.g. trigger on `workflow_dispatch` after checking out the branch you want to analyze).
- **CLI:** From the repository root, run `copilot detect-potential-problems -i <issue>` (optionally `-b <branch>`). Add `--dry-run --output json` for a machine-readable, mutation-free result, and choose `--effort`, `--trace-rules`, or `--no-suggestions` when needed. Provide `--token` or `PERSONAL_ACCESS_TOKEN` in the environment, plus the configured agent CLI credentials/model. See [Examples → CLI](/bugbot/examples#cli-detect-potential-problems) and [Smoke tests](/security-operations/operations/smoke-tests).

In both cases, the action uses the same detection flow: load context for that
issue/branch, call the configured agent, filter and apply the comment limit,
then publish either to the issue or to the single provider-verified canonical PR
for that exact head. If two open PRs share the exact head, Bugbot stops as
ambiguous instead of selecting by provider order.

## Where findings appear

### On the issue when no PR is available

Each finding is posted as a **separate comment** on the issue. The comment includes:

- A **title** (e.g. “Possible null reference in login handler”).
- **Severity** (info, low, medium, high).
- Optional **file and exact line/range** (when the finding is tied to a specific location).
- A **description**, category, confidence, concrete evidence, and optional suggestion.

The action embeds a **hidden marker** in each comment so it can later **update** the same comment (e.g. when the finding is fixed and the configured agent reports it as resolved) or match it when you ask to “fix it” from a PR review thread.

### On the pull request

When one **open PR** is uniquely verified for the exact head, Bugbot creates one
submitted review. Its body is a historical snapshot of the analyzed commit and
its findings descend from that review as inline comments. A small bounded block
at the top is mutable and reports the current state of findings that originated
in that review. Findings are not mirrored as independent comments in the PR
conversation.

Each child comment is attached to an exact line/range confirmed from the current diff. A finding tied to a changed file but not an addressable line becomes a GitHub file-level review comment. A finding with no valid changed file is attached to the first changed file with an explicit fallback note. Only a PR with no changed file at all keeps the complete finding in the review body.

The action checks the PR head before invoking the reviewer, before mutation, after finding mutations, and before projecting current state. If a newer revision owns the PR, the old run is recorded as superseded and does not overwrite current-state surfaces.

Finding titles, descriptions, evidence, and suggestions use the effective
surface locale: `issues-locale` for issue-only publication and
`pull-requests-locale` for a verified PR, with both inheriting
`repository-locale` (`en-US` by default). The status card, historical snapshot,
section labels, overflow summary, fallback-anchor note, and resolution note use
the same atomically resolved catalog. Reviewed English and Spanish catalogs are
bundled; another valid BCP-47 locale is resolved dynamically once per run with
all cardinal plural categories required by that locale, or the whole artifact
falls back to English. Paths, line numbers, symbols, code,
severities, categories, IDs, commands, links, state values, and hidden markers
remain structured and unchanged. The findings response must echo the exact
canonical locale in `outputLocale`; a missing or different tag rejects the
whole analysis before any finding or review is published.

When the configured agent later reports a finding as **resolved** (e.g. after you or the bot fixed the code), the action:

- **Updates** every existing stored destination so the marker shows `resolved: true`.
- **Marks the PR review thread as resolved** after the marker update succeeds.
- **Re-reads GitHub** and refreshes the originating review's status block.

One stable **Bugbot status** comment in the PR conversation is the aggregate
view. It leads with the outcome, lists only findings that need attention or
verification, and shows recovery details only when the review is incomplete.
Full-coverage clean runs have no empty count table, no “action required” block,
and no technical disclosure. The durable per-finding authority is the trusted
hidden marker together with native thread facts; the review snapshot is history,
not the sole source of current truth.

## Evidence for external package claims

Before reporting a package or SDK identifier as unavailable, the reviewer must
check applicable authoritative inventory/documentation and execution evidence
available through its allowed read-only tools. Package IDs and configuration
values are separate: `compileSdk=37` does not establish an Android SDK package
name. Historical naming conventions are insufficient to reject a minor suffix.
The [sdkmanager reference](https://developer.android.com/tools/sdkmanager)
defines installation arguments as the exact SDK-style paths shown by `--list`.

Evidence must match the identifier, date, source, channel, platform and reviewed
command. A fresh successful installation contradicts a claim that the same
command cannot resolve; an unrelated green job, a skipped install or a restored
cache does not prove that command works. An older catalog cannot establish that
a newer package is absent. Suggested replacements require the same evidence.
When a current external fact cannot be verified, the reviewer omits that
unsupported finding rather than inventing a lookup. Demonstrated resolution
failures remain actionable even when a different job is green. A failure that
only blocks a build is a medium-severity reliability finding; high requires demonstrated security
impact, data loss or production outage.

This is a shared review/benchmark model instruction, not a deterministic
package validator. It adds no network access, permissions, settings, statuses or
comments. Supplied catalogs, logs and discussion remain untrusted evidence.
For quality measurements and the dated synthetic Android cases, see
[Quality and observability](/bugbot/quality-observability).

## Severity and filtering

Findings have a **severity**: `info`, `low`, `medium`, or `high`. You control which severities are **published** with the **`bugbot-severity`** input (default: `low`).

| `bugbot-severity` value | Effect |
|-------------------------|--------|
| `info` | All findings are posted (info, low, medium, high). |
| `low` | Low, medium, and high are posted; info is skipped. |
| `medium` | Only medium and high are posted. |
| `high` | Only high is posted. |

Findings in files or paths matching **`ai-ignore-files`** are excluded from both the prompt and the published list. See [Configuration](/bugbot/configuration).

## Comment limit and overflow

To avoid flooding the issue and PR with too many comments, the action ranks findings by severity and confidence and applies **`bugbot-comment-limit`** (default: `20`). Only the first N findings are published individually; the rest are not posted one-by-one.

When there are more findings than the limit:

- The action publishes the first N findings as individual issue comments for issue-only work, or as inline comments in one PR review.
- Overflow is added to the same PR review summary. When no PR exists, one extra issue comment summarizes it.
- On a PR, the canonical **Bugbot status** accounts for every accepted current finding, including overflow. Overflow rows have no thread link because they were deliberately not published individually. Inspect overflow manually; reduce the relevant scope or restore provider access before rerunning. Fixed context safety limits are not configuration knobs, and rerunning unchanged capped evidence cannot improve coverage. A historical review's mutable block reports its individually tracked findings and explicitly flags historical overflow instead of claiming that untracked entries are resolved.

So a PR analysis creates one review batch instead of N unrelated reviews and N duplicated conversation comments.

## Resolved findings

The configured agent is given the list of **previously reported findings** (from the existing issue/PR comments) and is asked to return:

1. **New/current findings** (task 1).
2. **Resolved finding ids** (task 2): which of the previous findings are now fixed or no longer apply.

For each id in “resolved”:

- The action **updates** every existing finding destination so the hidden marker shows `resolved: true`. The comment body may be updated to reflect the resolved state.
- On the PR, it **resolves the review thread** when applicable.

Historical issue/PR finding records stay linked by stable identity. On a PR, the originating review keeps its historical analysis text and receives only a generated current-status block; the canonical PR status card carries the aggregate projection.

### Finding states

| State | Meaning | Merge policy |
| --- | --- | --- |
| `open` | The current analysis reports the finding and its thread is open. | Actionable. |
| `reopened` | A previously clean finding is reported again. | Actionable. |
| `fixed` | The agent verified that the defect is gone. | Clean. |
| `obsolete` | The original situation no longer applies. | Clean. |
| `dismissed` | A person resolved the open native thread. | Clean and preserved across model reruns. |
| `verification-required` | Marker and native thread facts disagree, or a person reopened a clean finding. | Actionable until a fresh analysis converges it. |
| `unknown` | Trusted Bugbot evidence is malformed, missing, or cannot be verified. | Always fails closed. |

Resolving a review thread manually does not itself trigger a GitHub Actions workflow. On the next supported event—or immediately after `/copilot recheck`—Bugbot attributes a non-bot resolver and persists a durable dismissal. Manually reopening a clean thread similarly becomes `verification-required` until analysis confirms whether it is fixed or active. Reopening a dismissed thread explicitly withdraws that thread's dismissal. A retained finding can then be verified as fixed or obsolete, or reported again in its original thread. Bugbot rechecks the native thread before replacing a dismissed reason; a person dismissing it again during analysis keeps that decision. An untouched dismissal remains durable. Omission by the reviewer is not a fix, and guarded approval still requires its independent checks and complete evidence.

Open, reopened, or verification-required findings make the `Copilot / Review` Check Run neutral by
default, while the Job Summary still contains the complete bounded state
counts. Set `bugbot-fail-on-unresolved: true` only when the repository
intentionally wants findings to fail both the Check and Action invocation as a
branch-protection gate. `unknown`, incomplete synchronization, and analysis failures remain failures in either policy.
Bounded `partial` context, skipped draft review, and superseded review use a
neutral Check conclusion and never claim a complete clean result. A PR metadata
run without exactly one validated Bugbot telemetry snapshot for the current
head publishes no `Copilot / Review`; this also covers duplicate snapshots and
a valid snapshot accompanied by malformed telemetry. Its workflow result and
Job Summary remain visible without hiding the latest analysis Check for that
head. Finding-state evidence uses one complete seven-state count schema. A
missing state, unexpected state, invalid count, or aggregate overflow fails the
Action and Check closed; `/copilot status` reports the evidence as invalid
instead of inventing clean counts.

Bugbot repairs historical review blocks in sequential batches of at most 20, up to 100 per run, with no more than four concurrent writes in a batch. A 42-review backlog therefore completes in the same run as the analysis. If more than 100 remain or a batch fails, the status card and Check show the exact pending count and `/copilot recheck` continues the idempotent repair. The Action uses `workflow.presentation-pending` for a budget remainder, not `provider.unavailable`; a genuine provider write failure remains separate. Duplicate trusted status cards are not deleted: the oldest becomes canonical and later copies are converted to redirects.

The shipped PR workflow grants `checks: write` only to its short-lived `github.token` and exposes it to the Action as `COPILOT_EVIDENCE_TOKEN`. That token is used only for Check Run publication and is excluded from every agent child environment. The separate PAT remains responsible for configured repository and project operations.

Finding matching is intentionally stable across agent providers and wording
changes. The primary local identity uses normalized path, title, and a nearby
line bucket. A second semantic identity uses category plus exact code snippet,
symbol, or title fallback, so nearby movement and file renames keep the same
thread. Descriptions and suggestions are mutable explanation, not identity.
Resolution is only accepted for findings
present in the loaded, bounded history, so an agent cannot resolve an arbitrary
identifier invented in its response.

### Complete and partial context

Bugbot's status card contains a context-coverage section. `complete` means every
applicable bounded source finished without reaching a fixed cap. `partial`
means the run retained a deterministic subset—for example the newest 200
comments, newest 200 thread records, or first 1,000 diff files. The per-prompt
diff character budget does **not** omit later files: Bugbot splits every
non-ignored provider patch into bounded fragments, reviews every partition for
the same head SHA with at most two concurrent reviewer calls, verifies each
partition attestation, and aggregates once before publication. Large patches
are split without dropping sanitized patch characters; missing provider patches
become explicit local-diff inspection assignments.

When every changed file in a canonical pull request matches
`ai-ignore-files`, the exhaustive plan contains zero partitions by design.
Bugbot records the ignored-file count and completes without invoking the
reviewer. It neither creates findings nor asks the model to resolve earlier
findings, so any existing unresolved finding remains open. The legacy
single-query path is reserved for non-PR issue or commit contexts that have no
canonical pull-request diff plan.

If any planned partition still fails, is missing, or returns the wrong
identity/SHA after at most three identical local attempts, or attempts a
resolution outside the sole resolution-owner partition, the whole analysis
fails before finding publication or resolution. A provider file-page
cap is still partial because unenumerated files cannot be planned. Partial analysis
may still report findings supported by retained evidence, but it never says the
whole PR is clean, never resolves a prior finding omitted from the prompt, and
never receives a successful Review Check conclusion.
Lifecycle presentation is equally conservative: partial coverage replaces any
stale `state:ready` label with `state:blocked` and
`state:awaiting-maintainer`. The maintainer can inspect the named omissions or
reduce the change scope; zero findings in the retained subset is not a ready
decision.

A GitHub read error or incomplete partition set is not a successful partial
review: the run fails before finding publication or resolution. For a cap,
inspect the named omitted source, split an
oversized PR when appropriate, and run `/copilot recheck`. For an ambiguous PR
head, close the obsolete PR or invoke the review from the intended PR event.

## Conversation completeness

A generated report from a User account and an ordinary human comment follow the
same untrusted conversation rules. A 5,959-character report can be retained in
full as ordered fragments without granting trust to its heading or author name.
The fixed budget is 50 logical comments and 24,000 rendered characters, with at
most 4,000 UTF-16 units per payload fragment. Source attribution is bounded
untrusted metadata too. No fragment creates a separate source or notification.

Only fully retained comments have zero truncation. Genuine source/provider or
section exhaustion still makes the overall review partial, even when the diff
analysis completed with no findings. Inspect **Incomplete coverage** before
calling that review complete. Approval and protected-path requirements remain
unchanged; retaining a report does not authorize a merge.


## Dependency types and error handlers

Before claiming that a dependency exception escapes a typed catch, Bugbot checks
the exact imported type, resolved coordinate/version and platform against
version-matched source or actual artifact hierarchy. A wrapped cause is not the
same as inheritance. It reconciles the actual fault path and asserted result;
a green mock, skipped test or another artifact is not proof that the production
wrapper is handled. An already caught subtype does not justify a broader catch.
Genuine uncaught wrappers and cancellation swallowed by a broad catch remain
reportable. If the type premise cannot be verified with existing read-only tools,
the reviewer omits that unsupported claim. This is model guidance, with no new
permissions, resolver service, project exception or guarantee of accuracy. See
[quality and observability](/bugbot/quality-observability) for the paired controls.


## Delegated test paths

Before claiming a parameterized test always fails or its stub is unused, Bugbot
selects that row, follows its actual invocation through delegates and callbacks,
and checks fixture identity, guards, collection size and arrangement order. It
traces how map/flatMap and recovery preserve or change the error before the exact
assertion. Looking only at the public method body can miss an indirect binding
call. Matching test/call-count evidence must agree with that path; an unrelated
green test or a called stub alone is insufficient. Real bypassed calls, empty
loops and swallowed errors remain reportable. Review does not change a tested
operation just to reach a mock without first establishing the intended contract.
Unverifiable always-fails claims are omitted. This uses existing bounded read-only
context and review policies, with no new permission or deterministic call-graph
service. See [quality and observability](/bugbot/quality-observability).


## Kotlin/Wasm JavaScript parameter scope

For package-level Kotlin/Wasm `= js(...)` functions, declared parameters become
formal arguments in generated JavaScript, and nested callbacks can capture them.
Before reporting an unbound identifier, Bugbot checks the target/version,
signature and lexical scope against applicable official interop documentation or
exact generated imports. It reconciles same-source compiler/test evidence; an
unrelated green job cannot prove the bridge works. Genuinely missing identifiers
and invalid bridges remain reportable. Unsupported binding claims and unproved
global-state replacements are omitted. This shared model guidance is neither a
static Kotlin analyzer nor a guarantee of accuracy. See the [official contract](https://kotlinlang.org/docs/wasm-js-interop.html#kotlin-functions-with-javascript-code)
and [quality evidence limits](/bugbot/quality-observability).
