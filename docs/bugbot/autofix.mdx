# Autofix

**Bugbot autofix** lets you ask the bot to **fix** one or more previously reported findings. The configured agent determines which findings you mean and applies the fixes. The action checks out the target branch before agent execution, runs your verify commands, and commits and pushes only safe workspace paths. Findings stay open until a fresh review verifies the pushed revision.

When `bugbot-dry-run` is enabled globally, autofix exits successfully before invoking the fixer, verification, commit, or push.

This page explains how to trigger autofix, who can do it, and what the action does under the hood.

---

## How to ask for a fix

### From the issue

Add a **comment** on the issue that references the findings you want fixed. The configured agent receives your comment plus the list of **unresolved findings** (id, title, short description) and returns whether it’s a fix request and which finding ids to fix.

**Example phrases (English):**

- “fix it”
- “fix this”
- “fix all”
- “fix the first one”
- “fix finding abc-123”
- “please fix the null reference and the off-by-one”

**Example phrases (Spanish):**

- “arregla”
- “arregla este”
- “arregla todos”
- “fix it” (also understood)

You don’t have to use exact wording; the configured analysis role interprets intent. Be clear when you want only **some** findings (e.g. “fix the first two” or “fix the one about the login handler”).

For a natural-language comment, mention the configured bot user (for example,
`@vypbot fix the authentication finding`). Explicit `/copilot fix <finding-id>`
and `/copilot fix all` commands do not require a mention.

**Important:** An issue-only comment does not infer a branch by scanning open
pull requests. Request autofix from the intended PR review thread, or use an
explicit branch-scoped CLI/workflow run. Without an authoritative PR/branch
target, autofix stops before workspace mutation. See [Troubleshooting](/security-operations/operations/troubleshooting).

### From a pull request review thread

Reply to the **review comment** that contains the finding. The action sends your
reply plus the **parent comment** (the finding text) to the configured agent so
it can match the finding and run the fix.

The action runs on the PR’s **head branch**, which is supplied by the review-comment event and revalidated before any workspace mutation. A general comment in the PR conversation is an `issue_comment`, so it can request a review or answer but is not a write target. No “resolve branch from issue” fallback exists.

For a read-only fresh review, comment `/copilot review`, `/copilot findings`,
or `/copilot recheck`. These commands invoke the reviewer/detection route and
never modify the workspace. Use `/copilot fix ...` only when you explicitly
want an authorized file-changing operation.

## Permissions

Only **certain users** can trigger file-modifying actions (autofix and [do user request](/bugbot/do-user-request)):

- **Organization repositories:** The comment author must be a **member of the organization** (checked via GitHub’s `orgs.checkMembershipForUser`). If the author is not a member, the action does **not** run autofix; it can still run **Think** and reply with an answer.
- **User (personal) repositories:** The **repository owner** or a collaborator with `push`, `maintain`, or `admin` permission can trigger autofix. Other users get a Think response only.

This avoids random contributors or external users pushing commits via comments. There is no separate “Bugbot role”; the same rule applies to both autofix and do-user-request.

---

## Workflow permissions

The action must be able to **commit and push** to the authoritative branch. A
workflow that runs autofix from **`pull_request_review_comment`** must grant:

```yaml
permissions:
  contents: write
```

Without `contents: write`, the action cannot push. Detection (and posting findings) does not require this; only **autofix** and **do-user-request** do.

Example: see [Examples → Pull request review-thread workflow](/bugbot/examples#pull-request-review-thread-workflow-for-autofix).

## Verify commands

After the configured agent applies the fixes in its workspace, the action runs **verify commands** in the runner (e.g. build, test, lint). These are configured with **`bugbot-fix-verify-commands`** (comma-separated). For example:

```yaml
bugbot-fix-verify-commands: "pnpm run build, pnpm test, pnpm run lint"
```

- If **all** commands succeed, the action runs `git add`, **commit**, and **push** with a message like `fix(#123): bugbot autofix - resolve finding-1, finding-2`.
- If **any** command fails, the action **does not commit**. No push happens, and the findings are not marked as resolved.
- Each command is spawned without a shell, with a temporary `HOME` and an allowlisted environment that excludes GitHub tokens, agent/provider credentials, cloud secrets, and local agent auth-store paths.

So verify commands act as a gate: only passing runs produce a commit. They still execute repository code as the runner OS user, so configure only commands trusted for that repository and isolate self-hosted runners from sensitive host data. If you leave `bugbot-fix-verify-commands` empty, only the configured agent’s run is used (the action may still commit if there are file changes). See [Configuration](/bugbot/configuration#bugbot-fix-verify-commands).

## What happens after a successful fix

1. The configured execution role applies the code changes in its workspace.
2. The action runs the **verify commands** in the runner; if any fails, it stops.
3. The action runs **git add**, **commit** (message: `fix(#N): bugbot autofix - resolve <finding ids>`), and **push** to the branch.
4. The action leaves the findings open, pushes, and then starts a fresh read-only review in the same authorized workflow. Bot-authored push events are intentionally discarded before queueing; only the independent post-push analysis may update markers and resolve PR threads.

This prevents a successful edit or test command from being mistaken for proof that the original defect no longer exists.

## Troubleshooting

- **Bot didn’t run autofix:** Check that the selected agent CLI is configured, the comment is interpreted as a fix request (e.g. “fix it”, “fix all”), and there is at least one **unresolved** finding. The request must come from the intended PR review thread or another execution with an explicit branch target; issue-only comments never guess a branch. See [Troubleshooting](/security-operations/operations/troubleshooting).
- **Commit not made:** Verify commands run after the fix; if any fails, no commit is made. If the configured agent didn’t change any files, there’s nothing to commit. If push failed (e.g. conflict or missing `contents: write`), check workflow permissions and token scope.
