# First issue workflow

Use a documentation change for your first run: it exercises issue admission,
branch creation and PR review without changing application behavior.

<Steps>
  <Step title="Create a Documentation Update issue">
    Open **Issues → New issue → Documentation Update** and complete the required
    fields. The installed form supplies the routing labels (`documentation` and
    `docs` by default). Copilot checks the enabled workflow profile and adds the
    native issue type, assignee, project item and welcome or plan response.
    Admission alone does not start implementation or create a branch.
  </Step>
  <Step title="Start the work">
    An authorized maintainer adds `in-progress`. Wait for the Action run to
    finish and inspect **Development** on the issue for its exact linked branch.
    Copilot applies `branched` after it verifies the remote branch. Continue on
    that linked ref; its name and parent are chosen by the Action.
  </Step>
  <Step title="Check readiness and recover failures">
    Comment `/copilot status` to inspect the current lifecycle and branch, or
    `/copilot help` for the command reference. If the branch is missing or the
    issue is `state:blocked`, inspect the failed run and its **Job Summary**,
    correct the reported cause, and retry the workflow. If the issue is awaiting
    a maintainer and no run failed, follow the status card's next-action guidance
    or wait for the maintainer. A branch created before a later failure may
    already be retained: verify the
    existing link before contributing.
  </Step>
  <Step title="Contribute on the linked branch">
    Fetch and check out the exact remote ref shown in Development. Make the
    documentation change, run the relevant validation, commit, and push to the
    same ref. The Action manages remote naming, parent selection, synchronization
    and cleanup; use its branch commands when those operations are needed.
  </Step>
  <Step title="Open and verify a linked pull request">
    Open a PR from the managed branch to its recorded parent and link the issue,
    for example with `Closes #123`. Include what changed and the checks you ran.
    Verify the generated description, native labels and project status, the
    **Copilot / Review** check, and the Actions **Job Summary**. Use
    `/copilot description` to refresh the PR description and `/copilot recheck`
    after addressing review findings.
  </Step>
  <Step title="Complete the workflow">
    Resolve findings and required checks, then let an authorized maintainer merge
    the PR. Verify the linked issue and project status after completion. Release
    and hotfix publication have their own explicit deployment workflow.
  </Step>
</Steps>

## When an SDD is required

With `pre-branch-sdd: true` and `issue-managed-branches: true`, features and
issues marked `contract-change` must pass the pre-branch SDD gate. After
`in-progress`, answer the blocking questions using the exact format on the
status card, such as `SDD Q1: Show the verified state and pending questions.`
Copilot then validates and commits the SDD to the linked branch before applying
`branched`. Help issues remain branchless.
