# Configurable issue workflows

`copilot setup` uses one ordered workflow catalog for Issue Forms, routing labels, native Issue Types, branch roles, release dependencies, runtime admission, and generated agent guidance. Interactive setup starts with **All** selected: use Space to toggle a kind and Enter to confirm.

In the terminal, Enter without toggling keeps **All**. Pressing Space while **All** is selected clears every kind; Enter then submits that empty selection explicitly instead of restoring the default. If issue automation is still enabled, setup stops before applying changes and explains that you must select at least one kind. To configure no issue workflows, turn off issue automation at the earlier question. In the text-only fallback, type `none` to submit an empty selection explicitly.

For non-interactive setup, pass stable IDs:

```bash
copilot setup --non-interactive --yes \
  --issue-workflows feature,bugfix,documentation,chore,help
```

Or configure the same selection in YAML:

```yaml
issueWorkflows:
  enabled: [feature, bugfix, documentation, chore, help]
```

`all` is accepted by the CLI. Unknown and duplicate IDs are rejected. The older `features.release` and `features.hotfix` switches are compatibility inputs; when both old and new settings are supplied they must agree.

## Catalog

| ID | Installed form | Routing labels | Managed remote branch | Extra workflow |
|---|---|---|---|---|
| `feature` | `feature_request.yml` | `feature`, `enhancement` | `feature/…` | — |
| `bugfix` | `bug_report.yml` | `bugfix`, `bug` | `bugfix/…` | — |
| `documentation` | `doc_update.yml` | `documentation`, `docs` | `docs/…` | — |
| `chore` | `chore_task.yml` | `chore`, `maintenance` | `chore/…` | — |
| `help` | `help_request.yml` | `help`, `question` | none | — |
| `hotfix` | `hotfix.yml` | `hotfix` | `hotfix/…` | `hotfix_workflow.yml` |
| `release` | `release.yml` | `release` | `release/…` | `release_workflow.yml` |

Configured label overrides are rendered into newly installed forms and into `.copilot/repository-profile.json`. Deselecting release or hotfix also deselects its workflow; an unchanged setup-owned file is moved to `.copilot/setup-backups/`, while a customized file is preserved and reported as drift.

If `features.issueTemplates` is disabled, admission still uses the selected profile. A maintainer-approved manual issue must then contain exactly one enabled routing group and every required Markdown heading.

## Live admission

The compact profile is stored in `COPILOT_ISSUE_WORKFLOW_PROFILE` and passed as `issue-workflow-profile` by every issue-bound workflow. After the workflow queue, the Action reloads the live labels, body, and durable Copilot state. It does not trust a stale event payload.

| Live state | Passive event | Explicit command, `in-progress`, deploy, or issue-bound action |
|---|---|---|
| enabled and valid | execute | execute |
| disabled or unmanaged | successful no-op | blocking result |
| conflicting kinds | block | block |
| missing, duplicate, or invalid required fields | block | block |
| disabled with an existing branch/PR | PR completion and cleanup only | unsafe commands block |
| disabled with an existing durable deployment | finish or recover that operation only | a new deployment blocks |

An unlinked pull request stays on its PR-native route. Help is always branchless after `in-progress`, including when `issue-managed-branches` is enabled.
Provider-backed `ai-members-only` authorization runs only after this live
decision returns `execute`. No-op, blocked, and continuation-only work does not
query membership or prepare an agent; protected agent task models remain
disabled until the post-admission lookup authorizes them.

## Migration and diagnosis

Setup without field mappings writes an explicit schema-1 profile, including an all-kinds selection. Explicit mappings opt into schema 2. Run `copilot doctor --config <setup.yml>` to detect profile, form, workflow, generated-guide, and manifest drift without changing files.
An omitted profile in a manually wired workflow selects all seven kinds and
still applies the same required body checks. Malformed profile JSON blocks.
When admission blocks, correct the selected setup kind, conflicting live labels, or required issue body. Do not work around admission by inventing a branch or changing the generated profile manually.


## Preserved application-specific headings

A consumer form may call its application version `VaultStadio Version` instead
of `copilot Version`. Declare that relationship in the reviewed setup file;
Copilot never guesses version fields from their suffix or rewrites a customized
form to fit an upstream product name.

```yaml
issueWorkflows:
  enabled: [feature, bugfix, documentation, chore, help, hotfix, release]
  fieldMappings:
    bugfix:
      copilot Version: VaultStadio Version
```

Run `copilot doctor --config copilot.setup.yml`, then apply setup using the same
configuration. Setup compares the selected existing forms before writing guide/
profile facts. A missing or duplicate governed label, an unsupported required
scalar, or a required-value mismatch blocks that local apply and names the form
and expected field. Existing compatible consumer forms keep their bytes. New
forms, guide facts and the runtime Variable use the same mapped headings.
Checkbox acknowledgements and optional contextual fields remain native form UI.
Release Type keeps a single-select dropdown with Patch, Minor and Major. Version
dropdowns offer only Automatic or semantic versions and a single selection; version
textareas use plain text so rendered code fences cannot invalidate their value.

Mappings are one-to-one replacements for catalogued headings in enabled kinds,
including release/hotfix headings. They change names, not `Automatic`, semantic
version or release-type meanings. A target must be trimmed single-line text of
at most 128 UTF-8 bytes; two roles cannot share a case-insensitive target. Unknown
roles/kinds, mappings for disabled kinds, duplicate JSON keys and malformed input
are rejected. The complete runtime profile remains limited to 4096 UTF-8 bytes.
Schema 1 rejects mappings; schema 2 requires a nonempty explicit map. Upgrade both
the setup CLI and every effective Action runtime to a version supporting schema 2
before adopting the new profile. A merge into develop does not upgrade a runtime
pinned to master or a released tag.

For a blocked run, open its GitHub Actions Job Summary. It names the exact missing
or invalid heading, its workflow kind and the recovery action. Correct the body
using the installed form, or review the mapping if form and profile disagree,
then rerun. An unrelated upstream compatibility heading cannot replace the mapped
field. Fenced examples and hidden HTML comments do not supply required fields.
No planner or branch starts, no conversation diagnostic is posted and no minimal
hidden configuration is saved for blocked/no-op admission. Existing configuration
stays intact. The previous summary records that attempt; a repaired fresh run uses
its own live issue body and labels and resumes the normal Action-owned lifecycle.
Bundled English/Spanish diagnostics and complete English fallback require no agent.
