# Comment commands

Branchless help requests stay on the read-only answer route even when natural
language classification suggests a repository task. File changes require an
authoritative branch from a supported surface, such as a PR review comment;
a general conversation cannot infer one from the checkout's current branch.

Copilot can act as a project assistant directly from an issue or pull-request comment. With the default workflow PAT, the bot user is `@vypbot`; if your installation uses another account, replace that mention with the configured PAT user.

A comment must begin with `/copilot` or contain the exact bot mention. All
other comments—including documentation, coverage, and other automated
reports—are inert and exit before project lookup, AI configuration, translation,
or agent runtime preparation.

## Fast start

Comment this on an issue or PR:

```text
@vypbot analyze this change for security and reliability risks
```

This starts a read-only analysis when the mention matches the bot account. It does not edit files, commit, or push. You can write the request in English, Spanish, or another language supported by the configured locale/agent flow.

## Explicit commands

Commands are recognized at the beginning of a comment, case-insensitively. The complete command is limited to 2,000 characters. Prose requests such as implement, plan, explain and remember may exceed twenty words; structured commands retain the twenty-argument limit. They are deterministic and easier to audit in automation logs.

| Command | Purpose | Writes files? |
| --- | --- | --- |
| `/copilot help` | Show this command reference. | No |
| `/copilot plan` | Propose an implementation plan. | No |
| `/copilot clarify` | Identify missing information and questions. | No |
| `/copilot estimate` | Estimate implementation effort. | No |
| `/copilot test-plan` | Propose a test strategy. | No |
| `/copilot explain` | Explain the relevant code or behavior. | No |
| `/copilot diagnose` | Investigate a reported error or failure. | No |
| `/copilot analyze` | Run a fresh Bugbot-style review for potential problems, including security risks. | No |
| `/copilot review` | Run the read-only review flow. | No |
| `/copilot findings` | Reconcile and publish current findings. | No |
| `/copilot recheck` | Re-run the review against the current branch. | No |
| `/copilot sdd-diff` | Compare verified first/current SDD publications without an agent. | No |
| `/copilot status` | Show the current Copilot status. | No |
| `/copilot description` | Refresh the PR description when that action is configured. | No |
| `/copilot fix <finding-id> [finding-id ...]` | Fix one or more existing Bugbot findings. | Yes, if authorized |
| `/copilot dismiss <finding-id> [finding-id ...]` | Dismiss one or more findings. | No file changes |
| `/copilot implement <request...>` | Apply a general code, test, refactoring, or documentation request. | Yes, if authorized |
| `/copilot remember <rule...>` | Save a learned Bugbot rule. | Yes, if authorized |
| `/copilot sync-branch [--dry-run] [--no-agent] [--from <branch>]` | Merge the issue/PR parent into its working branch; use the fixer only if eligible conflicts occur. | Yes, if authorized |

`/copilot fix`, `/copilot dismiss`, `/copilot implement`, and `/copilot remember`
require at least one argument. Give `fix` and `dismiss` one or more finding IDs;
give `implement` a concrete request and `remember` the rule text. For
`sync-branch`, `--from` must be followed by a branch name. Arguments are
whitespace-separated, and commands are limited to 2,000 characters and 20
arguments. Missing or malformed required arguments produce a validation reply;
they never mean “all” or authorize a broad change.

`help`, `status`, `sdd-diff`, `dismiss`, `remember` and rejected commands do not run a
model or change the temporary agent activity label. `sync-branch --dry-run`
and `--no-agent` also avoid model activity. Ordinary sync may use the conflict
fixer, and `findings` runs a fresh review. These distinctions preserve each
command's existing authorization and repository effects.

### Where command results persist

Read-only commands publish a correlated GitHub reply and do not change repository
files. Retrying the same source comment updates or reuses that reply. Results
that change repository state are retained in the repository or GitHub resource
they operate on:

- `/copilot fix` and `/copilot implement` apply changes to the authoritative
  working branch, run configured verification, then commit and push through the
  trusted workflow. A verification failure prevents the commit. Every new file
  inside an untracked directory is checked against sensitive-path rules and
  the 100-file automatic mutation limit.

  `/copilot implement` then confirms whether changes were pushed or no commit
  was needed. Review the diff and acceptance criteria before considering the
  feature complete. A successful implementation clears an earlier blocked
  lifecycle state on the issue and returns it to working.

- `/copilot remember` appends the rule to `.copilot/BUGBOT.learned.md` and
  commits it to the repository.
- `/copilot dismiss` records dismissal against the existing Bugbot finding in
  GitHub review state; it does not edit repository files.
- `/copilot sync-branch` merges the parent into the working branch and pushes
  the result unless `--dry-run` was supplied.

An implementation request in an issue uses its verified linked branch, even
when the comment event has no commit branch. In a PR conversation it uses the
exact current PR head in this repository. Missing or conflicting branch
evidence stops implementation before the agent runs.

The agent runtime does not retain a session between runs. Repository changes
that are committed and pushed, plus finding/review state stored by GitHub, are
the durable record. A prepared but uncommitted workspace is not durable.

When a finding ID contains spaces, quote the complete ID with double quotes:

```text
/copilot dismiss "docs/file.mdx:28:message with spaces"
/copilot fix "docs/file.mdx:28:message with spaces"
```

Fix IDs are literal and are not translated. `/copilot fix all` selects all
unresolved findings; otherwise only the exact requested IDs are selected.
You can combine plain and quoted IDs. Use JSON escapes for a literal double
quote or backslash; malformed, empty or multiline quoted IDs are rejected.
The command still accepts at most 20 IDs and 2,000 characters.


`/copilot status` reports lifecycle, waiting state, branch, labels, and the
canonical Bugbot counts: open, reopened, verification-required, unknown, and
resolved. In a PR conversation, it reads one trusted complete Bugbot status
card for the current commit and checks that the head is still unchanged. If
that evidence is missing, malformed, incomplete or stale, run `/copilot recheck`
and retry status. It never substitutes cached counts or zero. Setup reads that
exact PR to resolve its linked issue and working branch. An unlinked PR remains
separate from an issue with the same number. Status and description queries
preserve existing lifecycle and waiting labels when they make no lifecycle
decision.

For issue types covered by `pre-branch-sdd`, status also appends an SDD
readiness section. It reports when an SDD is not required and marks required
SDD evidence unavailable until the reader verifies the current owned card,
immutable catalog and remote publication. It shows pending question IDs and
the owning specification, then links the verified current publication once
ready. Old answer rounds and stale issue or branch evidence cannot establish
readiness. A `published` marker or existing branch alone never means the SDD is
ready. Missing or unverified evidence blocks a readiness claim; status remains
read-only and preserves its existing fields. SDD readiness confirms the published
specification and its branch evidence. It does not certify that implementation
is finished, that CI or review passed, or that the PR can be merged.

Status uses the same installed issue-workflow profile as SDD preparation. An
unchanged profile does not require republishing an otherwise current SDD; a
changed profile still invalidates its current readiness claim.

A newer bot-owned comment that lost its SDD identification prevents an older
card from certifying readiness. Canonical replies, progress cards and branch
notifications for the same issue remain separate surfaces. An unidentified or
corrupted bot comment can therefore make SDD evidence invalid; inspect and
reconcile that conversation before relying on an older publication.

After the first verified publication, a new clarification round reports
**Revision pending**. Its first-publication link is explicitly historical; it
does not certify the pending revision. The section keeps unanswered question
identifiers visible, or asks to resume publication once answers are complete.
Once the revision is verified, status shows the current publication and the
immutable first publication separately when their commits differ. A change to the issue body keeps a separately verified first publication explicitly historical until the revision is published. Failed final identity checks remove that link. Status reads each maintainer's current permission once per request, with at most 16 distinct accounts; failed or exhausted permission reads make SDD evidence unavailable. Later requests recheck permissions.

Read-only commands answer the current comment, using the issue or PR as
background. Add the file, symbol, failure or requested work after the command to
make the subject explicit. For example, `/copilot explain src/domain/copilot_command.ts`
asks for that file's behavior. If the agent cannot inspect it, its answer should
state the limitation. `diagnose` separates evidence from hypotheses, `clarify`
asks for missing information, `estimate` includes uncertainty, and `test-plan`
provides test cases and observable acceptance criteria.

Every explicit answer uses a correlated reply marker. A webhook retry with the
same source comment updates or reuses that response instead of creating another.
These replies contain only their requested content; they are never wrapped in an
“Automatic Actions” summary or a list of internal steps.

### Implementation-plan response

`/copilot plan` returns one implementation-plan card. The same card is also the
planning surface used when a normal issue is opened with the planner configured,
or when `recommend_steps_action` is invoked. It contains three to eight ordered
steps, no more than two short details per step, and one specific, verifiable
acceptance criterion. For example:

```markdown
## Implementation plan

> **Current status:** Ready to start. No action is required from maintainers before implementation.

1. **Define the locale contract**
   - Add the repository default and issue/PR inheritance rules.
   - Preserve BCP-47 identifiers in stored state.
2. **Apply the contract at publication boundaries**
   - Keep command names, paths, refs, and error codes unchanged.
3. **Verify replay and strict-state behavior**
   - Cover English defaults, a configured locale, and rejection of removed state shapes.

**Acceptance:** Replaying the same event creates no additional comment, while a material issue edit updates this card in the configured issue locale.

Need something else? Mention the bot with a question or use `/copilot help`.
```

This visible structure is owned by Copilot rather than generated as arbitrary
Markdown by the agent. The agent supplies only bounded titles, details, and the
acceptance text in the effective issue locale. English (`en-US`) is the default;
any configured valid locale uses the complete resolved catalog or fails back
atomically to English. A plan with the wrong output locale or an invalid shape
is rejected before publication. Material issue edits update the existing card;
equivalent edits and webhook retries are silent. Stored plan state has one closed
shape: description fingerprint, plan fingerprint, structured plan, and canonical
effective issue locale. Missing, extra, or removed free-form fields make the
state invalid. A replay is allowed only while the stored locale still matches.
Changing the issue or repository locale makes the next configured planning run
replace the complete plan in the new language; an agent that returns `unchanged`
is rejected. Without a configured agent, Copilot fails closed instead of
republishing content in an unverified language.

GitHub delivers a comment in the main PR conversation as an `issue_comment`
event. Copilot uses GitHub's PR marker and exact PR number to keep that transport
detail from changing the target: read-only commands such as `/copilot recheck`
use the PR locale, reviewer role, and canonical PR diff. They do not run
issue-only setup or search for a candidate PR. GitHub does not include the PR
head fields in this event, so Copilot verifies the exact numbered open PR and
base repository through GitHub, reviews the returned head revision, and checks
that revision again before and after publication.

## Natural-language requests

Mention the bot and describe the outcome you want:

```text
@vypbot explain why this test is flaky
@vypbot diagnose the 500 error described above
@vypbot review the PR for authentication and injection vulnerabilities
@vypbot add regression tests for the null response case
@vypbot update the issue's branch
```

The first three are read-only requests. The last one may be classified as a general implementation request. Natural-language file changes require an authorized actor and an available branch; the action runs the configured verification commands before committing and pushing.

Language detection and translation apply only after this same explicit
command-or-mention boundary. Copilot does not passively translate ordinary
conversation or machine-authored status comments. When an addressed request is
translated, its one useful answer ends with a collapsed, localized block named
“Interpreted request” and “Original request” in the effective issue or PR
locale. The human comment is never edited, and a translation never creates its
own timeline comment. English is used when no locale is configured; any valid
configured BCP-47 locale uses its complete resolved catalog or an atomic English
fallback.

Before the language provider receives an addressed request, Copilot replaces
code spans, paths (including bare names such as `README.md`), recognizable Git
refs and versions, issue or PR references, URLs, quoted literals, option flags,
and commit IDs with opaque operands. Commands whose grammar has no translatable
prose protect every argument, including an arbitrary value passed to `--from`.
The provider must return every operand exactly once. Sentence-ending periods
beside code spans remain ordinary punctuation. Copilot restores operands only
after validating that none was removed, duplicated, reordered, changed, or
introduced, so a translation cannot turn `src/cache.ts` into another path or add
`--force`. A failed validation performs no requested repository change. Reconstructed commands also retain the fixed 2,000-character and 20-argument limits; an expansion beyond either limit returns an interpretation error before answering or writing. Rephrase the request more briefly to retry.

An explicit command or mention that fails receives one correlated semantic
error reply with impact, recovery action, retained state, stable error code,
retryability, and reference. It never exposes parser, provider, or exception
text. Background failures remain in the Check and Job Summary instead of
creating timeline noise. If the request itself could not be translated safely,
that reply uses the complete English fallback so it cannot mix languages.

## Authorization and safety

`remember` confirms when the rule was saved, verified and pushed to the exact
working branch. Repeating an existing rule confirms that no change or additional
commit was needed. `dismiss` confirms the number of matching findings dismissed;
if no finding matched, its reply explicitly says nothing was dismissed. A
permission or capability refusal says the command was not applied. A failed
verification or mutation receives an error reply, never a success confirmation.
These replies use the conversation language and reuse the same response on an
event replay.

- Read-only commands and answers can be requested by any participant who can comment.
- File- and finding-state-modifying requests require the comment author to be the repository owner or have `push`, `maintain`, or `admin` permission; organization membership alone is not sufficient. `ai-members-only` remains a separate membership gate.
- In personal repositories, the author must be the repository owner or a collaborator with `push`, `maintain`, or `admin` permission.
- `/copilot dismiss` does not edit files, but it changes finding state and therefore uses the same authorization guard.
- File-changing commands require an authoritative PR review-thread branch or an
  explicitly branch-scoped execution. Issue-only comments never scan open PRs
  to guess a write target. `/copilot remember` verifies the exact current PR
  through GitHub or the issue's native branch link before checking it out; a
  missing event ref is allowed only when that verification supplies the ref.
  Closed PRs, forks and unavailable identity are rejected before storage.
- The workflow must grant `contents: write` for file-modifying actions and
  disable checkout credential persistence. When repository mutation uses the
  configured `PAT` Secret, that token must have repository contents write
  access. Actor authorization is checked separately, so a capable token does
  not grant the commenter permission. Verification failures prevent the commit.
- Bot mentions are matched case-insensitively and with username boundaries, so `@vypbot-extra` does not accidentally trigger `@vypbot`.
- Branch synchronization accepts `--dry-run`, `--no-agent`, and `--from <branch>` and applies additional Git-state, path, verification, and remote-race guards. See [Branch synchronization](/issues/branch-synchronization).

## New-issue welcome

When a new normal issue has a generated plan, that single plan card includes a
one-line command hint and no separate welcome. A question/help issue receives
its direct answer in the configured issue language without a second onboarding
comment. Event replays reuse the answer's hidden correlation marker instead of
creating a duplicate; unchanged stored plans are reconciled with their existing
card and recreated if that card was removed. Before adding a fallback, Copilot
also checks its own existing plan, direct-answer, and current welcome reply markers. If neither plan nor
answer can run, one static welcome explains `/copilot help` and `@vypbot`.
Release and hotfix issues do not receive this fallback because their durable
deployment dashboard owns the presentation.

The shared reply publisher adds the same current hidden identity used by other
correlated replies; the welcome text embeds no separate marker.

See [Bugbot detection](/bugbot/detection), [Autofix](/bugbot/autofix), and [Do user request](/bugbot/do-user-request) for the execution details.

SDD status keeps an unknown requirement visible when the issue has no admitted
workflow kind. Evidence links use the configured GitHub server origin and the
same issue identity; an untrusted or mismatched URL is shown without navigation.

## Compare SDD publications

Run `/copilot sdd-diff` without arguments in an eligible issue. The reply links
verified immutable first/current SDD publications and their commits, and compares
added/removed lines and up to eight changed section titles. The commit comparison
link can include other files changed between those commits; the reported counts
cover only the owning SDD. This is a structural comparison, without an assessment
of semantic requirements or document excerpts.

A first publication without a revision reports `initial-only`. Pending answers
and a changed issue withhold current counts and link the existing clarification
card when verified. Missing, invalid or unavailable evidence is explicit. The
command reads current issue, record and branch facts again before claiming a
current comparison. It does not run an agent, change activity labels or edit files.

On a PR, exactly one SDD-eligible issue among the native same-repository closing
links is required, and its current linked branch must match the PR head. Copilot
checks at most 100 native candidates and reports ambiguity for multiple eligible
issues; the command never guesses from issue numbers in text. Use the intended
issue conversation to resolve ambiguity. The same eligibility selection is rechecked before returning counts. A replay of the same source comment
refreshes its existing owned reply; a new comment gets a separate reply.

Comparison limits are fixed: 70,000 characters, 280,000 UTF-8 bytes and 2,000
content lines per document, and 2,000,000 line-comparison steps. Over-limit
results retain safe verified links and withhold exact counts. English and Spanish
are bundled; other locales receive a complete English fallback without a model.
Paths, refs, URLs and configurable limits are not accepted as command arguments.

When the detected request language and writing script already match the target,
Copilot keeps the original wording and omits a redundant translation disclosure.
Mixed-language requests and different writing scripts can still be translated.


On a PR, `/copilot sdd-diff` verifies the native closing-issue association again
before returning every result, including pending or missing publication. If the
association changes, retry the command: the stale reply withholds links belonging
to the previous issue. An unreadable final association remains unavailable.
