# Branch management

Adding `in-progress` starts every admitted issue workflow. Opening an issue or adding its type label only classifies it. When `issue-managed-branches: true` (the default), the Action creates the issue branch, verifies the exact linked remote branch, and then adds `branched`. `branched` is a readiness result; adding it yourself cannot start work.

| Issue kind | After `in-progress` |
| --- | --- |
| Feature, bugfix, docs, chore | Create a branch from `development-branch` when branch management is enabled. |
| Hotfix | Create from the selected production version tag after form and membership checks. |
| Release | Create from `development-branch` after form and membership checks. |
| Help | Answer the issue without a branch or `branched`. |

To work without Action-managed branches, set `issue-managed-branches: false`. The issue still starts with `in-progress`; the Action does not add `branched`. Release and hotfix workflows require managed branches. The optional [pre-branch SDD gate](/issues/pre-branch-sdds) also requires managed branches.

## Ready to implement

For a regular branch-bearing issue, the visible sequence is `in-progress` → linked branch → `branched` → implementation. The Action checks the branch's exact GitHub issue link and remote SHA on every issue run. If the link or branch is missing, it removes an unsupported `branched` label. If verification fails, it reports the error and pauses branch-dependent work.

Implementation recommendations also wait for verified branch readiness, including issues that do not require an SDD. A failed or pending verification cannot publish a new “Ready to start” plan. Branchless workflows can still provide guidance without branch evidence.

In private repositories, keep `persist-credentials: false` on the checkout and pass the configured credential through the Action's `token` input. Issue branch preparation authenticates its Git fetches using configuration scoped to each Git process; it does not store credentials in the checkout configuration or remote URL. If preparation fails, inspect the reported error, correct token access if needed, and rerun the same issue workflow.

With `pre-branch-sdd: true`, an eligible feature or behavior-changing issue enters `state:specifying` first. The Action clarifies the contract in issue comments, validates the SDD outside the new branch, creates the linked branch, and publishes the SDD as its first commit. Only after the remote commit is verified does it add `branched` and move to `state:working`.

## Naming and source branches

Branch names follow `<tree>/<issue-number>-<slug>`. The title supplies the slug; `feature-tree`, `bugfix-tree`, `docs-tree`, `chore-tree`, `hotfix-tree`, and `release-tree` configure the prefix. `development-branch` defaults to `develop`; `main-branch` defaults to `master`.

Examples: `feature/123-add-user-login`, `bugfix/456-fix-null-check`, `hotfix/789-critical-payment-fix`, `release/10-v1-2-0`.

If branch creation succeeds but a later step fails, rerun the issue workflow on the same issue. The Action reuses the linked branch and verifies its current remote state. Do not create a second branch to recover an SDD publication failure.

## Progress evidence

Progress assessments use an immutable GitHub comparison of the actual native PR target and the managed branch head. If no open PR owns that exact head branch, they use the configured development base. The agent receives the source patches directly and does not need shell commands. Generated build files contribute metadata only; a percentage does not certify CI or a build.

Copilot first classifies every nonempty line of the full issue body by source identifier as required, excluded, context or uncertain, before it analyzes patches. The scope request, comparison parts and final assessment keep complete issue text, extracted scope and model facts inside explicit untrusted-data blocks. Embedded instructions cannot grant workflow authority. Inputs that exceed the fixed UTF-8 budgets are rejected with retained progress rather than shortened to fit. Small comparisons then use one assessment. Larger complete comparisons are reviewed in up to four rounds of 16 parts (64 parts total), each containing complete patches or identified content slices within the unchanged 256,000-byte UTF-8 evidence limit. Every part must return bounded facts for every assigned file or content unit before one final assessment can update progress. These facts preserve uncertainty and do not certify CI. Their final combined summary has a maximum 384,000-byte budget. Copilot reserves every admitted path and the complete security/schema/task envelope and configured effort suffix inside the unchanged 512 KiB runtime ceiling, then requests concise facts using the same calculated limit in the schema and parser. No returned facts are silently shortened. Source parts and the manifest retain the 256,000-byte limit.

### Which comparison is assessed

One native open PR in the same repository selects its actual base branch, including
production or release targets. Copilot verifies the exact head, reads the native
base ref and pins both SHAs. It does not trust a possibly historical PR `base.sha`,
a target named in issue prose, local checkout state or model output. Two matching
PRs, foreign/fork identities, unavailable reads or an invalid head fail closed;
Copilot does not guess a target or silently fall back. A runtime missing this
read capability reports an unsupported configuration.

Before publishing, Copilot rereads the acceptance body, PR ownership and native
refs. A PR closing, appearing, changing target or being replaced, or a source/base
moving, retains the prior progress. Branch names are untrusted data in prompts
and escaped metadata in run logs. The result keeps the configured
`developmentBranch` and separately records `comparisonBaseBranch`,
`comparisonSource` and the actual `baseSha`.

This matters for inherited production binaries. A maintenance PR against master
may have only text changes even though comparing it against develop includes
already-produced libraries. Copilot assesses the complete native-target delta;
it does not filter those libraries or call their metadata a content review.
Standalone work without a PR still uses development. Binary changes genuinely
remaining in the selected comparison require adequate reviewable evidence and
remain unassessed when that evidence is unavailable.

### Omitted or incomplete patches

Copilot checks unified hunks and changed-line totals before using a patch. For
omitted, truncated or oversized text patches it reads exact Git commit, tree and
blob objects using the same repository credential. The preimage is the pinned
comparison merge base; the target is the pinned branch head. Complete directories
prove paths and presence; blob size, canonical base64 and recomputed Git hash
prove bytes. This does not inspect a checkout or execute commands.

Regular UTF-8 text, empty additions/removals and verified renames/copies are
supported. Identical renames require independently resolved old and new paths
with the same blob; zero statistics alone never prove equality. BOM, CRLF and
Unicode bytes are preserved. Binary/non-UTF8 files, symlinks and submodules remain
unsupported recovery inputs. Lockfiles and specification registries receive
complete content, rather than a metadata exemption.

Native recovery uses at most four accounting frames. Each frame admits 64 files,
4,194,304 represented side bytes, 256 Git object requests and 50,000 directory
entries. A new frame continues automatically when a frame is full; total credit
never resets. Total limits are 256 recovered files, 16,777,216 side bytes,
1,024 requests and 200,000 entries. Each verified blob is at most 2,097,152 bytes.
The 299-path complete inventory, 512-unit, 120,000-byte JSON slice,
256,000-byte source/manifest, 384,000-byte fact and 512 KiB full request limits
remain fixed. Cached contents still consume represented side-byte credit.

Every source part and the complete manifest bind the exact base/head/preimage,
paths and units. A fresh host attempt ID and digests bind each model request to
the full issue, extracted scope and locale. Missing, reordered, stale, duplicate
or corrupt parts/responses are rejected before final assessment. All source and
prompt capacity checks finish before the first model request. No source or facts
are shortened to fit; progress is published only after every response and the
existing native freshness checks pass.

Run details show required path/part counts, recovery usage and the current round.
Automatic continuation happens inside the same invocation. After interruption,
rerun the current managed source through the existing progress/Commits workflow;
it collects a fresh complete attempt without reusing partial facts. There is no
durable partial-analysis checkpoint. Coherent specification packages do not need
to split scope, omit registries or retarget a PR to fit the old per-frame limits.

If full recovery is unavailable, the run reports `validation.evidence-unavailable`
and names up to eight unreviewed paths plus their total count. Exhausted total
or analysis capacity reports nonretryable `validation.evidence-too-large` with
retained progress. Inspect the pinned comparison and reported limit; retrying an
identical over-limit input cannot add capacity. A genuine provider outage keeps
its normal retryability.
For unsupported binary/non-text contents, the shared CLI/Job Summary reports
exact unreviewed paths and distinguishes unavailable progress from project
verification. It shows up to eight complete names within an 8,192-byte diagnostic
budget, with total/shown counts; the complete pinned inventory appears in at most
299 numbered run-log records. Names remain reversible JSON literals, with control,
HTML, mention and Markdown characters kept inert. No source or binary bytes are
logged. Inspect the intended PR base and pinned paths. Actually changed binaries
need reviewable source and provenance; zero counters or a successful compile do
not establish binary correctness. Do not retarget a legitimate PR to hide changes
or split production libraries merely to manufacture textual patches.

A failed middle part never publishes partial progress or requests a final
percentage. Replay reloads exact evidence and does not reuse partial facts.

### Scope and verification

Only the original issue defines completion requirements. Each assessment cites a
requirement such as `[R1] Edit and clear inventoried inputs` and explains its
source support or verification uncertainty. Reports and patches can reveal
separate product debt; that debt does not automatically become work required to
finish this issue. Compatibility-only mobile scope does not require device
execution. If search correctness or device journeys are actually required by the
issue, they remain required.

Source changes, reported execution and independently verified execution are
different facts. Repository reports and model summaries are not trusted test
attestations. An execution requirement without independent evidence remains
unverified, rather than becoming a successful test claim. A percentage is an
estimate; it does not replace review, CI, coverage or approval gates.

Every source line must be accounted for exactly once, including unchanged acceptance criteria; an omitted or duplicated source identifier rejects the entire interpretation. Ambiguous lines remain required verification uncertainty and cannot be marked complete. The issue-only interpretation admits at most 1,024 nonempty source lines, with at most 32 required/uncertain lines and 32 exclusion
lines, each a complete trimmed source line of at most 1,200 Unicode code points.
Its serialized form is limited to 64,000 UTF-8 bytes, reserved before the first
request within the existing runtime ceiling. Nothing is silently shortened to
fit. One scope request precedes the existing complete evidence and final
assessment requests. An invalid source identifier, incomplete classification, extra/missing requirement identity,
contradictory result, oversized output or changed issue body retains existing
progress. Inspect the run, clarify ambiguous acceptance scope when needed and
rerun against current evidence. Existing head and native-open checks still apply.

Scope interpretation and assessment prose are model-derived. Exhaustive source classification, exact citations and
identity validation cannot prove that natural language was interpreted correctly
or that an execution report is true. Review ambiguous scope; neither unknown
verification nor a newly disclosed defect justifies inventing a requirement.

Fact lengths use Unicode code points consistently in the provider schema, local
response validation and progress parser, so supplementary characters share the
same boundary. The evidence and runtime ceilings still count UTF-8 bytes.

If source evidence is missing or any part fails, the Action retains the current progress and reports that it could not assess the revision. A single file, the final aggregate or a comparison exceeding the fixed part budget reports `validation.evidence-too-large` with Retryable: No; inspect the pinned comparison and reported supported capacity. Native multipart recovery continues automatically within its fixed totals; after interruption, rerun the current source for a fresh complete attempt. Retrying identical over-limit evidence cannot add capacity. It also retains state if either head or the issue body changes while the assessment is running. Inspect the run before retrying; an unavailable assessment is not proof of 0% completion.

## Completion after a PR merge

Native issue closure owns completion. Copilot clears obsolete managed active,
waiting, temporary activity and old percentage labels with selective operations.
It retains issue kind, priority, size, branch/SDD history and unrelated labels.
Only a native completed reason permits `100%`; not-planned or unknown closure
removes old progress without asserting completion. No extra timeline comment or
terminal `state:*` label is created.

A repeated merged-PR delivery reconciles already-closed metadata and becomes a
no-op once verified. If the issue was intentionally reopened, the old delivery
stops without reclosing it. Partial errors preserve completed native effects and
report metadata as unverified. Read the run and retry after resolving the cause.
`/copilot status` reads current native state independently of these label writes.


Configured lifecycle names must be distinct from canonical progress labels
(`0%` through `100%`) and protected kind/artifact labels. Invalid configuration
produces no completion metadata writes; keep the native state and correct the
configuration before retrying.


Native duplicate closure is distinct from completed closure: obsolete progress
and activity are removed without adding `100%`. Inconsistent state/reason pairs
stop reconciliation before writes. A reopened issue is never re-closed by an old
merged-PR delivery.

Closed issue events skip open-work branch and SDD preparation. Adding or removing metadata labels after completion preserves the historical `branched` and `SDD` artifacts; reopening produces an open issue event and resumes its normal admission flow.
