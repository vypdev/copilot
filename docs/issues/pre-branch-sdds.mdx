# Pre-branch SDDs

When an existing SDD owns the change, automated drafting adds a proposed change
appendix while preserving the previous contract verbatim. Each appendix is
limited to 18,000 characters and the complete SDD to 70,000. If the document
would exceed that limit, use a companion SDD before branch creation or review
and integrate existing proposals as a normal contributor on the linked branch.
Publication retries keep the validated owner and do not consume another
clarification round. Review the generated specification before implementation.

The numeric test budget may use the canonical template table in section 14.
Each allocation must be a positive integer and the single `Total` must equal
their sum; formatted numbers are supported. Placeholders, inconsistent totals
and fenced examples do not prove a budget. Existing positive numeric prose
remains supported. A malformed existing owner needs contributor review;
regenerating a proposed appendix cannot repair that retained contract.

Newly generated drafts and appendices also need a checkable inventory. They use
these visible tables, with the English column names retained in localized prose:

| Section | Columns | What publication verifies |
|---|---|---|
| 4 | `Requirement`, `Behavior` | Every declared goal has one stable ID |
| 14 | `Area`, `Minimum distinct cases`, `Behaviors/risks covered` | Every area and the total match its distinct cases |
| 14 | `Case ID`, `Area`, `Requirements`, `Scenario` | Fully qualified, unique IDs, exact areas and comma-separated requirement IDs |
| 15 | `Path`, `Change` | `update` and `reference` files exist at the immutable base; `create` explicitly proposes an absent file |
| 17 | `Requirement`, `Cases` | Every requirement names defined cases and the reverse links match |

Tables inside a code fence cannot establish this inventory. A closing fence
must use the same marker with at least the opening length, at most three leading
spaces, and only spaces or tabs after it. A marker followed by text keeps the
example fenced until a valid close or the end of the document. HTML comment
syntax inside the code block is literal and cannot turn that line into a close.

Use a separate case namespace for each proposed change, such as
`identity-development-C01`. Copilot reserves identifiers across **every** SDD
registered to the selected owner, including legacy shorthand inventories. A
new case cannot redefine a baseline case. Use full IDs in references; shorthand
and ranges do not establish new cases. Each case belongs to one budget area.
Equal grand totals cannot hide an over-allocation in one area and a shortage in
another. Generic documentation checks cannot replace defined acceptance cases.

Cite repository files with full repository-relative paths in backticks or
relative Markdown file links. Existing paths are checked against the selected
Git commit, including files outside the catalog evidence arrays. Relative links
may include a URL query and fragment; publication checks their file pathname.
A file present
only in the current checkout does not count. Declare intended new files in the
section 15 table with `create`; ordinary documentation updates must identify
the real existing document. Symlinks, submodules and paths below them cannot
establish file evidence. Source paths remain language and layout neutral.
The selected SDD must appear in this table too: use `create` for a new or
companion SDD, and `update` for an existing one. A self-link or a `reference`
row cannot replace that declaration.

The new tables apply to generated candidates. Existing owner documents remain
verbatim and do not require a table migration to receive an appendix. These
checks establish internal consistency for draft publication. Product,
architecture, security, operator review and runtime acceptance remain separate.

`pre-branch-sdd: true` enables a specification gate for admitted **feature** issues and issues marked `contract-change`. It requires `issue-managed-branches: true` and an agent configuration that can return structured responses. The default is `false`.

The repository must already contain a valid `specs/catalog.json`, `specs/README.md`, and `specs/_template.md`. The catalog identifies the owning SDD. The Action can update that SDD, add a companion SDD to its capability, or create a new proposed capability when the catalog evidence and referenced paths are valid. Drafting receives the selected owner's verified source, test and documentation paths at the immutable base, the canonical issue link and retained authorized answers. A new companion identifies the existing owner; its own new path is proposed evidence. It does not generate PRDs or ADRs in this flow.

## When specification preparation is blocked

A repeated draft validation failure updates one bot-owned **Specification
preparation is blocked** card in the issue. The card names the cause, explains
what remains unchanged, links the workflow run when its runtime identity is
available, and shows a correlation reference. A welcome or recommendation does
not replace this blocking result. No new branch or specification is published
by a failed preparation attempt.

Open **Validation diagnostics** in that card. It shows the closed validation
check and, where available, the affected section, data-row ordinal and expected
or observed counts. For example, a reverse mapping row may expect two cases
while naming only one. An owning-case collision reports a reserved-identity
check and collision count. The card reports the first proven rejection, not an exhaustive audit. Same-size
mapping sets can still disagree on their members; that check reports mismatched
links rather than implying equal counts prove correctness. These are observations from the actual validator;
missing evidence is reported as unavailable rather than guessed.

An illustrative failure view is:

> **Specification preparation is blocked**
>
> No new specification or branch was published by this preparation attempt.
>
> **Action:** Review the safe validation diagnostics below. Clarify requirements
> or decisions in this issue if needed, then retry this same issue workflow.
>
> **Retained state:** Existing answers and published specifications are retained.
>
> **Validation diagnostics:** requirement-mapping; section 17; data row 1;
> expected count 2; observed count 1. The card also includes its run and reference.

The diagnostic feature retains only fixed checks and bounded numeric facts.
It does not publish the rejected Markdown, case/requirement identifiers,
repository paths, scenario prose, source, credentials or raw validator messages.
There is no downloadable candidate or artifact token to retrieve. The current
safe card remains available under the issue's normal repository permissions;
GitHub may retain its prior revisions. A retry replaces its current facts.
Workflow logs follow the repository's existing retention; if a run has expired,
retry this same issue to obtain a fresh bounded attempt and safe diagnostics.

The limits are fixed: at most two drafting attempts per invocation (one shared
eligible size/format repair), eight diagnostic facts, bounded coordinates/counts
and a 16,000-character diagnostic card. The card never truncates a requirement
or turns a rejected draft into acceptance. If localized copy exceeds its card
bound, the complete card falls back to reviewed English with an explicit note.
English/Spanish, compatible base locales, validated dynamic localization and
atomic English fallback follow the repository locale policy. There are no new
configuration options, permissions or artifact scopes.

Retry after correcting the issue's requirements/decisions or the repository
prerequisites identified by the failure. Existing authorized answers, immutable
owners, baseline cases and published SDDs remain. A valid retry clears the
blocked view; branch readiness still requires the independent linked-branch and
publication checks. If a branch/commit already exists and publication recovery
is pending, the card says so and recovery reuses that exact branch. A later
failure to refresh the diagnostic card does not erase a verified publication.
Stale issue/title/base evidence cannot overwrite the current status or recovery
record. Recovery rechecks that evidence before retaining a pending record and
after diagnostic localization. A revision may retain its own returned commit;
an unrelated branch advance requires a new analysis on the same issue. If an
answer-permission lookup temporarily fails, retrying returns the status to
waiting when existing questions are still incomplete. The Action keeps the
original question record and answers and does not start drafting.

## Starting without product implementation

Start with the product documents that can be reviewed truthfully. SDK version 1
accepts `proposed` capabilities with explicitly empty `entrypoints`, `code` and
`tests` arrays. Every field remains required; `specs` and `documentation` must
reference existing files. Every supplied implementation path is also checked for
existence, containment and ownership. Keep prospective SDDs at Draft with their
unresolved decisions and planned acceptance cases clearly identified.

1. Open the repository's enabled documentation Issue Form for the initial
   standard, template, SDDs, documentation and catalog.
2. A maintainer adds `in-progress`; use the exact branch created by the Action.
   An ordinary documentation issue follows its existing admission path.
3. Add `specs/README.md`, `specs/_template.md`, the Draft SDDs, user documentation
   and a version-1 proposed catalog. Generate and validate its catalog index
   using the reviewed SDK, and review the Drafts against the standard/template.
   See [initial catalog generation](/development/specifications#initial-catalog-generation).
4. Review and merge those prerequisites through the normal PR lifecycle. Passing
   structural validation leaves Draft/readiness blockers and proposed status intact.
5. Start the feature issue normally. Its existing clarification, SDD validation,
   immutable evidence and verified branch-publication checks still apply. Add
   real source and meaningful executed tests as implementation proceeds; promote
   the catalog status only with that implementation's review.

For example, before payment implementation exists:

```json
{
  "version": 1,
  "capabilities": [{
    "id": "payments",
    "title": "Payments",
    "status": "proposed",
    "scope": "Prospective payment behavior",
    "owner": "Maintainers",
    "lastVerified": "2026-10-29",
    "specs": ["specs/payments.md"],
    "workflows": [],
    "entrypoints": [],
    "code": [],
    "tests": [],
    "documentation": ["docs/payments.md"]
  }]
}
```

The generated evidence map shows **Not yet implemented (proposed capability).**
for those three empty fields. Its date identifies the reviewed metadata/document
snapshot. Planned test cases remain plans. `implemented`, `as-built-baseline`
and `deprecated` capabilities retain complete evidence requirements. Missing
arrays, nonexistent supplied files and empty specification/documentation fields
still block validation. Restore the required array or provide real files, then
regenerate and retry the same normal workflow.

An older installed SDK may reject this supported proposed state. Obtain the
reviewed version that includes it through the normal SDK/Action upgrade route.
Retain the prospective documents while that upgrade is pending. Keep the
repository's native schema and readiness rules if it uses another profile;
the compatibility recovery below still applies.

## Catalog publication profiles

The installed automatic writer supports the **SDK version-1** catalog profile:
`specs` arrays, the existing required metadata/evidence arrays, and SDK statuses
`as-built-baseline`, `implemented`, `proposed` and `deprecated`. The reader checks
that profile and unique, normalized owner paths before asking the model for a
plan. Full file, SDD and publication checks still run independently.

A repository-native catalog can be valid under its own selected schema and
readiness rules while requiring a different publication adapter. Catalogs using
`specification`, a repository-selected `$schema`, or mixed dialects receive an
explicit compatibility result before model work or branch publication. Preserve
the native schema, requirements, evidence, blockers and readiness; obtain a
reviewed compatible adapter and retry the same issue. Changing statuses or
replacing native standards merely to pass this gate cannot establish readiness.

Compatibility diagnostics show a closed reason and the current workflow, with
retained state and the next action. The Action checks the issue and raw source
revision independently of loading that rejected catalog. Stale or unavailable
source facts keep the workflow blocked and preserve the current status. A custom
older workspace adapter that cannot read this revision remains unverified.

The fixed profile limits are 2,097,152 catalog source characters, 1,000 capability
entries and 20 nested object/array levels for extension metadata. These are not
configuration options. Supported SDK companion/new writes preserve decoded
extension metadata from the immutable original catalog; existing statuses,
requirements, evidence and blockers remain. New SDK entries stay `proposed`.
Profile recognition and diagnostics never establish implementation acceptance.

## Repository layouts and support limits

Catalog version 1 accepts source, entrypoint, test and documentation evidence
at any normalized repository-relative location. Authors declare each file's
role; Copilot does not infer it from a language extension or require `src/`,
`.test.ts`, or a root README. For example:

```json
{
  "entrypoints": ["backend/app/src/main/kotlin/example/Application.kt"],
  "code": ["frontend/apps/console/src/components/Card.svelte"],
  "tests": ["sdks/python/tests/test_client.py", "src/client.spec.ts", "src/client.test.js"],
  "documentation": ["sdks/python/README.md"]
}
```

These are evidence fields within a complete capability entry, not a complete
catalog. Every referenced file must exist. Absolute paths, parent traversal,
backslashes, Windows drive/stream paths, control characters, Git metadata,
symlinks (including parent directories), and directories used as files are
unsupported. Store ordinary files inside the repository and correct the catalog;
do not add fake source wrappers or omit relevant tests. Specifications remain
Markdown under `specs/`; workflow evidence remains YAML under
`.github/workflows/` or `setup/workflows/`. Ownership, SDD structure, numeric test
budgets and the SDD/catalog-only publication allowlist remain enforced.

Catalog discovery rejects unregistered symbolic links anywhere below `specs/`,
including links to directories, dangling links and links whose names look like
excluded files. It does not follow a target to decide whether it contains SDDs.
The ordinary-file exclusions for root `README.md`, `_template.md`, `CATALOG.md`
and non-Markdown files remain supported. Replace a reported link with ordinary
contained files, register any resulting SDD, regenerate and retry. A rejected
generation or validation leaves the existing catalog and targets unchanged;
neither the Action nor the standalone SDK silently treats this tree as complete.

Accepted names with parentheses, spaces, Unicode or Markdown punctuation do not
need renaming. The generated catalog preserves their full paths and literal
labels, with URI-escaped link destinations. Register the original filename,
including any literal percent sign, and regenerate `specs/CATALOG.md` after
updating the shared SDK validator. For example, `specs/foo).md` links to
`./foo%29.md`; source files, capability ownership and readiness stay unchanged.

| Convention | Verified coverage | Execution support |
|---|---|---|
| Kotlin/Gradle, Astro/Svelte JS/TS monorepos, Python SDKs | Metadata paths, nested READMEs, `.spec.ts`, `.test.js` | Toolchains are not executed by catalog validation |
| Java/Maven, .NET, Go, Rust | Representative source/test/documentation fixtures | Full consumer workflows remain untested |
| Other languages and custom roots/extensions | Ordinary contained-file evidence uses the same policy | Unknown until independently verified |
| Linux, macOS, Windows | Shared path policy; platform CI checks the Action | Consumer runtime/framework compatibility requires separate verification |

Before enabling the gate, prepare the three prerequisite files and run
`copilot doctor` with the intended `pre-branch-sdd` configuration. The local
`workspace.sdd-prerequisites` check uses Copilot's bundled catalog validator.
Prerequisite structure is checked outside fenced examples and HTML comments:
the standard needs the canonical eight numbered sections with content and
the canonical rule “A MUST requires an acceptance scenario.” in section prose,
with optional inline emphasis/code formatting. A keyword in a title, heading,
introduction or example is insufficient. The template needs all twenty numbered sections with
content and the exact canonical heading prefixes used by the draft validator.
A title-only document, missing section or fenced copy cannot establish readiness.
Keep the canonical structure when adapting these documents to your repository.
A failure directs you to repair the catalog/standard/template; an unreadable
inspection reports unverified, never ready. `/copilot doctor` also checks the
catalog paths against the selected immutable Git tree's regular-file inventory.
Neither diagnostic certifies framework tooling or published SDD readiness.

Upgrade the Action and local CLI together. Existing version-1 catalogs and the
`pre-branch-sdd: false` default need no schema or configuration migration. The
updated policy applies at the next validation, including in-flight drafts and
branch synchronization; it does not rewrite historical SDD commits. Repositories
using symlink evidence must register real contained files before retrying the
same issue. A consumer-supplied validator cannot replace the Action's bundled
validation policy.

## Issue flow

1. Open an admitted issue with a feature type or `contract-change`, then add `in-progress`.
2. The Action adds `SDD`, analyzes the issue against the catalog, and posts one **SDD work status** comment. If it finds blocking questions, it waits in `state:specifying` without drafting a document or creating a branch.
3. Answer each question in an issue comment using `SDD Q1: your answer`, `SDD Q2: your answer`, and so on. The issue author answers questions assigned to the author; a repository member answers maintainer questions. A comment can answer several numbered questions. The Action ignores answers from other accounts.
4. When all questions are answered, the Action analyzes the answers again. It may ask another bounded round of questions. Once the contract is clear, it drafts and validates the SDD in an isolated temporary worktree.
5. The Action creates the linked issue branch, commits only the validated SDD and any required catalog files, pushes the commit, and verifies the exact remote branch. It updates the status comment, adds `branched`, and moves to `state:working`.

The status comment uses the effective issue locale (Spanish and English are bundled, with English fallback). It shows the owning SDD, each question and its owner, the retained branch if one exists, and the verified commit. The first branch commit contains the SDD; implementation starts afterward.

The Action validates the SDD itself and publishes its commit without running contributor Git hooks from the runner checkout. Your hook configuration is preserved for normal contributor commits.

## Edits, retries, and revisions

If the issue body, human title, or source branch changes while an SDD is being prepared, the Action reanalyzes or blocks publication so it cannot publish a stale contract. A duplicate event reuses the status comment and branch. A push that succeeded before the comment update can be recovered from the same remote branch.

If the branch was created but the first SDD commit could not be published, the status comment retains that exact branch and keeps implementation blocked. A retry uses its original base, even if `develop` has advanced. The Action rejects a branch containing implementation commits before the first SDD commit. Updates to the Action's hidden issue configuration do not invalidate the human specification answers.

If the issue materially changes after publication, the Action retains the linked branch and its first commit, removes `branched` while the revision is pending, clarifies the changed contract, and publishes a validated SDD revision on that branch. `branched` returns only after the remote revision is verified. Resolve a blocked status on the existing issue and rerun its workflow; a new branch is not needed.

## Configuration example

```yaml
- uses: vypdev/copilot@v3
  with:
    token: ${{ secrets.PAT }}
    issue-managed-branches: true
    pre-branch-sdd: true
    development-branch: develop
```

See [Branch management](/issues/branch-management) for the standard flow and [Specifications](/development/specifications) for the catalog format.

Opening a PR replaces GitHub's direct issue-to-branch connection with its issue-to-PR connection. Copilot retains branch readiness by verifying that the associated open PR belongs to this repository and its exact head name and commit still match the live remote branch. Closed PRs, forks and missing or stale heads cannot establish readiness.

Automatic updates retain the owning SDD from its original Git commit, including when Windows converts checkout line endings.

### Ownership analysis recovery

If the analysis proposes an unknown companion owner or a path already registered
in the catalog, Copilot blocks before drafting and publishes an editable **SDD
work status: analysis blocked** card. The card identifies a closed failure
category without exposing the model's proposed values or raw response.

Clarify the existing capability ID and intended SDD path in the same issue, then
rerun the original workflow. Updates use a path registered to that owner;
companions use an existing owner and a new path; new capabilities use a new ID
and path. Each invocation makes one analysis attempt with no automatic repair.
Existing answers, SDDs, branches and commits remain intact. A later valid analysis
updates the diagnostic; normal publication checks still determine readiness.
The diagnostic is separate from the validated question/publication record and
cannot authorize a branch or `branched` label.

### Draft validation recovery

Drafting aims for a complete compact document: about 6,000 characters for an
update appendix or 10,000 for a new/companion SDD. These targets leave room for
the provider to complete its structured response; they do not remove resolved
requirements or change the acceptance limits below. Codex receives a compatible
closed JSON shape; Copilot enforces the complete original string-length schema
locally before any document reaches the writer.

The provider writes the requirements and explicit case inventory once. Copilot
calculates the final area counts, total and reciprocal requirement links before
validating the document. Every resolved acceptance minimum and scenario must
remain in the inventory; the compact target is advisory, and the hard character
limit also applies after the calculated tables are inserted.

Assembly never changes case IDs, scenarios, requirement edges, supplied tables
or paths to make a contradiction pass. Malformed definitions, colliding IDs,
uncovered requirements and invalid paths still block publication. Existing
complete drafts retain their bytes and checks. Structural consistency does not
establish completeness or runtime acceptance; human review remains required.

Copilot limits proposed update appendices to 18,000 characters and complete new
or companion specifications to 70,000. If a generated draft exceeds its limit,
it tries one concise regeneration for the same owner and answers. Missing
required sections or a numeric test budget can use that same single attempt.
Case identity, per-area case budgets, requirement mappings and repository paths
share that attempt too. A repeated failure gives a specific recovery message:
choose distinct full IDs, reconcile each area's cases, repair both directions
of the mappings, or correct the paths and explicitly proposed files. No further
generation or publication occurs in that run. Review the named contract and
retry the same issue workflow; answered questions and historical commits remain.
Proposed files must also be compatible with one another: a file cannot be the
parent directory of another proposed file, in either declaration order or at
any nesting depth. Sibling files and distinct pathname prefixes remain valid.
All validation and freshness checks still apply. If the second draft still fails,
no draft is published; existing answers and SDDs are retained. Retry with a proportional
change or an approved companion specification.

If the Action log reports `reported-output-token-limit`, the provider stopped
before completing its response. No draft or branch is published for that failed
generation, and the answered plan is retained. Update Copilot to use the compact
targets and native-schema compatibility, then rerun the same issue workflow. If it still fails, review concise
coverage of the resolved scope before another run. This is a different limit
from a request timeout or a GitHub permission failure; the Action does not
silently change models, credentials, native JSON shape or hard document limits.

### Additional clarification rounds

The question card shows its current round. Reply to each new round in a new
comment, even when a question reuses an ID such as Q1. Copilot retains earlier
decisions with their question and round, but those answers do not satisfy a new
question automatically. A changed issue or development base starts clarification
again. Keep answers concise; the retained history has fixed size limits and is
never silently truncated. Copilot may ask up to three sets of questions;
answering the third set can complete preparation without starting another round.

## Inspect readiness with status

Run `/copilot status` in the issue to see whether the SDD is required, which
question IDs still need authorized answers, and whether publication is pending
or verified. A ready result links the owning specification at its verified
first or current revision commit. The SDD-card link returns you to the existing
clarification flow.

Status reads current GitHub facts and immutable publication evidence. It
preserves the issue, labels, branch and SDD. Missing or partial access reports
unavailable; a corrupted card, changed issue or racing branch cannot produce a
ready result. A newer invalid owned card never restores an older ready state.
Answers from older rounds without matching question provenance remain pending.
Help issues remain branchless and do not require an SDD.


## Compare the first and current publication

Use `/copilot sdd-diff` in the issue to inspect a bounded structural comparison
of the first and current verified SDD. A reply shows immutable document and
commit links, exact added/removed line counts and up to eight escaped changed
section titles. It does not quote document contents or decide whether semantic
requirements changed. The commit comparison may show other files; the command's
counts concern only the owning SDD.

Only a first publication means there is no revision pair. Pending clarifications
or stale issue evidence withhold current counts and return you to the existing
SDD card. Invalid or unavailable authority cannot certify a comparison. Repeating
the same source comment refreshes one reply; it never regenerates the SDD or
changes the branch. See [comment commands](./comment-commands.mdx) for exact PR
link rules, fixed limits and the English/Spanish fallback contract.


## Reopening after a merged PR

Reopening an issue does not reopen its merged PR or restore GitHub's direct
issue-to-branch connection. If that connection is absent, the retained branch
needs a new open, same-repository PR linked to the issue before Copilot can
verify current SDD readiness. A retained branch name and its historical SDD
commits alone cannot establish that live relationship.

For follow-up work, contribute a normal commit on the existing Action-managed
branch and open a follow-up PR linked to the same issue. Let the Action finish
linking it, then rerun the failed issue workflow and `/copilot sdd-diff`. The PR
head name and commit must match the live remote branch; the original verified
first and revision SDD commits remain immutable. Keep branch synchronization
with the Action's `/copilot sync-branch` command.

If there is no follow-up work, leave the issue completed and use its immutable
historical SDD links. A closed issue without `in-progress` reports that a current
comparison is not applicable. Do not treat an unavailable relationship as proof
that the saved SDD documents were lost.
