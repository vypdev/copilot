# Self-hosted runners

A self-hosted runner that can access agent credentials MUST be dedicated or isolated from unrelated workloads. Operators MUST:

- restrict repository and organization access;
- prevent untrusted fork jobs from selecting the runner;
- patch the operating system and CLIs;
- remove workspaces and transient logs after runs;
- restrict outbound network access where feasible;
- audit runner labels and permissions;
- keep local session files outside repository workspaces.

The compact Copilot comment callbacks require GitHub Actions runner **2.336.0+**
and platform support for self-repository references. Their reusable coordinator
keeps the Action on the called workflow's exact commit. Setup retains self-hosted
labels and groups in the call's `with.runs-on` JSON; it does not change group
access or prove capacity. See [comment workflow upgrades](/security-operations/operations/upgrade-rollback#upgrade-an-existing-copilot-repository).

A shared persistent runner is not equivalent to an ephemeral trusted runner.

The platform smoke jobs use the local pnpm store and disable automatic
dependency-cache backup. Each platform installs pnpm in its own job directory.
See the [setup-node cache inputs](https://github.com/actions/setup-node#usage).

In `vypdev/copilot`, `CI Check` uses the `vypdev` runner group with
`self-hosted`, `codex` and `Linux` labels. It runs for same-repository PRs,
pushes to `master` and manual dispatches. Static checks, package build and
smoke, and tests with coverage can occupy three runners at once. Each uses its
own checkout and the runner's local pnpm store. The required `CI Check` job
then records all three conclusions without checking out code. Every job
excludes fork PRs before runner assignment. The source repository has no
active merge queue. Restore a compatible required check on a suitably isolated runner
before enabling a queue.

Run the setup fixture matrix manually from protected `master`. It exercises
Ubuntu, Windows and macOS on self-hosted runners, using Windows services
without the `codex` label. A Linux runner needs the Firefox ESR system
libraries preinstalled. The workflow checks the pinned Firefox binary without
installing system packages. Windows coverage is preserved as a short-lived
artifact and exported only with `upload_windows_coverage=true`. The separate
Codex service smoke remains Ubuntu-only until macOS capacity is restored.
A queued or skipped platform job is unverified.

The only GitHub-hosted jobs in this repository are issue-event admission and
release/hotfix npm publication. [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/#supported-cicd-providers)
requires a GitHub-hosted runner for OIDC. Deployment preflight and credential
health use the self-hosted Linux pool. Setup templates retain their consumer
defaults and accept runner choices from each project.

RepoWise obtains a complete Python 3.12 distribution via
`actions/setup-python`, creates its virtual environment and reports in
run-specific temporary directories, and removes them after artifact upload.
Its runner needs a writable Actions tool cache and GNU `/usr/bin/time` for phase
RSS evidence. The isolated Python suite verifies the pinned history adapter before
analysis; phase time/virtual-memory caps and a 40-minute job bound the run.
The workflow does not install
Ubuntu system packages. RepoWise runs only through manual dispatch on
`[self-hosted, codex, Linux]`, using the reviewed repository ref selected by the
maintainer. It is optional and must not be required by branch protections or
rulesets. It no longer consumes this pool on every PR or push. See
[testing and manual analysis](/development/testing) for launch instructions,
revision evidence, scan limits, artifacts, and retry behavior.

The `[self-hosted, codex]` pool routes agent jobs to macOS and Ubuntu. Windows
services MUST omit `codex` on registration; recreate existing registrations to
remove it. The four Windows services remain available for other jobs. Install
Git and Bash on runners selected by the installed Bash workflows. Distributed
agent workflows use the embedded Action Node; development and packaging jobs
keep their own toolchain.

**Codex no soportado en runners Windows ejecutados como servicio.** The
session-0 service limitation does not claim that interactive Windows fails.
Do not deploy a patched CLI, disable its sandbox, or require interactive login
as recovery. See [Codex runtime support](/agents/codex-openai).

The JavaScript Action runs under the runner's embedded Node. Missing agent CLIs and confirmed newer official releases use standalone installers and release archives in private job directories. Self-update commands are not run against installed CLIs. Existing npm `.cmd` shims on Windows still need a separately trusted Node executable; native installed CLIs do not.
Verify each operating system with an actual runner job before
claiming Action-wide compatibility; the platform matrix exercises isolated
setup and agent fixture paths. In particular, inspect timeout and cancellation of
agent child processes on Windows separately from POSIX process-group behavior.

The Action passes agent children an allowlisted runtime environment plus only the credential selected for that provider; unrelated GitHub, cloud, database, and PAT variables are not inherited. Codex review capabilities are forced to `--sandbox read-only --ignore-user-config --ignore-rules`; fixer capabilities use `workspace-write`, with network and extra writable roots disabled. Cursor receives a per-invocation configuration/home with sandboxing and default-deny network policy. OpenCode receives a pure, inline default-deny permission profile with shell, task, skill, web, and external-directory tools disabled. Dangerous bypass flags are rejected for every runtime. These controls complement rather than replace runner/container isolation.

Configured verification commands also receive a temporary `HOME` and credential-free allowlisted environment. They are repository processes, not model tools, so the runner must still prevent them from reading unrelated host paths through OS-level isolation.

Timeout and cancellation terminate the complete POSIX process group, with a bounded graceful period before a forced kill, so abandoned CLI descendants do not occupy the runner indefinitely.

Windows PowerShell 5.1 can spend the first invocation discovering cmdlet modules
inside a fresh isolated profile. Bounded native shell fixtures explicitly import
the absolute system `Microsoft.PowerShell.Utility.psd1` manifest before hashing.
Their timeout stays unchanged. This avoids depending on a host's warm module
cache and keeps the runtime's private profile and checkout-cleanliness checks.
A runner-disconnection annotation is an infrastructure failure; passing tests on
another platform does not turn that job into a successful smoke run.

The manual `Copilot - Runner diagnostics` workflow retains only its Linux
Codex prerequisite job. General Windows PowerShell startup diagnostics and
platform fixtures remain separate and do not invoke real Codex. CLI or
model success is distinct from a verified tool read, edit, or command. A model
reply and a setup marker cannot certify sandbox tools. No new Windows-service
Codex acceptance run is required or scheduled.
