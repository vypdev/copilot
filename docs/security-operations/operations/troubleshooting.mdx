# Troubleshooting

For setup runner selection, use the named state to choose the next action:

| State | Meaning and next action |
|---|---|
| Access unverified | Inventory is unavailable/incomplete, a group is workflow-restricted, or the exact route is unobserved. Ask an organization administrator to verify repository and workflow access, or enter a known manual profile. Selection never grants access. |
| Capacity pending | Matching authorized runners were observed busy/offline. Keep the route, check the runner service and refresh setup/readiness when capacity returns. No hosted fallback occurs. |
| Unavailable | A confirmed eligible group has no runner matching all labels. Correct the exact group/labels or restore the intended runner, then review again. |
| Incompatible generator | Retain the asset or restore a compatible generator/snapshot. Do not replace source guidance or native release/CI jobs with consumer templates. |
| Registry changed | Setup stopped before probes/writes. Restart profile review against the current effective registry; preserve existing installer PRs and receipts. |

Runner availability does not prove Codex authentication or runtime tools. Merge
the reviewed installation PR through the normal process, then run the appropriate
provisioning/credential checks and actual trusted workflow. See
[runner profiles](/configuration#runner-profiles) for schema, limits and snapshots.

If guarded PR approval is missing, run `copilot doctor` and inspect the ordered `approval.*` checks. A missing `PR_APPROVAL_POLICY` is safely off; a copied observer that has not reached the default branch cannot receive `workflow_run` wakeups. Correct the named CI producer, Bugbot completeness, runtime PAT, or stale-dismissal rule, then manually dispatch **Copilot - Pull Request Approval** with the PR number. An ambiguous review POST is read-first on retry; never blindly submit a second approval. See [guarded approval](/pull-requests/guarded-approval).

This guide helps you resolve common issues you might encounter while using Copilot. Expand the section that matches your problem.

If the guided setup PAT belongs to the wrong account, decline the account
confirmation, delete the unintended PAT in [GitHub PAT Settings](https://github.com/settings/personal-access-tokens),
and rerun setup in the correct browser account. If the final permission table
requires more than the reviewed local-intent link, inspect the named grant
delta, use the corrected link printed by setup, and rerun; no approved setup
mutation has started. If the final plan removes grants, your existing PAT may
have excess access; replace it for strict least privilege. A guided bot PAT
created while signed into another account fails the numeric-ID check before
the Secret is written. The message identifies both accounts. Choose **Enter
another bot PAT** to keep your answers, approved plan and selected bot in this
session, or **Stop setup** to end it. Delete that unused PAT and create one as
the chosen bot, using a private window or switching GitHub accounts. Re-entry
verifies the new token's numeric identity and required grants; it does not retry
provider failures or permission checks automatically. Closing the session still
requires a fresh setup run.
If setup fails after applying changes, inspect the Actions Secret name and
scope before revoking or replacing the bot PAT: it may already be active.
Cancelling setup never revokes either PAT. Delete an unused setup PAT in GitHub;
renew an installed bot PAT before its suggested 90-day expiry.

If setup reports that repository Secret `PAT` shadows the selected organization
PAT, open the linked repository Actions Secrets settings. Remove the repository
Secret in GitHub and select **I have deleted the repository PAT — check again**.
The button requests a fresh read; a still-present PAT returns to the same choice.
An unavailable read never means deletion succeeded: check setup-PAT access or
GitHub availability and retry. Your answers remain in this session. **Store PAT
in the repository instead** changes only PAT storage and requires a rebuilt plan;
**Stop setup** ends the run without a setup Secret write. Copilot never performs
that deletion and cannot restore a value you removed manually. The new bot PAT
must still pass every required check before any replacement. Organization PAT
replacements can affect other repositories, including when the old Secret was
not available to this repository; read the shared-impact notice before approval.

For `copilot setup --web`, an inaccessible page or failed browser launch does
not imply a setup failure: open the exact `127.0.0.1` URL printed by the CLI.
Enter the terminal's 16-character pairing code in the page; after a refresh,
enter it again. Do not share the code. TCP loopback can be reached by other
local OS users; the code, not the public URL or OS-user identification, grants
access to this setup session. After five wrong codes, pairing and takeover
pause for 30 seconds; wait, then retry the code printed by the launcher.
If the local bind or bundled assets fail, stop and use `copilot setup` in the
terminal. A second browser tab is read-only until you select **Take control
in this tab**; the former tab then cannot submit decisions. A rejected stale
answer means the page should refresh to the current decision, not replay it.
If the page closes during Apply, reopen it and pair with the launching
terminal's code while that process is alive. The per-resource progress view
shows completed, skipped, in-progress, and uncertain operations. If the
process exits during a write, treat its result as needing inspection: check
the local checkout and corresponding GitHub resource names/scopes, then run
`copilot doctor --read-only` with a valid setup PAT before retrying. The
previous approval and secrets are not restored by a new process. Completed
local or remote writes are not rolled back. No local session shutdown revokes
a PAT in GitHub.

Ctrl+C releases the exiting setup process's own session lock when delivered
as a Node console signal; SIGTERM does the same on macOS and Linux.
An abrupt crash, forceful termination or older version can leave an orphaned
lock. Startup reports the owner's PID and exact path in the terminal, rather
than replacing that actionable local diagnostic with `Setup failed`.
If setup reports a lock belonging to a stopped process, it will not delete
that lock automatically: another setup could have acquired the same path in
the meantime. Verify that no setup process for this checkout is running,
then remove **only the exact lock file path printed in the error** and retry.
Never remove a lock for an active process or clear the entire temporary
directory. The lock contains no PAT or other credential.

    setup confirmed the token identity and repository selection. Grant the named
    repository or organization permission to the correct resource owner, ensure
    the repository is included in the fine-grained PAT selection, and rerun
    setup. The dependent mutation has not started.

    A conditional repository Secret or Variable row may be missing before the
    setup choices are final. In that case inventory is shown as unavailable,
    not as an empty list. Setup may continue to the plan, but it stops before
    credential choices, resource targeting, or mutation if a selected resource

    response leaves the permission merely unverifiable. If every selected resource is forced to
    organization scope, including an organization default with
    `preserveExisting: false`, setup uses the available organization inventory
    and does not block on unrelated repository inventory.

    completed temporary transaction for the requested write level, returned an ambiguous
    `403`/`404` (including the generic message `Forbidden`), reported SSO
    enforcement, or had a transient/rate-limit failure. A `403` becomes
    `Missing` only when bounded provider metadata explicitly identifies a
    permission denial without rate-limit, retry, or SSO headers.
    Malformed provider JSON, unreadable response headers, or a response body
    that stalls until the probe deadline also remain `Unverifiable`.
    A successful public read is also not token evidence: public repository
    metadata, commits, labels, workflows, checks, pull requests, and

    the read-only commit list; this is not the workflow-presence check described
    below. GitHub's documented empty-repository response verifies read access
    only for a metadata-proven private repository; on a public repository it
    remains inconclusive and never proves write access. A `404` is still
    ambiguous because it can also mean the token cannot see the repository, so
    setup never upgrades it to `Verified`.
    A required unverifiable read without positive public-repository operational
    evidence blocks and must be retried. Required writes are checked by creating,
    reading and deleting a temporary resource for each permission. Guided links
    prefill possible health-write grants when managing Secrets, but their tests
    wait until the approved plan needs them. Manual and supplied-token paths
    also test displayed conditional writes during initial PAT verification. Inspect the failed phase and HTTP category. An unresolved
    cleanup blocks retries until the recovery journal can finish it. The old
    `--confirm-unverifiable-write-permissions` flag is rejected.
    In the web assistant, inspect only required rows marked `Unverifiable`;
    a `Verified` organization Projects read row already passed. Public
    repository reads say `Read available` when setup can use them without
    proving the PAT grant. The browser explains each status beside its row.

    When required repository or organization inventory validation fails after
    the questionnaire, the wizard returns a structured inventory block before
    plan approval or further configured permission tests. The CLI then
    handles the structured block immediately and exits with the bounded inventory
    error without starting another audit or inventory validator. It does not run
    plan confirmation,
    credential prompts, workflow comparison, resource targeting, or mutation.
    If the later provisioning inspection itself fails or its read port is
    unavailable, setup stops before copying local setup files or provisioning
    Secrets, Variables, labels, issue types, and tags, even for a
    repository-scope default. Restore inventory access
    and rerun setup; an absent snapshot is never treated as an empty repository.

    If PAT transactions pass but Plan reports organization Secrets or Variables
    as unavailable, the failure is a separate inventory read. Upgrade the local
    installation and restart the session: older adapters used incompatible SDK
    methods or repository parameters for these inventories. A valid PAT does
    not make that adapter error a missing grant. If the problem persists, check
    the selected scopes, repository selection, organization policy, and the
    named inventory errors in the terminal; setup must preserve unknown
    inventory rather than treating it as empty.

    A Secret collision keeps a version-two incident marker under
    `~/.copilot/setup-permission-probes/`. Review the GitHub audit trail and
    reconcile the potentially replaced value before removing that marker
    manually; retries never delete the unknown Secret. Older releases reject
    new journal records, so complete recovery before rolling back. A legacy
    Actions record lacking its workflow ID blocks automatic recovery before
    any GitHub request. Open the matching journal and inspect its repository,
    temporary branch, recorded commit, and optional run ID. In GitHub Actions,
    identify the exact `workflow_dispatch` run on that branch; cancel it if
    active and delete it only after verifying its ownership. Delete the branch
    only after verifying its recorded commit. If the run or branch is already
    absent, confirm that independently. Remove only that matching journal file
    after GitHub cleanup is confirmed, then retry setup. Never delete the whole
    journal directory to bypass a pending resource.

    If cleanup reports that a temporary branch changed, inspect its exact ref
    and the local journal before deleting it manually. Copilot refuses to delete
    an advanced commit or a legacy ref without a recorded commit. Retry only
    after the matching cleanup is complete. If the workflow PAT can update some
    Projects but cannot update a selected one, grant that account access to the
    named Project; an organization permission alone is insufficient. See the
    [audit prerequisites](/authentication) for Issue deletion, temporary PR
    branches, and no-job Actions checks.

    Permission probes use a fixed maximum concurrency of four and preserve the
    table's requirement order. A large permission plan therefore does not launch
    every GitHub request simultaneously.

    A Secret check uses GitHub's create-or-update API, which has no atomic
    create-only mode. Copilot uses a private random name and checks that it is
    absent before writing. If GitHub responds that it updated a Secret, stop:
    the check is not verified and Copilot will not delete that Secret. Inspect
    the GitHub Secret audit trail before retrying; a concurrent value may have
    been replaced.

    A credential-health Actions write check needs Contents write to create and
    remove its isolated branch, even when the health workflow is `installed`.
    An installed workflow omits Workflows write. Only confirmed `missing` adds
    Workflows write to install and remove a temporary workflow on that branch.
    `unavailable` or `unknown` never authorizes bootstrap; correct
    Actions/Contents access or a transient provider failure and rerun. An HTTP
    403 while creating the branch identifies Contents write as the prerequisite
    that failed; it does not prove whether Actions write is present.

    An Actions API `404` alone does not prove that the credential-health
    workflow is absent because GitHub can hide inaccessible workflows that way.
    Setup reports `missing` only after an independent Contents request to the
    repository root (`path: ''`) first proves repository visibility and a
    subsequent lookup of
    `.github/workflows/copilot_credential_health.yml` returns `404`. The
    root response must be a directory listing array (possibly empty) with
    named entries; a successful response with malformed root data is not
    visibility proof. A readable file, unavailable Contents endpoint, failed
    visibility proof, denied exact
    lookup, or transient failure reports `unavailable` and skips temporary
    workflow creation. Existing credential health remains unverified.
    The preliminary inspection may reflect GitHub's default branch; after you
    select the main branch, setup checks the repository root and exact file on
    that selected ref before auditing the final PAT permissions. An inaccessible
    selected ref is `unavailable`, not an inherited default-branch state.
    An exact-file response without a usable file `sha` is also `unavailable`,
    even if GitHub returns success; it never proves installation.
    A valid file `sha` proves installation on the selected ref, but dispatch
    also needs a workflow definition on GitHub's default branch. Setup accepts
    the Actions index or, after its `404`, exact Contents proof on that branch.
    If the file exists only on the selected ref, setup leaves health
    unavailable and does not dispatch or create a temporary workflow. A
    missing selected-ref file may be bootstrapped only with a default-branch
    definition already present or by installing it on the default branch.
    If another actor creates or changes the temporary workflow, setup does not
    overwrite or remove that actor's file; inspect the selected branch before
    retrying a reported cleanup failure.
    Terminal setup marks the run partial as soon as it attempts a temporary
    credential-health workflow create, even if the request fails ambiguously or
    the file is later removed. Inspect the selected branch and GitHub workflow
    history before retrying: the create/delete commits remain in history.
    Browser setup never performs this bootstrap before final Apply.

    If the final PAT audit says GitHub could not verify the repository owner
    type, do not treat the earlier guided owner selection as proof. Confirm the
    repository owner in GitHub, restore API access, and retry setup. No local
    provisioning or bot Secret write should begin from that blocked audit.
    Expected missing or unconfirmed final PAT permissions return a blocked
    result with the chosen configuration and stop before storage validation or
    setup application. Initial PAT verification can already create
    temporary GitHub resources. If a row says cleanup is pending, retain the
    local recovery journal and retry only after its exact resource is cleaned;
    cancellation or expiration during unconfirmed cleanup is a partial result.

    If an existing `PAT` passes credential health but setup asks for it again,
    this is intentional: GitHub never returns a Secret value, and remote health
    proves only bounded runtime reachability. Re-enter the workflow PAT so setup
    can run and display the complete permission audit. For unattended setup,
    supply `PAT` explicitly; without it setup fails before any resource write.

    If identity itself is invalid, confirm token expiration, resource owner, and
    selected repository before changing individual permissions. Never paste the
    token into an issue, log, screenshot, or troubleshooting comment.

    **Symptoms:**
    - Error messages during branch creation
    - Branches not being created automatically
    - Permission denied errors

    **Solutions:**
    1. **Token permissions:** Ensure the `token` (PAT) has repo and project access; check token scope and validity.
    2. **Label configuration:** Confirm labels exist in the repository, verify label names match your config, and check that label triggers are firing.
    3. **Branch names:** Ensure branch names are valid, check for naming conflicts, and verify branch prefix configuration (e.g. `feature-tree`, `bugfix-tree`).
  </Accordion>

  <Accordion title="Project linking problems" icon="table-cells-large">
    **Symptoms:**
    - Issues not appearing in projects
    - PRs not being linked automatically
    - Project automation not working

    **Solutions:**
    1. **Project configuration:** Use `project-ids` (comma-separated project IDs), not URLs. Ensure projects exist and the token has access. For org projects, verify organization project permissions.
    2. **Token scope:** Confirm project access permissions, verify organization access if needed, and check token expiration.
    3. **Visibility:** Check project visibility settings and ensure the bot has access.
  </Accordion>

  <Accordion title="PR-to-issue linking is partial or interrupted" icon="code-pull-request">
    Copilot may briefly add a closing reference and target the default branch so
    GitHub can register the issue link. It normally restores the exact original
    description and base before the run finishes.

    1. If the result says both originals were restored, rerun the failed GitHub
       Actions run so it uses the original event snapshot.
    2. If it names a retained temporary default base, change the PR base back to
       the original branch shown by the result.
    3. If it names a retained temporary issue reference, remove only the trailing
       Copilot pending marker and its adjacent temporary `Resolves #…` line.
       Preserve all other author content.
    4. Rerun the failed run after the manual repair. Copilot recognizes its exact pending marker
       first and will not layer another temporary reference.

    Never paste a token or raw provider response into an issue. If inspection
    itself failed, verify Pull Requests read/write permission and that the PR
    number belongs to the configured repository.
  </Accordion>

  <Accordion title="Branch sync or automated fixes cannot find Java or another runtime" icon="code">
    A separate application's CI setup does not prepare the job handling the
    Copilot command. Check that job's steps, including for `sync-branch --no-agent`.
    Provision Java, Node, pnpm or other project tools there before Copilot and
    commit a reviewed `.copilot/verification-prerequisites.json` to check their
    versions. The declaration is optional: older installations without it still
    run the configured verification directly and may report only its generic
    command failure.

    If a declared prerequisite fails, Copilot does not execute the repository
    verification command or publish its change. Branch sync aborts its prepared
    merge; remote branches stay unchanged. Correct the bootstrap or version
    declaration, then retry the original operation. Do not remove verification
    to force a push. Follow the
    [same-job example and environment contract](/security-operations/operations/verification#repository-verification-prerequisites).
  </Accordion>

  <Accordion title="Workflow timeouts or execution issues" icon="clock">
    **Symptoms:**
    - Workflows timing out
    - Long execution times
    - Failed workflow runs

    **Solutions:**
    The hosted Windows verification-environment fixture reports a fixed
    `verification-powershell` stage with the child status and error code when
    its real PowerShell command fails. Use that evidence to distinguish command
    failure from a timeout; `exit 2` alone does not identify a cause. This
    literal-argv fixture also retries only the removal of its own temporary
    root up to five times when the filesystem reports a retryable error; an
    exhausted cleanup still fails the test. The PowerShell
    fixture imports the trusted system hash/path modules explicitly and keeps
    the existing execution deadlines. Its success certifies the fixture only,
    and does not certify real Codex tools in Windows services.

    1. **Timeouts:** Identify the phase before changing a job timeout. A pending
       promotion, environment approval, merge queue, or reconciliation PR is an
       external GitHub wait and has no release runner to extend. npm visibility
       has its own bounded polling interval and timeout.
    2. **Network:** Check GitHub API status, verify network access, and monitor rate limits.
    3. **Triggers:** Verify event triggers, workflow conditions, and concurrent executions. A newer run may intentionally cancel an older run from the same workflow, but a Commit run and its paired Pull Request run must not cancel one another. When an open same-repository PR exists, Commit must skip Bugbot and `pull_request:synchronize` must own review for that head. The supplied PR workflow must not subscribe to metadata-only `pull_request: edited`; if an automatic description update starts another PR run, update the workflow template. Run names must expose event/action and review-state events must have their own check identity. The dedicated merge-group workflow must retain the same `Copilot - Pull Request` context so required checks continue to resolve without a skipped duplicate in normal PR runs. If event owners cross-cancel, both run Bugbot for one head, append lifecycle/debug-only comments, or a newer ambiguous Check says `Bugbot review: —`, update the shipped workflows and Action before trusting the result. Bounded partial, skipped, and superseded reviews should be neutral, not successful.
  </Accordion>

  <Accordion title="Release or hotfix orchestration stops" icon="rocket">
    **Start with the launcher issue control center**, which distinguishes an
    external wait from a failed runner:

    1. **No continuation after a PR merge:** Confirm
       `copilot_deployment_orchestration.yml` existed on the default/base branch
       before the PR closed. Confirm the PR body still contains Copilot's managed
       marker and that it was created with the workflow PAT rather than
       `GITHUB_TOKEN`.
    2. **Promotion pending:** Open the linked production PR and let GitHub own
       required checks, reviews, auto-merge, or merge queue. Do not increase
       the pull-request checks and do not publish manually.
    3. **Merge-queue readiness is `unknown` or `unsupported`:** Run
       `copilot doctor --config <setup.yml>`. For a GitHub Actions producer,
       make its literal required job handle `merge_group: checks_requested` on
       the target and candidate refs. For third-party CI, configure
       `gh-readonly-queue/<base>` support and add an exact reviewed
       `(context, integrationId, targets)` attestation only when Copilot cannot
       inspect it. A known missing trigger cannot be attested away. A 403 means
       the PAT needs Metadata and classic branch-protection Administration read.
    4. **npm `ENEEDAUTH`:** Verify both npm Trusted Publisher records use the
       exact organization, repository, workflow filename, and `npm` Environment;
       ensure **Allowed actions** permits direct `npm publish`, the job runs on
       `ubuntu-latest`, and it has `id-token: write`. `npm whoami` is not an OIDC
       preflight.
    5. **npm visibility timeout:** `NPM_VISIBILITY_POLL_INTERVAL_SECONDS` accepts
       10–60 seconds and defaults to 20;
       `NPM_VISIBILITY_TIMEOUT_SECONDS` accepts 60–900 seconds and defaults to
       600 (10 minutes). npm can accept a publication while its validation is
       still pending; the workflow bounds every lookup by the remaining
       window and rejects responses arriving after the deadline. Rerunning `publish`
       with the same operation ID verifies and reuses an
       already-visible exact version.
    6. **Reconciliation pending:** The package is already public. Complete or
       correct the linked reconciliation PR; never increment or republish the
       version to solve this phase.
    7. **Immutable tag conflict:** Stop and inspect the reported SHAs. Copilot
       never moves an existing version tag that points at another commit.

    See [Release and hotfix orchestration](/issues/deployment-orchestration) for
    preflight, state, configuration, and recovery details.
  </Accordion>

  <Accordion title="Action skips issue/PR/push pipelines" icon="user-slash" defaultOpen={true}>
    **Symptoms:**
    - The workflow completes quickly but nothing happens (no queue wait, branches, project linking, or comments).
    - Logs say something like "User from token (...) matches actor. Ignoring."

    **Cause:** At the start of the GitHub Action, when the **event actor** (the user who triggered the event: e.g. who opened the issue, who pushed, who opened the PR) is the **same** as the user who owns the PAT (`token`), the action completes successfully before waiting for previous runs or entering the normal issue, PR, and push pipelines. It will still run a valid **single action** if you passed `single-action`; otherwise it exits without doing anything.

    **Solutions:**
    1. Use a **dedicated bot account** for the PAT (e.g. `copilot-bot`) so that the actor (developer) is different from the token user. Then the full pipelines run as expected.
    2. If you want to run only a specific action when you are the actor, use `single-action` (for example `check_progress_action`) so the action runs that command and exits.

    See [Authentication](/authentication) for token setup and the note on token user vs. actor.
  </Accordion>

    **"Permission Denied"** — Check token permissions, verify repository access, and review security settings.

    **"Resource Not Found"** — Verify the resource exists, check access permissions, and validate URLs and paths.

    **"Invalid Configuration"** — Review workflow syntax, check configuration values, and validate input parameters.

  <Accordion title="Bugbot autofix" icon="wrench">
    - **Bot didn't run autofix**: A configured `fixer` agent runtime must be available and the comment must be interpreted as a fix request (e.g. "fix it", "arregla", "fix all"). There must be at least one unresolved finding. On issue comments, the action needs an open PR that references the issue so it can resolve the branch to checkout and push; otherwise autofix is skipped.
    - **Commit not made**: Verify commands (`bugbot-fix-verify-commands`) run after the configured agent applies changes; if any command fails, the action does not commit. If there are no file changes after the fix, nothing is committed. If push fails (e.g. conflict or permissions), check workflow `contents: write` and that the token can push to the branch.

## Web configuration adjustments

If **Change** is unavailable, connect to GitHub and check whether both Variable
scopes can be read. Literal or complex workflow expressions, input environment
overrides and unreadable files require the complete assistant. The panel keeps
unknown values distinct from missing or disabled values.

A change during review or a browser control takeover invalidates the approval.
Review the refreshed value before trying again. A permissions failure allows a
corrected setup PAT; the guided link grants Variables Write only at the reviewed
scope and Variable reads for precedence. Cleanup or read-back uncertainty stops
the session with an inspection receipt. Check the actual GitHub Variable before
retrying; there is no automatic rollback of an unconfirmed remote write.

## Reuse and batch setup

| Result | Meaning and next action |
|---|---|
| Inventory unavailable | No assumption of absence was made. Restore metadata read access, then inspect the affected repository again. |
| Required binding missing | Provision the credential separately with current-repository Customize or grant its existing organization binding; reuse never requests or copies its value. |
| Waiting for merge | The setup PR exists. Review and merge it, then verify the installation. |
| Verification pending | Available metadata does not prove runtime capabilities. Inspect trusted default-branch checks or run the appropriate doctor verification. |
| Partial / stopped | Completed grants, repository resources and PRs remain. Inspect their receipts before the explicit retry. |
| Plan drift / moved head | No overwrite is attempted. Inspect the default branch and existing installer PR; renew the plan instead of force-pushing. |
| Workflow runners need review | Existing matching jobs retain their static runner labels/group. A dynamic runner expression or unreadable job definition blocks automatic upgrade; review its complete matrix/input contract separately, then prepare again. Newly added jobs keep template defaults and require runner inspection before merge. |
| Source Action workflows retained | Workflows calling the root-local `./` Action retain their native jobs and release configuration. Setup only adds the installer push exclusion to the source Commit workflow. The all-branch synchronization observer, other native workflows and complete source guidance remain in their existing version. A partially missing source guidance set blocks rendering: restore it with the checked-in source generator, then inspect again. Review their migration with the source generator; consumer templates cannot replace them. |
| Rate-limited | Reads honor a valid provider wait of up to 15 seconds, at most twice in three attempts. Missing, invalid or longer waits pause the target. Mutations are not automatically retried. Wait for access to recover, then inspect and explicitly retry. |
| Cleanup pending | Resolve the reported temporary probe resource before starting any installation work. |

A new process needs a fresh PAT and review. `--resume-operation <operation-id>`
reconstructs the same desired plan from the private receipt identities; it
rejects changed configuration/base/targets before probes. Shared grants are
additive; cancellation does not roll them back or revoke the operator PAT.


### Recover an orphaned batch operation lock

If setup reports an operation is locked, its error gives the exact private lock
path and operation ID. The lock contains a PID and nonce; a PID alone cannot
prove ownership because operating systems reuse it. Setup never automatically
removes an unknown or apparently stale lock.

On the same machine, use a single operator maintenance window:

1. Stop every setup session that could access this journal directory. Prevent
   new setup sessions during recovery. Do not recover a shared directory while
   another machine or user can start an owner.
2. Inspect the exact `<operation-id>.json.lock` and matching `.json` receipt.
   Check the recorded PID against the process command and start time. On Unix,
   `kill -0 <recorded-pid>` can establish that a process exists; permission denied
   or uncertain identity means stop and investigate. Only a confirmed absent
   owner, with all setup sessions stopped, permits the next step.
3. Remove only that confirmed orphaned lock (for example,
   `rm -- "$HOME/.copilot/setup-operations/<operation-id>.json.lock"` on Unix,
   replacing the placeholder with the ID from the error). Keep the receipt,
   installer branch and PR. Never remove a live/replaced lock or the directory.
4. Resume with `copilot setup --batch --resume-operation <operation-id>` and a
   current temporary PAT. Review the fresh inventory and retained effects before
   approving probes or writes. Release the maintenance window afterwards.

Resume rebuilds the shared-resource snapshot instead of restoring an old
process's in-memory grant revisions. A completed access effect does not repeat
its PUT; the new review uses current memberships and timestamps. Any rotation
or other revision change after that review still blocks Apply. A stale plan
passed directly to Apply is deliberately rejected rather than trusting an
unrecorded grant or ignoring Secret freshness.


When current-repository organization reuse reports configuration/access changed
after review, inspect the credential-health workflow too. Its installation or
removal changes required bootstrap permissions. Prepare and approve a fresh plan
instead of applying a previously audited permission set.

## Unsupported stored configuration

An issue or PR with an invalid stored Copilot block stops with
`configuration.invalid` and **Retryable: No**. The annotation and Job Summary
identify its number, the missing/unsupported/malformed state, the required
schema version (currently `3`), and the same reference. Retrying unchanged state
will fail again. The failed read does not change the body or stored state.

| Stored content | Meaning | Next action |
|---|---|---|
| No Copilot block | No previous state to restore | An unlinked PR can follow its normal PR workflow. |
| Missing schema, unsupported version, malformed JSON/value or incomplete delimiters | Stored state cannot be trusted | A maintainer must review it before retrying. |
| Valid current-schema block | Supported state | Continue through normal validation; this is not a reset instruction. |

An ordinary inline mention or closed code example containing only an opening or
closing marker is not stored state and does not cause a configuration error.
Complete legacy blocks inside code fences still undergo strict validation;
avoid reproducing complete live delimiter pairs in examples. Multiple complete
blocks or potential state behind an unclosed fence require maintainer review,
so Copilot never silently discards one record or chooses between conflicting
records. Reads and updates preserve the human description around the owned block.

Recovery is manual and depends on what the block owns:

1. Preserve the original body using GitHub history or a copy before editing.
2. If a maintainer verifies that the issue/PR is unmanaged and the block is
   only an obsolete marker with no branch, release, hotfix or orchestration
   state to retain, remove **only that block**, preserve the human description,
   and rerun the failed workflow. An obsolete reproduction example can instead
   show its JSON without live Copilot comment delimiters: the current reader
   also recognizes those delimiters inside fenced issue/PR examples.
3. If managed state may exist or ownership is unclear, stop. Ask a maintainer
   to inspect linked branches and operations and restore verified supported
   state through the supported workflow before rerunning. Do not discard
   unknown state.

Never repair this by merely adding `schemaVersion: 3`, changing a version number,
automatically migrating/resetting state, or turning the failed check into a
successful skip. A version field alone does not prove that the stored branch or
operation facts are valid. Authorization and temporary GitHub read failures
retain their own error categories; follow their permission/provider recovery
instead of deleting configuration.

## Branch sync catalog compatibility

`configuration.unsupported` with profile `legacy-evidence`, `native` or
`ambiguous` means the catalog does not establish the SDK version-1 contract.
`configuration.invalid` identifies an unknown shape or invalid SDK field.
The response names a closed phase, field and capability position: position 0
means the document; positive positions count entries from 1. Repository titles,
IDs, paths and validator output are excluded from this diagnostic.

For example, a catalog with `specs` and combined `evidence`, title-case
`Proposed` / `As-built baseline`, and historical null dates is identified as
`legacy-evidence`, field `workflows`. Copilot stops before a conflict fixer,
repository verifier, commit or push. It does not run the repository's validator
to certify a different schema. On conflicted JSON, both immutable original
catalog objects must establish SDK compatibility before a fixer can proceed.
A clean merged SDK catalog can establish a reviewed migration directly.

Conflicts in JSON alone receive these same checks. The resolved catalog still
has to pass full SDK validation. If its index was not authorized for refresh by
the original merge paths, Copilot checks that index without writing or staging
it. An `index-output` failure in this case requires a reviewed repair of the
catalog/index pair before retrying; it does not authorize an extra fixer path.
Metadata that merged cleanly is also classified before resolving another file's
conflict, then validated read-only after that resolution.

1. Inspect the workflow response and original catalog at the reported entry
   position. `abort: completed` means the local abort call finished;
   `unverified` requires inspecting the local merge state before retrying.
   Neither value certifies application readiness or executed tests.
2. Have maintainers review the intended catalog contract. Keep an exact copy of
   the original metadata and index in the review evidence. Preserve every
   combined/directory evidence item, unresolved decision and historical null
   or date in a reviewed extension or companion document. Never silently turn
   directory evidence into claims about individual source or test files.
3. If adopting SDK version 1, supply every path array and map only existing
   regular repository files to the correct roles. `specs` and `documentation`
   are nonempty; `workflows` may be empty. Only `proposed` entries may also have
   empty `entrypoints`, `code` and `tests`. Review status mapping explicitly:
   title-case legacy labels alone do not prove implementation. A new
   `lastVerified` records an actual metadata/document review; preserve its
   historical predecessor separately, and never describe that review as an
   application test run. Existing SDK entries may retain opaque evidence
   extensions, which do not satisfy required role arrays.
4. Run the trusted SDK catalog generation/validation commands from the
   [specification guide](/development/specifications#initial-catalog-generation),
   inspect the generated links and evidence, then review and merge the migration
   through the normal managed issue workflow. Repository-native `$schema` or
   `specification` formats need a supported adapter or an explicit reviewed SDK
   adoption; changing a version number alone does not provide either.
5. Adopt the corrected Copilot runtime through the normal installation route on
   the branch used by comment workflows, then retry `/copilot sync-branch` from
   fresh heads. Successful catalog validation establishes the catalog contract;
   the configured application verifiers must still pass before publication.

Catalog metadata and rendered output retain the existing fixed 10 MiB limit.
No new configuration, automatic conversion, date repair, evidence omission or
verification bypass is introduced. An incompatible catalog stays unchanged;
only an already-authorized generated index can be refreshed after SDK validation.

## Repository setup blocks verification

`Repository setup blocked verification` means preparation did not establish a safe
command environment. Verification and commit/push are withheld; branch sync uses
its existing merge abort. Inspect the native setup step and closed cause in the
run, then repair the reviewed action on `main-branch`.

| Cause | Recovery |
| --- | --- |
| `source-unavailable` | Make the trusted origin ref available in the full checkout. |
| `helper-invalid` | Review the fixed native composite and regular auxiliary files; respect file/step bounds and avoid nested local `uses`. |
| `native-workflow-required` | Update generated callbacks and use their normal directory-based Git checkout in GitHub Actions. The local CLI cannot execute composite actions. |
| `workspace-changed` / `candidate-changed` | Keep setup dependency-only; do not change publishable source, index, branch or lockfiles. Retry from a fresh candidate. |
| `process-failed` | Inspect the native action's logs and fix its reviewed dependency installation. |
| `timeout` | Fit each native setup within five minutes; no limit override or automatic retry exists. |
| `output-limit` | A Copilot worker log line/output exceeded its framing bound; native setup logs use normal Actions limits. |
| `cancelled` | Retry the authorized operation after cancellation is resolved. |
| `handoff-invalid` | Rerun through updated generated callbacks; never reuse a session from another run/job or request. |
| `result-invalid` | Export only supported, existing PATH/JAVA_HOME directories under the candidate, private HOME or trusted tool cache. |

The consumer file is `.github/actions/copilot-verification-setup/action.yml`.
Candidate edits do not replace the trusted snapshot. Enabling without a reviewed
action blocks verification; the disabled default preserves existing behavior.
See [repository-owned setup](/security-operations/operations/verification#repository-owned-setup)
for native Python/pnpm examples, profile lifetime, trust boundaries and migration.


### Sync branch cannot resolve workspace packages

If root build passes but a workspace typecheck reports missing tools, compare the installed graph with the actual merged candidate. In the source incidents tracked by [#746](https://github.com/vypdev/copilot/issues/746), Node/pnpm were present, but installation ran on `master` before the extension workspace existed. Commands after typecheck were not executed. Installing one extra member or disabling verification does not fix the sequencing error.

The corrected source coordinator provisions runtimes first and prepares the frozen candidate graph immediately before every verifier. Its sync result distinguishes dependency, native setup, runtime and command failures, and reports whether the original head was restored. Repair the reported prerequisite and inspect an unverified rollback before retrying. Confirm the corrected runtime and workflow are adopted on the default branch used by comment events: `develop` checks alone do not update a running `master` Action. Read [verification](./verification) for source limits and consumer setup alternatives.


### Issue work was skipped after early admission

Open **Admit issue event** in the native workflow Summary. `self-event` identifies
an internal product-account transition. `already-reconciled` means a completed
successful run from the same workflow covered this exact queued reconciliation;
it does not claim a new branch build or review. The normal issue/run links in
Actions remain the navigation surface. No conversation comment is added.

No receipt, an expired artifact, state/configuration/code changes, a failed or
canceled source run, a later deliberate request or a manual rerun all preserve
full runtime authorization and reconciliation. Optional artifact lookup/upload
failure never establishes permission to skip work. Partial effects retain their
normal recovery state. If authentication fails, repair the existing product
credential and rerun; do not broaden its scopes to enable receipt storage.

A pending issue workflow may be waiting for its own earlier run, without holding
a work runner. GitHub limits each multi-pending queue to 100; inspect native
canceled runs after saturation and rerun the needed intent when capacity returns.
Do not enable active cancellation or single-pending replacement as a workaround.
Older runtime references missing `issue-admission` require the matching runtime
upgrade before installing the new generated workflow. This upstream change does
not itself prove a consumer's queue improved.


## Collect logs when advisory checks appear as jobs

If `gh run view RUN_ID --repo OWNER/REPO --log` reports
`log not found: CHECK_ID`, inspect the native job inventory before retrying.
Optional `Copilot / Approval`, `Copilot / Review` or `Copilot / Verification`
checks published by the GitHub Actions app can appear beside executable jobs
with zero steps and no assigned runner. Those advisory records have check
output, rather than an executed job log. This does not establish the cause of
the workflow's own success or failure.

1. Select the exact run and attempt. For a complete collection, wait for its
   real jobs to finish. Inventory every page; the endpoint below explicitly
   selects the latest attempt. When auditing an older attempt, use the native
   `/actions/runs/RUN_ID/attempts/ATTEMPT/jobs` endpoint instead.

   ```bash
   gh api --paginate \
     'repos/OWNER/REPO/actions/runs/RUN_ID/jobs?filter=latest&per_page=100' \
     --jq '.jobs[] | {id, name, status, conclusion, runner_id, stepCount: (if (.steps | type) == "array" then (.steps | length) else null end)}'
   ```

2. Match each record to the native run. Inspect advisory check output separately
   when a completed zero-step/no-runner record corresponds to a Copilot check.
   A name or missing log alone does not prove a record advisory.

   | Native record | Next action |
   |---|---|
   | Completed job with execution steps | Fetch that exact job ID, including failed jobs |
   | Confirmed completed advisory check without steps/runner | Read its check output; no job execution log is expected |
   | Queued or running job, possibly without steps/runner yet | Keep it pending; wait for execution/completion |
   | Skipped job | Preserve the skip and its condition; do not call it executed or advisory |
   | Missing/incomplete metadata or failed inventory request | Keep collection incomplete; investigate the actual API error |

3. Retrieve each real job independently with the ID from that inventory:

   ```bash
   gh run view --repo OWNER/REPO --job JOB_ID --log
   ```

   Preserve every command's exit status and any partial output. A whole-run
   command may already print real logs before failing on an advisory record.
   A failed per-job download for an executable job remains a genuine collection
   failure; inspect the native job, access, availability or log retention rather
   than suppressing it. Continue collecting other available real jobs, but call
   the bundle partial until all intended executable jobs are accounted for.
   `--log-failed` alone does not collect successful-step evidence.

The supported per-job command is documented in the
[GitHub CLI manual](https://cli.github.com/manual/gh_run_view); native job and
attempt inventories are described in the
[Actions jobs API](https://docs.github.com/en/rest/actions/workflow-jobs).
An exported log proves what that job recorded, not that its workflow passed.
Keep required failures, review findings and coverage results unchanged. No
check deletion, permission expansion, token replacement, workflow rerun or
blanket error suppression is needed for this read-only collection route.
