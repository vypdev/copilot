# Application error reference

Every failure presentation uses the same order: impact, stable error code,
recommended action, retained state, retryability, then a correlation UUID.
Search the Job Summary and sanitized logs using that UUID; it is safe to include
in a support request. Do not include credentials or private provider output.
Repository-aware views use the configured repository locale and default to
English. Error codes and references never translate.

| Code | Meaning | Action |
| --- | --- | --- |
| `configuration.invalid` | A configured value or combination is invalid. | Correct the configuration and retry. |
| `configuration.unsupported` | This installation cannot provide the requested capability. | Select a supported configuration or update the installation. |
| `authorization.denied` | The actor or credential lacks required authority. | Grant the documented permission and retry. |
| `authorization.credential-invalid` | A required credential is missing, rejected, or expired. | Replace or configure the credential and retry. |
| `provider.not-found` | A required provider resource does not exist. | Verify the target resource and retry. |
| `provider.conflict` | Current provider state conflicts with the operation. | Reload current state and retry only if still needed. |
| `provider.rate-limited` | The provider temporarily limited requests. | Retry after the provider limit resets. |
| `provider.unavailable` | The provider or transport is temporarily unavailable. | Retry when the provider is available. |
| `provider.contract-invalid` | A provider response could not be interpreted safely. | Review the integration before retrying. |
| `agent.policy-rejected` | Fixed policy rejected the agent execution plan. | Use an allowed agent configuration. |
| `agent.failed` | An admitted agent did not produce a usable result. | Inspect sanitized agent status and retry if appropriate. |
| `locale.output-invalid` | Generated product content violated its target-locale contract. | Retry with a provider compatible with the configured repository locale. |
| `locale.translation-failed` | An addressed request could not be safely adapted to the target locale. | Rephrase the request or retry when the language provider is available. |
| `validation.evidence-unavailable` | A required patch is omitted/incomplete and bounded immutable content recovery cannot verify complete regular UTF-8 text (including a lockfile or binary change). The diagnostic identifies unreviewed paths. Progress was not assessed; existing labels and assessments remain unchanged. This is nonretryable. | Inspect the intended native PR target and exact pinned paths, then supply complete reviewable evidence. Actually changed binary contents require source and provenance; metadata or a successful build is not binary review. Retrying the same commits does not repair unavailable immutable contents; manual inspection does not certify Copilot completion. |
| `validation.evidence-too-large` | Progress evidence or immutable recovery exceeds a fixed file/byte/request/directory/unit/aggregate/partition-count limit. Existing labels and assessments remain unchanged; this is nonretryable. | Inspect the complete pinned comparison and reported capacity. Supported recovery continues automatically across bounded parts/frames. After interruption, rerun the current managed source to collect a fresh complete attempt. Identical over-limit input cannot gain capacity; preserve coherent scope and review any unsupported total limit. |
| `validation.invalid-input` | Entrypoint input is malformed. Comment-command failures identify the safe syntax/limit cause without echoing input. | Follow the shown command example and [argument rules](/issues/comment-commands#argument-rules-and-rejected-commands), then send a corrected comment. Other entrypoints retain their own recovery. |
| `workflow.invalid-event` | The event cannot start the requested workflow. | Start from a supported event or surface. |
| `workflow.stale` | A newer durable state superseded this invocation. | Inspect current state and start a fresh invocation only if needed. |
| `workflow.cancelled` | The operation was explicitly cancelled before completion. | Start a new invocation if the operation is still required. |
| `workflow.failed` | Orchestration failed without a narrower classification. | Inspect current state and retry the failed step. |
| `timeout` | A bounded operation exceeded its deadline. | Verify current state before retrying. |
| `unexpected` | An unclassified failure was handled safely. | Investigate with the correlation ID before retrying. |

Retryability is determined by the code. A specific operation can make a
normally retryable failure terminal, but presentation never turns a terminal
code into a retry recommendation.

For stored issue/PR state, `configuration.invalid` includes the affected number,
the expected schema version, and a missing-schema, unsupported-version or
malformed-content diagnosis in the failure annotation and Job Summary. It
remains nonretryable until corrected; the same correlation reference survives
to the final Action failure. The read does not rewrite the body. Use
[stored-configuration recovery](/security-operations/operations/troubleshooting#unsupported-stored-configuration):
only a verified obsolete unmanaged block may be removed after preserving a
copy. Potentially valuable managed state requires maintainer review and verified
restoration. Provider/authentication failures are not schema failures.

Some partial operations add a closed recovery variant, for example to name a
retained managed branch or a closed issue whose final explanation was not
published. These variants use reviewed catalog templates and only bounded,
validated variables; feature code cannot replace them with arbitrary prose.

Provider exceptions are not diagnostics for public surfaces. They remain a
private in-memory cause even if a catch block interpolates or assigns the value
to another local variable; the architecture guard follows those derived values
and rejects any attempt to log them. Setup resource summaries and lifecycle
synchronization likewise use fixed semantic messages. Maintainers must call
`toApplicationError` before logging a caught value and must never copy provider
message text into that safe message. Provider-returned observation reasons are
untrusted too: before setup or deployment renders them, secret patterns are
redacted and GitHub workflow commands, markup and mentions are neutralized.


Pre-branch SDD validation failures also publish a reusable issue status card.
Open its safe validation details and inspect the exact check and available
section/row/count evidence before retrying. The one existing format regeneration
receives only normalized host check/section/row/count facts, never rejected content. Undefined links and
uncovered goals include the first relevant data-row ordinal; derived slots
distinguish occurrence count from visible placement. All publication checks
remain mandatory, and no extra regeneration is added. An unavailable diagnostic
is not proof that the candidate or validator is correct. Existing specifications and
answers remain; see [blocked preparation recovery](/issues/pre-branch-sdds#when-specification-preparation-is-blocked).


Undersized draft responses use nonretryable `validation.invalid-input` with
`sdd-draft-response-too-short`. The validated recovery contains only `minimum`,
`observed` and `attempts`; its phase is draft response. The minimum remains
1,800 Unicode code points. An unretained observed length is `unavailable`, not
zero. Clarify the complete proposed Markdown requirement in the issue description,
preserving resolved requirements and ownership, then retry its normal workflow.
Existing answers, owner and specifications remain. This cause adds no generation
attempt, relaxes no acceptance bound and is separate from provider unavailability.
See [undersized draft recovery](/issues/pre-branch-sdds#undersized-draft-response).

Managed SDD resource diagnostics show the measured stage, observed amount, and
allowed amount in the same unit. Provider transport and token failures have
separate diagnoses. A composed update can offer a specific companion for
maintainer approval when its existing owner cannot accept the delta. See
[SDD recovery](/issues/pre-branch-sdds#size-and-format-repair).

SDD source-view failures use `validation.evidence-unavailable` with
`sdd-source-context-unavailable`. The only recovery facts are the immutable
`sourceCommit`, `phase` and closed `reason`; unverified identity is `none` /
`unknown`. Check the linked run, local selected Git objects, `--no-lazy-fetch`
support, portable regular source paths and the fixed SDK limits. Correct the
prerequisite and retry the same issue workflow. The canonical checkout, answers,
published SDDs and linked branch remain; no model repair or publication is
attempted. Do not restore files into the default checkout or create a branch
manually. See [source selection](/issues/pre-branch-sdds#source-used-by-analysis-and-drafting)
and [execution limits](/agents/execution-contract#immutable-sdd-source-views).

Catalog profile failures use `configuration.unsupported` with the closed
`sdd-catalog-unsupported-profile` or `sdd-catalog-format-invalid` recovery.
Review [SDD publication profiles](/issues/pre-branch-sdds#catalog-publication-profiles)
before retrying the same issue. The diagnostic preserves repository-native
schema/readiness, answers and historical publication; a rejected profile does
not publish a branch or start the model.

Confirmed catalog absence at the trusted revision uses `configuration.unsupported`
with `sdd-catalog-missing-trusted-source`. The owned preparation card identifies
`specs/catalog.json` and its immutable source SHA. Review and merge the prerequisite,
update the displayed trusted source through the normal branch workflow, and retry
the same issue after that source changes. Existing answers, specifications and any
linked branch are retained. A Git object/read failure keeps its distinct error
classification. See [missing trusted catalog recovery](/issues/pre-branch-sdds#missing-catalog-in-the-trusted-source).

For progress, a unique exact same-repository PR owns the comparison base; only
proven absence uses development. Inherited production libraries can therefore be
unchanged in the real PR delta. If binary/non-text changes remain unsupported,
`progress-binary-evidence-unavailable` adds an inert bounded path excerpt and
complete inventory in run logs. Up to eight whole paths fit 8,192 diagnostic bytes;
total/shown counts disclose the excerpt. Progress is unassessed and retained;
project verification is a separate result. Do not manufacture a passing status,
retarget a legitimate PR or split production binaries just to obtain text patches.



## Complete progress evidence capacity

`validation.evidence-too-large` may carry
`progress-evidence-capacity-exceeded`. Its public variables are exactly
`phase`, `dimension`, `unit`, `bound`, `observedCount`, `supportedLimit`,
`countKind` and `context`. `maximum` compares measured or required usage with
available capacity; `minimum` reports a missing minimum. `exact`, `at-least`
and `unavailable` distinguish a completed measurement, a stopped scan and
missing facts. Out-of-range integer allocations retain known bounds; unknown
or unrepresentable allocations never become negative or invented counts.

Source, original scope, part prompts, reserved replacement prompts, receipt
envelopes and aggregate facts are separate dimensions. Known comparison context
contains actual base/head, source-manifest digest when available, separate
required/accepted/uncovered path-inventory digests and reconciled counts, plus
up to eight inert uncovered path excerpts within 8,192 serialized bytes. A
known original physical source line remains attached. `none` means that the
manifest or line identity is unavailable at this boundary; verified zero
coverage remains distinct from unavailable context. Model receipt acceptance
does not certify CI, tests or review.

Existing progress is retained. Supported parts continue within one invocation;
this nonretryable capacity error stops it. Preserve complete evidence and
requirements when reporting the diagnostic and run link. Identical input
cannot gain capacity, and partial receipts are not a durable checkpoint.
Existing inventory, source, scope and model-response recoveries retain their
own contracts. See [capacity troubleshooting](./troubleshooting#complete-progress-evidence-capacity).

## Invalid completed progress result

`agent.failed` can describe a process failure or an invalid returned assessment.
Completed progress contract rejections additionally identify
`progress-result-contract-invalid`. Inspect its phase, reviewed reason, known
field and any verified requirement/original-issue line. For example, requirement
`R2`, original line `L7` and `$.requirements[1].evidence` point to an invalid
evidence field. The array index is a field location, not a requirement identity.
`none` explicitly means an identity is unavailable; no positional or repeated-
quote anchor is inferred. Blank lines keep their original physical numbering.

The result remains rejected and prior labels/assessments remain unchanged. A
fresh attempt can help if the provider can return conforming data for the same
requirements; deterministic limits and unsupported contracts cannot be fixed by
repeating identical invalid data. Inspect the linked run and named schema rule;
do not weaken acceptance, verification or strict output validation, and do not
dump raw model output. JSON/schema/semantic details use only bounded reviewed
codes and fields, never returned values, unknown property names or exceptions.
Existing execution/transport classification and retryability remain unchanged.
A later optional Check Run 403 is secondary and retains the primary failure and
correlation reference.

For an eligible final completion contradiction, the host makes one complete read-only
reassessment after all other checks pass. Both full prompt envelopes are admitted
before the first model request. Each acceptance batch has one allowance. No third query, source recollection, partial
assessment publication or write retry is allowed. If the second final response
still contradicts completion, `agent.failed` has recovery
`progress-completion-recovery-exhausted`, with exactly five numeric observations
of that response. For example:

{/* progress-completion-example */}
```json
{
  "code": "agent.failed",
  "correlationId": "11111111-1111-4111-8111-111111111111",
  "recovery": {
    "id": "progress-completion-recovery-exhausted",
    "variables": {
      "reportedProgress": 100,
      "requirementCount": 32,
      "supportedCount": 29,
      "missingCount": 2,
      "unknownCount": 1
    }
  }
}
```

These illustrative counts are not independent execution evidence. CLI, API,
Check and Summary retain the same error code and correlation reference. Inspect
the complete pinned comparison and final facts at `assessment / $.progress`;
start a fresh complete assessment when the provider can satisfy the unchanged
contract. Existing labels and assessments remain. Verification, review, coverage
and approval are independent gates. Malformed output, provider interruption and
other semantic failures retain their own error and do not receive this recovery.

A completed acceptance response exceeding its current `summary` or `remaining`
schema bound can use that same single replacement allowance. Native measurements
must bind to the exact captured schema, current batch receipts and citations,
requirement, source anchor and locale. The host checks the rest of the complete
schema before admitting recovery. Neither length nor completion recovery can
allocate a third query, including when the two failure kinds alternate.

If the replacement still exceeds a fact bound, `agent.failed` uses
`progress-assessment-length-invalid` with exactly five closed observations:

{/* progress-assessment-length-example */}
```json
{
  "code": "agent.failed",
  "correlationId": "11111111-1111-4111-8111-111111111111",
  "recovery": {
    "id": "progress-assessment-length-invalid",
    "variables": {
      "requirementId": "R11",
      "sourceLineId": "L11",
      "field": "$.requirements[0].remaining",
      "maximum": 54,
      "observed": 62
    }
  }
}
```

These counts are illustrative Unicode code points, not the unavailable rejected
Domus prose or its actual lengths. Inspect the named fact and unchanged limit in
the linked run. A fresh complete assessment can help when the provider can meet
that contract. Existing progress remains; provisional batches are never published.
No rejected prose, clipping, enlarged limits, omitted requirements or source
recollection enters the correction. Foreign identities, incomplete output,
infrastructure failures and other invalid contracts retain their own errors.

For `assessment-text-limit`, the host reports the first source-ordered aggregate
overflow and its actual response-array summary/remaining field. Every full
original citation, ID, separator and newline participates in the unchanged
8,000-code-point limit; the per-fact ceiling remains 800. Generation derives a
smaller fact schema limit when needed. Older uneven facts remain valid when
the complete projection fits; no prose is clipped.

`validation.evidence-too-large` with `progress-assessment-capacity-exceeded`
means classification succeeded but the original citations leave insufficient
space for one nonempty fact per requirement. No evidence or final assessment
query follows. This is nonretryable for identical scope, preserves prior
progress and cannot authorize a passing verification. Inspect the exact original
scope and review a supported assessment protocol while preserving acceptance.
See [progress text capacity](./troubleshooting#progress-assessment-text-capacity).

### Progress part response length

An overlong file fact with a verified current part/path/unit, locale and schema
limit receives one replacement for the same complete immutable part. Every
original and replacement request is capacity-checked before the first part
query. Source evidence, identities, uncertainty and strict validation remain
unchanged. Provider, cancellation, locale and other schema failures retain their
own classifications and do not start this recovery.

Persistent overflow reports `agent.failed` with
`progress-partition-length-invalid`: part, path, unit, response field, maximum
and observed Unicode code-point count. `none` means the legacy part has no unit
identity. Paths are inert reversible JSON code spans; raw model output is never
shown. Inspect that fact in the linked run. There is no third part query, no
clipping, and no partial update to labels or the previous assessment. A later
optional Check Run warning remains a separate outcome.

## Optional Check Run publication not confirmed

This warning concerns an optional evidence projection. Required-stage success
or failure and completed external effects are preserved. It has its own safe
provider details; an earlier required error's correlation reference does not
identify this Check Run failure.

```text
Optional Check Run publication not confirmed
Impact: Native check status is not confirmed. The workflow result and existing Job Summary remain authoritative.
Cause: GitHub denied the check publication request. Credential type and exact policy cause are not inferred.
Action: Verify repository access and Checks write on the dedicated evidence credential. Keep the product token separate.
Retained state: Required-stage results and completed external effects were preserved.
Details: operation=checks.create; check=Copilot / Verification; head=<full SHA>; credential-route=action-token-fallback; error=authorization.denied; status=403; request=AB12:CD34
```

For 401/403 inspect the dedicated credential/access and the job's Checks write
permission. For 429 or an explicit secondary limit follow provider guidance. For
400/422/404 inspect the target/request or visibility. For 409/412 inspect the
conflict and existing check. For 408/5xx/known transport errors publication is
unconfirmed: a check may already exist. Without classified facts, the cause is
unknown; do not claim an outage. No automatic publication retry is made.

Only an integer HTTP status and a bounded colon-separated hexadecimal request
reference are exposed. Invalid fields become unavailable; credentials, response
bodies, authentication headers, URLs and raw exception messages are omitted.
The primary warning is in the log and a Summary appendix; if the appendix fails,
a localized note points back to the retained log. For credential selection and
the supported default, see [workflow setup](/issues/workflow-setup).


## Missing logs for advisory checks

If GitHub CLI whole-run log retrieval reports `log not found: CHECK_ID`, use the
[paginated inventory and per-job collection guide](/security-operations/operations/troubleshooting#collect-logs-when-advisory-checks-appear-as-jobs).
Collect real execution jobs by their native IDs and inspect advisory check output
separately. Preserve pending/skipped states, failed downloads and any partial
output. Required workflow results and existing review/coverage conclusions keep
their original meaning.

## Missing publication context

If `create_release` cannot load its durable deployment operation, it reports
`configuration.invalid` and stops before creating a GitHub release. Missing
context does not mean a newer state superseded the run. Persisted state and
completed external effects, including any previously published packages, remain
preserved; the message makes no claim that a release is absent remotely.

Verify `single-action-issue` selects the existing launcher issue and restore its
verified operation context. Only then retry the supported release/hotfix workflow
with the same `single-action-operation-id` and `single-action-version`. Do not
create a new operation, publish packages again, or bypass the stored ID, version,
phase and accepted production SHA checks to clear this error. See
[single-action configuration](/single-actions/configuration#internal-operation-identity).

## Complete Bugbot review blocked

`validation.evidence-unavailable` with recovery `bugbot-review-incomplete` means
a complete source-bound Bugbot review could not be verified. It is nonretryable
for identical unsupported input. The closed diagnostic reports the resource,
measured count, supported limit and unit; `≥` is an explicit lower bound. A zero
limit on an integrity diagnostic means no failures are acceptable, not a file
quota. Existing findings and resolution state remain; no partial frame or clean
review was published by this attempt.

Restore unavailable immutable Git objects through the Action-managed checkout
or synchronization flow, correct the source/identity evidence, or review the
PR's intended scope when it exceeds the finite profile. Start a fresh complete
review afterward. Do not add ignores, relax controls or treat a build/coverage
report as review proof. See [Bugbot recovery](/bugbot/failure-scenarios) and
[large-diff bounds](/bugbot/how-it-works#complete-review-of-large-diffs).

## Progress scope clause capacity

`progress-sdd-seed-unverified` means Commit could not bind a marked maintainer
draft to its selected SDD publication and evaluated head. Verify the current
selection and the published SDD on the linked branch before retrying. Existing
progress is retained.

`progress-batch-retained` reports nonretryable
`validation.evidence-unavailable` when the complete same-head receipt inventory
cannot be verified. Closed facts identify the reason, verified and expected
batches, failing batch and a host-verified requirement ID. Reasons distinguish
source coverage, manifest or batch identity, missing evidence, incompatible
receipts, call or time budget and aggregate capacity. Inspect the current run,
resolve the condition and start a complete assessment. Previous labels and
published progress remain available.

`progress-evidence-capacity-exceeded` identifies an over-limit summary or
remaining fact, or a complete projected field, with its measured and allowed
Unicode-point counts. Its assessment context includes the full requirement
count, host-known batch and requirement ID. Batch 0 and requirement `none` mean
complete reduction. No rejected text is retained. All batches use the same
complete-inventory allocation; an alternate query port cannot admit longer facts.

Semantic remaining rejections distinguish `requirement-remaining-null-required`
(supported requires null), `requirement-remaining-string-required` (missing or
unknown requires text), `requirement-remaining-blank` (whitespace only), and
`requirement-remaining-too-long` (above 800 Unicode points). Original requirement
and source-line anchors remain visible. The historical
`requirement-remaining-invalid` code does not establish which violation occurred.
Native schema errors retain their schema reason. Inspect the original requirement
and the named rule; preserve all scope, evidence and verification gates.

`progress-scope-clause-limit` remains the diagnostic for the legacy direct
single-assessment parser and historical runs. Current Commit supports bounded
batches of 32 obligations within its reviewed aggregate profile. Malformed
persisted state fails through the configuration-error family before model
queries. Rejected model prose is excluded from diagnostics.

## Assignment failures

`issue-assignment-count-invalid` uses nonretryable `configuration.invalid` when
the shared workflow receives a count outside its integer `0`–`10` contract.
Correct `desired-assignees-count` and rerun the same issue workflow. No assignment
operation was attempted; independent completed effects retain their own results.
The descriptor has no parameters and never echoes the supplied invalid value.

`issue-assignment-failed` identifies the assignment stage and safe provider
operation, target number, bounded HTTP status (or unavailable), current-read
certainty, observed/confirmed/remaining counts, and assignment-write certainty.
An unverified write may already have applied; do not treat zero confirmed new
assignments as proof of zero external changes. The same workflow rereads current
assignees before retrying missing work. Independent completed lifecycle effects
are retained in their own results.

Known denied/authentication failures are not retryable outages. A 403 with
rate-limit evidence or a 429 uses `provider.rate-limited`; recognized transport,
408 and 5xx failures use `provider.unavailable`. Unknown exceptions are
`unexpected`, with no invented transient cause. Malformed lists/rows use
`provider.contract-invalid`, rather than becoming an empty membership list.
For 404, check access and target; private-resource absence cannot be inferred.
Raw assignment-provider exceptions are discarded after their safe classification.
See [assignment recovery](/issues/assignees-and-projects#recover-an-assignment-failure).
