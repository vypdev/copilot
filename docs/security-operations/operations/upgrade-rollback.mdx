# Upgrade and rollback procedure

## Upgrade

1. Select one provider and one version.
2. Verify its release and checksum when applicable.
3. Update the repository or organization variable.
4. Run provisioning, help, focused tests, and a read-only smoke test.
5. Run the complete gates before enabling the version for write workflows.

For the published Copilot CLI, use `copilot upgrade` to select the latest version:

```bash
copilot upgrade
copilot --version
```

This updates the active npm or pnpm installation in its existing prefix/global
directory. Success requires both the installed package and the command resolved
through `PATH` to report the selected version. A failed verification does not
roll back an installer that already completed: inspect the effective command,
refresh the shell cache or open a new terminal, and retry. Other global copies
and shell configuration are preserved.

For a controlled rollout or rollback, install a specific package version explicitly:

```bash
VERSION=<known-good-version>
pnpm add --global "@vypdev/copilot@${VERSION}"
copilot --version
```

Use `@latest` only when the latest published release is intentionally selected. Keep explicit versions for reproducible rollback procedures.

## Upgrade an existing Copilot repository

Copilot has three separate versioned layers:

| Layer | What changes it | What still needs review |
|---|---|---|
| Installed CLI | `copilot upgrade` or an explicit npm/pnpm package version | The CLI prepares local files; it does not rewrite committed workflows merely by upgrading |
| Remote Copilot reference | Action and reusable-workflow `uses` references in committed workflows | `@v3` follows the published major tag; an exact version or commit SHA stays pinned until explicitly changed |
| Generated workflow files | An approved `copilot setup --update-workflows` run | New jobs, inputs and coordinator calls must be committed, reviewed and merged |

Moving a tag does not add steps to an old YAML file. Upgrading the CLI does not
change the Action references in Git. A merge into `develop` is not a package or
Action release: first select a [published release](https://github.com/vypdev/copilot/releases)
that contains the required setup and native verification support.

For verification setup adoption:

**1. Record the existing installation.**

Start with a clean branch, record the currently reviewed workflow references,
and keep `VERIFICATION_SETUP=false` during preparation. Inspect the effective
repository/organization value; a repository Variable overrides an inherited
organization value.

**2. Upgrade the CLI and preview.**

Upgrade the CLI and confirm `copilot --version`. Preview the installation:

```bash
copilot upgrade
copilot --version
copilot setup --web --dry-run
```

**3. Regenerate and review workflows.**

Before upgrading the comment callbacks, update self-hosted GitHub Actions runners
to **2.336.0+**. The centralized coordinator uses GitHub.com's self-repository
references to keep its internal Action on the exact selected workflow commit.
Verify platform support before adopting this format on other GitHub deployments.
Check that the repository/organization Actions policy permits the published
`vypdev/copilot/.github/workflows/copilot_comment_runtime.yml` reusable workflow
at your selected ref, as well as the existing Copilot Action.
If the existing comment jobs have custom dependency/bootstrap steps, migrate them
into the reviewed repository setup action before replacing those jobs; setup
blocks silently dropping them. Keep the prior reviewed callbacks until this is
ready. See [repository-owned setup](/security-operations/operations/verification#repository-owned-setup).

Apply a reviewed workflow upgrade:

```bash
copilot setup --web --update-workflows
```

The shared assistant also works in the terminal without `--web`. Keep the
verification setup question disabled for this preparation pass. Review the
displayed create/preserve result and changes before approval. The installer
creates `.github/actions/copilot-verification-setup/action.yml` only if absent;
existing action bytes and auxiliary files are preserved through upgrades.
Generated comment callbacks use
`vypdev/copilot/.github/workflows/copilot_comment_runtime.yml@v3`; other generated
callbacks continue using `vypdev/copilot@v3`. The coordinator owns setup,
continuations and cleanup in one job, keeping consumer YAML compact. If your
repository pins versions or SHAs, update the reusable-workflow and remaining
Action references to the chosen compatible published release. You do not edit
the internal `uses: $/` references: GitHub pins them to the called workflow commit.
The reviewed runner route is retained in the comment call's `with.runs-on` JSON.
Workflow backups are retained under `.copilot/setup-backups/`.

**4. Customize and merge on trusted main.**

Replace the starter's failing placeholder with reviewed project-specific
dependency preparation. Commit the action, its auxiliary files and the updated
workflows. Review and merge them onto the configured trusted `MAIN_BRANCH`;
the installer PR's default target may differ from this trusted branch. Follow
the repository's branch/promotion process until both contain the reviewed
changes. Creating or merging an installer PR alone does not verify the runtime.

**5. Activate verification setup.**

Re-run the assistant and enable **Prepare dependencies with the repository
verification setup action?**, or use:

```yaml
repository:
  verificationSetup: true
```

Setup writes `VERIFICATION_SETUP` only when Variable management is enabled
and follows the reviewed storage/reuse policy. With `--skip-variables`, update
the effective Variable manually. Confirm that generated workflows pass the
`VERIFICATION_SETUP` Variable through the coordinator (or the direct Action's
`verification-setup` input), and that the trusted action has been customized.
Choose **Customize** when changing an existing repository Variable; **Reuse**
keeps existing values. If an organization value must differ for this project,
select `VERIFICATION_SETUP` in the repository Variable overrides and review the
scope before Apply.

**6. Verify actual execution.**

Run `copilot doctor --read-only`, then an authorized write/sync operation that
actually executes the configured verification commands. Inspect the native
action and verifier results; a doctor pass, dry run or already-aligned sync
does not prove dependency preparation.

To roll back adoption, first set the effective `VERIFICATION_SETUP=false` (or
answer No with Variable management enabled). This stops the optional hook and
retains the existing verification commands. Restore the previous reviewed
workflow files and Action refs together if necessary, and install the prior CLI
version explicitly. Consumer action files are retained; restore any owner changes
through Git review instead of asking setup to overwrite or delete them. Inspect
partial setup receipts and GitHub resources before retrying a failed upgrade.

## Rollback

1. Restore the last known-good version variable.
2. Re-run provisioning and verification.
3. Confirm the qualified model and allowlists did not change.
4. Run a read-only smoke test.
5. Re-enable write permissions only after the rollback passes.

Rollback MUST restore a complete known-good tuple; changing only the binary while keeping incompatible command or model settings is not a valid rollback.

For a Codex model-only rollback from the current `gpt-6-luna` default, restore
both repository Variables to the previous known-good pair:
`AGENT_MODEL=gpt-5.6-luna` and
`AGENT_ALLOWED_MODELS=openai/gpt-5.6-luna`. Keep any other explicitly
allowlisted role models, and verify the effective tuple with a read-only smoke
run. Source and generated-workflow defaults are changed only by a reviewed
repository change; setting one Variable alone is not a complete rollback.
