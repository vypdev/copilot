# Single Actions Configuration

These inputs are used when you run the action in single-action mode. For the complete list of all action inputs, see [Configuration](/configuration).

## Required for single-action mode

| Input | Description | Example |
|-------|-------------|---------|
| `single-action` | The action to run | `check_progress_action`, `think_action`, etc. |
| `token` | GitHub PAT (required for almost all single actions) | `${{ secrets.PAT }}` |

## When the action needs an issue

For `check_progress_action`, `detect_potential_problems_action`, `recommend_steps_action`, `publish_issue_comment`, and every workflow-owned deployment action:

| Input | Description | Example |
|-------|-------------|---------|
| `single-action-issue` | Issue number to run the action on | `'123'` |

A positive, validated `single-action-issue` takes precedence over issue/PR
payloads, branch names and tag refs. The Action checks that exact native target;
a missing target or failed lookup cannot redirect execution to another issue.
If the target is a PR, its managed head branch must identify the associated
issue. `initial_setup` remains repository-only, and actions without an
explicit positive target retain their documented optional/event context.

`close_inactive_issues_action` does not use `single-action-issue`. It scans the
repository's open issues carrying a waiting-state label. Configure its optional
`inactivity-threshold-hours` input (default: `168`) or the
`INACTIVITY_THRESHOLD_HOURS` Repository Variable.

### Internal operation identity

`create_tag`, `create_release`, `publish_github_action`,
`continue_deployment_action`, `published_deployment_action`, and
`failed_deployment_action` require `single-action-operation-id`. It must be the
exact durable ID supplied by Copilot for that launcher issue. The workflows also
pass the matching version where applicable. `prepare_deployment_action` creates
the operation ID and instead requires issue, version, title, and changelog.

A tag-triggered `create_release` restores the operation from the explicit
launcher issue even when the tag payload carries no issue field. It must still
match the stored operation ID, version, allowed publication phase and accepted
production SHA. If the durable operation is unavailable, publication stops
before creating a release. Inspect the selected issue and restore its verified
operation context, then retry the supported workflow with the same operation ID
and version. Existing persisted state and completed external effects remain
preserved; missing context alone does not establish that a newer state
superseded the invocation. See the [error reference](/security-operations/operations/error-reference#missing-publication-context).

These workflow-owned actions belong to `release_workflow.yml`, `hotfix_workflow.yml`, and
`copilot_deployment_orchestration.yml`; do not invoke them manually or reuse an
ID across issues.

## Publishing an issue comment

`publish_issue_comment` requires `single-action-message` and creates a new
Markdown comment when no comment ID is supplied. To update an existing comment,
pass `single-action-comment-id`; the default mode is `replace`, while
`single-action-comment-mode: append` keeps the previous body and adds the new
message. An explicit `create` mode rejects a comment ID so configuration errors
cannot silently update the wrong comment.

## When the action needs a version

For workflow-owned `create_tag`, `create_release`, and
`publish_github_action`:

| Input | Description | Example |
|-------|-------------|---------|
| `single-action-version` | Version string (e.g. semver) | `'1.2.0'` |

`single-action-issue` and the exact
`single-action-operation-id` created for that issue. It is accepted only in the
publish phase of the matching durable release or hotfix operation; it is not a
standalone publication command. Release title and changelog come only from the
durable operation created by `prepare_deployment_action`.

## Example: workflow with single action

```yaml
- uses: vypdev/copilot@v3
  with:
    token: ${{ secrets.PAT }}
    single-action: check_progress_action
    single-action-issue: '123'
```

Use the supplied release/hotfix workflows for publication; direct examples are
intentionally omitted because there is no standalone or local compatibility path.

See [Workflow & CLI](/single-actions/workflow-and-cli) for more examples and CLI equivalents.

## Replacement proof inputs

`replace_deployment_action` is only the final step of the supplied serialized
release/hotfix `replace` workflow. It requires the existing issue/version and
operation ID plus all five declared inputs below. Generic `INPUT_VARS_JSON`
cannot synthesize a replacement or override these proofs. The local CLI rejects
this action before composing deployment capabilities.

| Input | Default | Meaning |
|---|---|---|
| `single-action-expected-revision` | empty | Exact previous positive durable revision |
| `single-action-reviewed-source-sha` | empty | Full corrected SHA reviewed before preparation |
| `single-action-candidate-sha` | empty | Full resulting SHA after complete project validation and normal push |
| `single-action-production-base-sha` | empty | Native production base fixed by read-only preflight |
| `single-action-confirm-unpublished` | false | Explicit confirmation after checking every project registry |

Title and changelog must remain empty; their stored values are retained. The
final adapter checks the native run, attempt, workflow path and successful
preflight/producer steps. Calling the single action from another job or passing
only a SHA does not establish fresh validation. See
[unpublished candidate recovery](/issues/deployment-orchestration#replace-an-unpublished-candidate)
for the supported operator flow.
