# Available single actions

This page lists every **single action** you can run with the `single-action` input: required inputs, what it does, and when to use it.

## Actions that require an issue

These actions need **`single-action-issue`** set to the issue number. The workflow should run in a context where the **branch** to use is the one you want (e.g. checkout that branch before calling Copilot, or use the default branch for the repo).

| Action | Required inputs | Description | When to use |
|--------|-----------------|-------------|-------------|
| **`check_progress_action`** | `single-action-issue` | Runs **progress check** on demand. The configured agent compares the issue description with the branch diff and updates the **progress** label (0–100%) on the issue and on any open PR for that branch. | Progress is normally updated on every **push** (commit workflow). Use this to re-run without pushing, or when you don’t use the push workflow. |
| **`detect_potential_problems_action`** | `single-action-issue` | **Bugbot:** the configured agent analyzes the branch vs base and reports findings on the issue when no PR exists, or in one summarized review on an open PR; updates stored findings and resolves PR threads when findings are fixed. | Same as push-time Bugbot but on demand. See [Bugbot](/bugbot). |
| **`recommend_steps_action`** | `single-action-issue` | Uses the configured agent's analysis role to recommend **implementation steps** from the issue description; **posts a comment** on the issue with the steps. | When you want a one-off suggestion for how to implement the issue. |
| **`publish_issue_comment`** | `single-action-issue`, `single-action-message` | Creates a Markdown comment. With `single-action-comment-id`, it replaces that issue comment by default; set `single-action-comment-mode: append` to preserve its current content and append the message. | Reusable workflow notifications such as release or hotfix failures. |

## Actions that do not require an issue

| Action | Required inputs | Description | When to use |
|--------|-----------------|-------------|-------------|
| **`think_action`** | — | **Deep code analysis** and change proposals via the configured agent. You can pass a question (e.g. from CLI with `-q "..."`). No issue required. | One-off reasoning over the codebase; use from CLI or a workflow that provides context. |
| **`initial_setup`** | — | Performs **initial setup**: creates labels, issue types (if supported), verifies access. If the repo has no version tags, creates default tag **`v1.0.0`** so release/hotfix issues get a base version. No issue required. | First-time repo setup; run once or when you add new labels/types. Run on new repos before creating release/hotfix issues to avoid "Unknown Version" loops. |
| **`create_release`** | `single-action-version`, `single-action-title`, `single-action-changelog` | Creates a **GitHub release** with the given version, title, and changelog (markdown body). | From a workflow after tests pass; use version and changelog from your build or inputs. |
| **`publish_github_action`** | `single-action-version` | **Publishes or updates** the GitHub Action: creates/updates the major version tag (for example, `v3` from a `v3.x.y` release) and the corresponding GitHub Release. Requires that `create_tag` has been run first to create the source tag `v{version}`. | In a CI job that builds and publishes the action, after `create_tag` and `create_release` have run. |
| **`close_inactive_issues_action`** | — (`inactivity-threshold-hours` optional) | Scans open issues waiting for a maintainer or issue author and closes those whose `updated_at` exceeds the configured inactivity window. Revalidates each candidate before closing and posts an explanation. | From the scheduled `copilot_close_inactive_issues.yml` workflow; no issue number is required. |
| **`check_branch_sync_action`** | — | Discovers open issue/PR branch relationships and updates stale/aligned notices without invoking an agent. | From the supplied all-branch `copilot_branch_sync.yml` observer; normally do not invoke it manually. |

## Workflow-owned deployment actions

These values are part of the Action contract so the supplied workflows can
publish or resume a durable operation. They are not general-purpose manual
commands and always validate the operation ID, issue, version, phase, and
accepted SHA that apply to them.

| Action | Required inputs | Workflow owner | Purpose |
|---|---|---|---|
| **`create_tag`** | `single-action-issue`, `single-action-operation-id`, `single-action-version` | Release/hotfix `publish` mode | Create or verify immutable `v<version>` at the production SHA accepted by that durable operation. |
| **`prepare_deployment_action`** | `single-action-issue`, `single-action-version`, `single-action-title`, `single-action-changelog` | Release/hotfix `prepare` mode | Snapshot configuration, create durable state, and create or reuse the production promotion PR. |
| **`continue_deployment_action`** | `single-action-issue`, `single-action-operation-id` | `copilot_deployment_orchestration.yml` | Verify the managed PR marker, repository, branches, stored SHA, and phase before advancing. |
| **`published_deployment_action`** | `single-action-issue`, `single-action-operation-id`, matching `single-action-version` | Release/hotfix `publish` mode | Record verified publication, project the `deployed` fact, and create reconciliation PRs. |
| **`failed_deployment_action`** | `single-action-issue`, `single-action-operation-id`; matching version/message when provided | Release/hotfix failure job | Record the phase failure as retryable while preserving tags, packages, releases, PRs, and SHAs already accepted. |

Copy or generate the shared continuation together with every release/hotfix
publisher you enable. This project enables both publishers. Do not invent an
operation ID or replay one from another issue: mismatches fail closed.

## Actions that fail the job on failure

These single actions **throw an error** if their last step fails, so the **workflow job** is marked as failed and you can block deployment or notify:

- **`publish_github_action`**
- **`create_release`**
- **`create_tag`**
- **`close_inactive_issues_action`**
- **`publish_issue_comment`**
- **`prepare_deployment_action`**
- **`continue_deployment_action`**
- **`published_deployment_action`**
- **`failed_deployment_action`**

Use them when you want the workflow to **fail** if the action does not succeed (e.g. release creation or tag creation fails).

## CLI-only: do (no single-action equivalent)

The **`copilot do`** CLI command (for example, `copilot do -p "..."`) uses the configured fixer/build agent to analyze or modify code. There is **no** `single-action` equivalent in the GitHub Action; it is available only from the CLI. Use it for interactive or scripted code changes with AI. See [Workflow & CLI](/single-actions/workflow-and-cli) for all options, provider overrides, output formats, and environment variables.

`publish_issue_comment` additionally requires `single-action-message`. Its optional
`single-action-comment-id` selects an existing comment, and
`single-action-comment-mode` accepts `create`, `replace`, or `append`.

The workflow-owned rows require `single-action-operation-id`, except for
`prepare_deployment_action`, which creates the operation ID. Do not pass that
input to ordinary single actions.
