# Final progress completion recovery

- Status: Draft proposal for Action input; not a published SDD or implementation acceptance
- Date: 2026-11-02

## 1. Executive summary

A completed final estimate sometimes contradicts its own otherwise valid requirement statuses. Preserve rejection and existing progress, but allow one complete read-only replacement with the same immutable evidence, scope, schema and model settings. Never repair source evidence, normalize a percentage into completion, or infer that verification/approval passed.

```text
complete pinned evidence -> strict final assessment -> valid result -> existing publication fences
                                | only completion contradiction
                                v
                     one complete same-source replacement
                          | valid -> same fences
                          | invalid -> retain previous progress and report safe facts
```
Text equivalent: only a narrowly classified completed contradiction reaches one replacement; every accepted result still passes the original publication owner.

## 2. Problem, current behavior, and evidence

Observed: PR #852 failed Commit at heads 3ecade3154f25a11bb3a8107dc1cd3d4185dfd3c and dca6114af8cf92eadf35e2a217479c90e61347ef, comparison base9d3915729c96ec93c6e064d3321ba54c790170eb. Runs41414634366 (two attempts) and41418428579 reported progress-completion-mismatch at $.progress after CLI completion. The prompt clarification alone did not resolve the incident. The actual rejected percentage/counts are unavailable; neither contradictory direction is alleged for those runs.

Current host parsing rejects both directions, preserves progress and provides a compatible five-field rejection. The final assessment has no automatic replacement. #830 addresses a separate per-part length failure and must remain separate. This is a prospective correction, not an as-built claim or executed acceptance. Existing evidence: the progress scope parser, final analysis workflow and immutable comparison SDDs in section20.

## 3. Actors, surfaces, and terminology

Actors: the issue author supplies scope; maintainers inspect Commit/errors; the configured model produces untrusted estimates; the host validates facts; the existing publication owner controls labels and cards. Surfaces: CLI, API error JSON, Check and Job Summary, existing progress card and operator documentation. A completed contradiction means a completed, fully validated response whose percentage alone violates completion equivalence. Counts are host-computed facts about that model response, not independent implementation or execution evidence. A replacement is a new complete final query, never a partial replay.

## 5. Current versus proposed product journey

Current: scope extraction and all parts succeed, then one final contradiction blocks without actionable counts. Proposed: preflight both final envelopes before any scope query; collect the same scope/parts once; query and parse final; replace only a host-created eligible mismatch; publish only after complete validation and native freshness. A persistent contradiction stops and exposes closed numeric facts. Ordinary valid input stays one final request. Cancellation and unrelated validation failures keep existing behavior.

## 6. Functional behavior and state model

States: preflight -> collecting -> final -> accepted, or eligible-mismatch -> replacing -> accepted/exhausted. Preflight failure makes zero model calls. No state publishes provisional percentages.

Eligibility requires complete adapter output, strict JSON/native and local schema, locale, exact keys/cardinality/unique in-scope IDs, status/evidence and uncertainty rules, nonempty summaries, supported/null equivalence, finite percentage0..100, every fact limit and both complete citation projections. Only the final completion equivalence may fail. Both all-supported with70 and any unfinished requirement with100 remain invalid;99.9 is never rounded into completion. A second contradiction is terminal. An unrelated replacement failure retains its category. Each new invocation starts fresh; no rejected state or allowance is replayed.

## 7. User-facing configuration

No new configuration. Keep the configured provider/model/effort and all existing repository/operation locale precedence. Recommended en-US and alternative es-ES use the same rules; unsupported locale follows existing whole-message fallback. Snapshot the original final request; optional undefined fields remain absent/undefined rather than being invented. No persistent migration. One eligible replacement, count bounds, complete evidence, capacities and all approval gates are intentionally not configurable.

## 8. Clean Architecture design

Domain owns closed numeric validation and immutable facts. The existing parser creates an application-only ProgressCompletionMismatch after all earlier checks. Its safe message/code/recovery and correlation preserve direct-parser compatibility; frozen numeric facts stay private. A narrow query_progress_assessment_workflow owns orchestration through the existing FindingsQueryPort and queryProgressResult. Query awaits execute outside a parse-only catch; provider-thrown typed lookalikes cannot allocate recovery. An evaluate-once owner returns either the normalized valid result or a closed mismatch outcome; raw rejected payload is not carried into the next await or prompt.

Capture a structured clone of original configuration/options/schema and recursively freeze only that clone. Keep the original prompt string, host-frozen scope/anchors and exact source identities. Replacement changes only a fixed reviewed footer plus validated previous-result numeric data. Those observations are untrusted model facts, never execution attestation; reassess complete evidence and preserve genuine uncertainty.

Pure binding validates total against the same current scope. Adapters retain process, DTO and credential concerns; presentation has no mutation authority. Existing module/port/dependency and raw-error logging guards remain unchanged. The helper has no publication capability.

AgentQueryOptions has no absolute assessment deadline: preserve existing per-admitted-query runtime timeout/cancellation and the native outer workflow deadline; do not invent a deadline field, reset the workflow budget or add timeout overrides. Disclose at most one additional bounded query. An observed timeout/cancellation cannot enter recovery.

## 10. Failure, recovery, and cleanup

Initial unrelated schema, locale, capacity, provider, process, timeout and cancellation failures retain their original identity and make no replacement. A valid replacement returns once to the existing publication owner. A second fully validated contradiction emits agent.failed with closed recovery progress-completion-recovery-exhausted and its own five numeric facts; no third request or partial progress. Correlation comes from the terminal rejection and is reused by every surface. Direct parser callers retain progress-result-contract-invalid and its original five-field recovery.

Do not claim a GitHub multi-call transaction: acceptance is atomic before publication, while an actual publication failure preserves existing provider/partial-effect classification. Never repeat writes automatically or claim no effect when one may have committed. Remove ephemeral failed outcomes; preserve prior durable progress, native state and necessary safe evidence. Fresh replay repeats complete scope/evidence collection under existing fences, not a cached partial result.

## 16. Acceptance scenarios

Given an initially valid final response, one final query produces the unchanged accepted estimate after all publication fences. Given either otherwise valid contradiction, exactly one complete same-source request may replace it; it can produce valid complete or partial progress without promoting uncertainty. Given another contradiction, previous progress remains and only its closed numeric facts/correlation render. Given malformed output, locale/evidence failure, provider lookalike or cancellation, no completion recovery is allocated. Given capacity shortfall, no scope query occurs. Given a moved head/base/native target/body or closed issue during replacement, no obsolete estimate publishes. Given a publication failure, preserve actual partial-effect classification and do not repeat writes. A fresh same-head invocation starts a complete new assessment. The forty cases provide detailed executable controls; external coverage/review/approval are separate evidence.
